## 5. 阶段二：KnowledgeDocument、Chunk 与 RAG 边界设计

### 5.1 核心概念
明确区分：
- **KnowledgeDocument：** 原始知识资料及其业务身份、来源、版本、权限和生命周期。
- **Chunk：** 从文档切分出的检索单元，保留与原文档的稳定关联、定位信息和必要检索元数据。

不得混淆原始文档、Chunk、Embedding、检索结果和模型回答。

### 5.2 KnowledgeDocument 元数据
逐字段给出字段名、类型、必填性、含义、来源、可变性、约束/索引建议。至少评估：
- 稳定标识：documentId；
- 业务信息：标题、文档类型、设备型号/系列、适用范围；
- 来源追踪：来源系统、原始文件标识、文件名、内部存储定位；
- 版本有效性：版本号、生效/失效时间、状态；
- 组织权限：租户/工厂/组织范围、可见范围、授权主体或权限策略引用；
- 生命周期：创建、更新、审核、发布、归档状态及时间；
- 内容治理：语言、摘要、内容哈希、解析状态；
- 扩展属性：仅在有真实需求时使用受控扩展字段。

说明权限数据来源和实际校验责任；不得只把权限字段当作检索标签。说明文档更新后旧 Chunk、索引和缓存的失效/追溯策略。避免存储不必要的敏感个人信息。

### 5.3 Chunk 元数据
逐字段说明类型、必填性、含义、来源和约束。至少评估：
- chunkId、documentId、documentVersion；
- chunkIndex、页码/章节/段落/字符偏移等定位信息；
- 文本内容或内容引用、内容哈希、长度（仅记录真实计算值）；
- Embedding 模型/维度/版本、向量记录标识（未实现字段标为规划项）；
- 设备型号、故障码、部件、维修类别等业务标签（仅在来源可确认时使用）；
- 权限继承规则，确保切分不会扩大父文档访问范围；
- 解析、切分、向量化、索引状态及版本关联。

说明 Document 与 Chunk 一对多关系、重切分/重嵌入版本策略、去重策略、元数据过滤与向量检索职责，以及本轮必需字段和后续字段的区别。

### 5.4 RAG 模块边界
结合现有架构评估以下逻辑职责，不要求机械拆成独立 Maven 模块：
1. Knowledge Ingestion：知识接入；
2. Parsing：文档解析；
3. Chunking：切分与定位；
4. Metadata：元数据、版本和权限关联；
5. Embedding：向量生成；
6. Vector Store：向量写入、删除和查询；
7. Retrieval：召回、过滤及必要的重排；
8. Context Assembly：证据整理与上下文构造；
9. RAG Generation：基于证据生成回答；
10. Evaluation：固定问题集、运行结果和评测记录。

输出职责边界表，包含每项职责的输入、输出、依赖和本轮状态（已有/本轮定义/后续规划）。明确 Controller、应用服务、领域模型、基础设施适配层的依赖方向。供应商 SDK 和向量数据库实现不得无理由泄漏到领域模型或业务接口。

### 5.5 设计决策
关键选择需给出推荐方案、备选方案、理由、适用边界和未来调整触发条件。不得过度抽象。本轮只形成设计，不因设计表格自动创建生产代码、数据库表或新依赖；若认为必须落地，先说明原因、范围和风险。

## 6. 阶段三：20 条起步评测问题集

### 6.1 数量与覆盖
设计**至少 20 条固定问题**，建议分布如下，可按真实资料调整，但四类重点场景必须覆盖：

| 类别 | 建议数量 | 目的 |
|---|---:|---|
| 有答案：设备/维修知识 | 6 | 验证证据召回和回答 |
| 有答案：故障码 | 4 | 验证故障码与型号/版本关联 |
| 无答案/证据不足 | 4 | 验证拒答、澄清和防编造 |
| 权限隔离 | 4 | 验证无权用户无法检索或获知受限知识 |
| 组合/边界 | 2 | 验证多条件、型号歧义或版本差异 |

资料不足时不得编造答案或证据。可将用例设计为“当前知识库应判定无答案”，并说明缺少的资料。

### 6.2 每条用例的固定字段

| 字段 | 要求 |
|---|---|
| caseId | 唯一编号，如 D25-EVAL-001 |
| category | answerable / unanswerable / permission / fault-code / boundary |
| question | 固定问题原文，后续不得随意改写 |
| userContext | 必要的角色、工厂/设备范围；不需要则明确无 |
| expectedDecision | answer / abstain / deny / clarify |
| expectedAnswerPoints | 应回答的关键事实；无答案项说明不可回答内容 |
| expectedEvidence | 文档标识、版本、章节/页码/Chunk 或证据特征 |
| forbiddenClaims | 无依据结论、危险建议或越权信息 |
| acceptanceCriteria | 可检查的通过条件 |
| sourceStatus | 真实资料支持 / 当前缺少资料 / 待业务确认 |

### 6.3 质量要求
- 问题具体、可复现，避免无法稳定验收的泛化问题。
- 故障码必须绑定设备型号/系列和资料版本，不假设跨设备通用。
- 无答案项说明知识库缺少什么证据，期望拒答或澄清，不得用模型常识补齐。
- 权限项定义测试身份、允许/禁止范围和期望结果；必须在证据暴露前完成权限控制。
- 答案要点与期望证据分开；答案正确但证据不支持，不算完整通过。
- 固定问题文本、用户上下文和预期判定，供后续 Chunk、Embedding、检索、重排和 Prompt 变更回归比较。
- 每条用例保留来源；没有真实来源时标记待补资料，不得虚构文档编号、页码或 Chunk ID。

### 6.4 评测判定
逐条定义：
1. 决策行为是否正确（回答/拒答/拒绝访问/澄清）；
2. 关键答案点是否覆盖；
3. 引用证据是否真实、版本正确且支持结论；
4. 是否出现无证据事实或危险维修建议；
5. 权限隔离是否有效；
6. 输出是否符合接口约定。

可定义命中率、Recall、MRR 等指标及计算口径，但未运行真实 RAG 系统时不得填写虚构数值，统一标记“待后续实际评测”。
