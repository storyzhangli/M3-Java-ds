## 一、需求概述

在 D33「检索 → 组装 → 生成」RAG 最小闭环之上，插入**证据评估门禁（Evidence Assessment）**，实现：

- **基于证据回答**：仅当证据充分（直接陈述或证据支持的有限推断）时允许进入生成；
- **无证据/低相关/冲突拒答**：无检索结果、低相关命中、覆盖不足一律拒答，且**模型零调用可核验**；
- **澄清**：缺设备型号/故障代码等必要条件时，复用确定性澄清策略（零模型费用）；
- **冲突受控**：有效证据对同一事实矛盾时返回 CONFLICT，禁止"按版本号一刀切"；
- 响应统一返回「回答/澄清/拒答/冲突 + 来源 + 状态」，决策轴与链路状态轴**双轴分离**；
- 落实**多层安全**：文档生命周期过滤 → `UNTRUSTED_EVIDENCE` 不可信标记 → Grounding Prompt → 引用 ID 合法性与事实支持关系两类校验 → 业务控制层拒答，明确"Prompt 不是唯一防线"。

**明确不做**：不重做 D33 闭环；不做 Agent/MCP/Reranker/混合检索/多轮对话；不允许模型用常识补全设备参数、故障代码、维修步骤或伪造引用。

## 二、架构与职责边界

### 2.1 处理流程（在 D33 链路中插入证据评估门禁）

```text
用户设备故障问题
      |
Retrieval（候选证据 + 来源/版本/生命周期）
      |
Evidence Assessment（生命周期过滤 → 型号匹配 → 相关性 → 澄清 → 冲突 → 充分性）
   |        |          |           |
 充分     信息不足     冲突       缺条件
   |        |          |           |
允许生成   拒答      受控处理     澄清
      |
Context Assembly（仅评估通过证据 + UNTRUSTED_EVIDENCE 标记）
      |
Generation + 引用清洗（ID 合法性） + 生成后校验（事实支持关系）
      |
回答 / 来源 / 澄清 / 拒答原因 / 冲突状态
```

### 2.2 职责边界

| 组件 | 职责 | 边界 |
|---|---|---|
| `EvidenceAssessmentService`（新增） | 确定性证据评估，输出 decision/reasonCode/充分性/冲突分组 | 不调用模型、不触发检索 |
| `PostGenerationValidator`（新增） | 答案事实支持关系校验（新故障码/数值参数必须映射到已接受证据） | 只做事实支持；引用 ID 合法性由 CitationRegistry 承担 |
| `RagOrchestrator`（重构） | 编排：检索 → 评估门禁 → 组装 → 生成 → 生成后校验 | REFUSE/CLARIFY/CONFLICT 三分支模型零调用 |
| `RagRetrievalService` | 检索通道（适配真实 pgvector） | 不调 ChatModel |
| `ContextAssemblyService`（扩展） | 组装 + `UNTRUSTED_EVIDENCE` 结构化包裹 | 只消费评估通过的证据 |
| `GenerationService`（扩展） | `RAG_SYSTEM_PREFIX` v2：三区分/澄清/注入防护/服务端决策约束 | 不访问 VectorStore |

相似度分数只是检索信号，不能证明证据充分，不得仅按 Top-K 第一条决定回答。

### 2.3 决策轴与状态轴（双轴分离）

- **决策轴** `RagDecision`：`ANSWER / CLARIFY / REFUSE / CONFLICT`，承载业务语义；
- **状态轴** `RagStatus` 五态 → **七态**：`SUCCESS / NO_HIT / NO_USABLE_CONTEXT / CLARIFY_REQUIRED / EVIDENCE_CONFLICT / RETRIEVAL_FAILED / GENERATION_FAILED`。

一个请求同时携带两个轴：如"拒答"（REFUSE）可对应 NO_HIT（空检索）或 NO_USABLE_CONTEXT（低相关/覆盖不足）；"证据冲突"（CONFLICT）对应 EVIDENCE_CONFLICT。互斥语义不混用。

### 2.4 稳定原因码（8 项，接入 `RagReasonCode`）

| reasonCode | 触发语义 |
|---|---|
| `NO_EVIDENCE` | 知识库无任何检索结果 |
| `LOW_RELEVANCE` | 仅关键词相似，证据不能支持问题 |
| `INSUFFICIENT_EVIDENCE` | 有相关证据但覆盖度不足（含全被生命周期过滤、全为其他型号、组装无可用内容） |
| `MISSING_REQUIRED_CONTEXT` | 缺设备型号/故障代码等必要条件，需澄清 |
| `EVIDENCE_CONFLICT` | 有效证据对同一事实给出矛盾内容 |
| `INVALID_CITATION` | 引用不在本次来源白名单或格式非法 |
| `UNSUPPORTED_CLAIM` | 输出含无证据支持的设备参数/故障码/维修步骤 |
| `GENERATION_VALIDATION_FAILED` | 生成后校验未通过的受控失败 |

## 四、文档生命周期落地

- `DocumentLifecycleStatus` 枚举：`DRAFT/ACTIVE/DEPRECATED/EXPIRED`；`isUsableForEvidence` 统一收口：仅 ACTIVE 且已生效（effectiveAt 空视为立即生效）、未过期（expiresAt 空视为不设过期）可用。
- 字段传播链：`DocumentChunk(+3) → RetrievalHitView(+3) → RetrievedChunk(+3)`，全程使用**额外便利构造器**保留旧构造签名，5 个既有 `DocumentChunk` 构造点零改动；`toVectorDocument` 写 metadata；`RetrievalHitMapper` 读取。
- 历史数据缺失 lifecycle 元数据视为兼容（解析失败/为空时不主动过滤），避免存量向量被一刀切拒之门外。
- MySQL `knowledge_document` 表加 `lifecycle_status/effective_at/expires_at` 三列属 schema 变更：DDL 脚本落 `docs\temp_docs\D34\d34-mysql-lifecycle-ddl.sql`，**由用户手动执行**，未自动 ALTER。
