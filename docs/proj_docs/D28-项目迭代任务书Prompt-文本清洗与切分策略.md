## 三、本次功能需求

### 1. 文本清洗组件

基于 D28 已有的 PDF 文本解析结果，建立独立的文本清洗组件。

要求：

- 统一处理换行符。
- 清理不必要的首尾空白。
- 处理连续空格及异常空白字符。
- 识别并处理无意义的空行。
- 处理明显的重复换行。
- 尽可能保留标题、段落及列表结构。
- 避免破坏原始文本中的有效语义。
- 保留原始文本与清洗后文本之间的必要关联。

特别注意：

1. 不得简单删除所有换行符。
2. 不得将所有空白字符无差别替换成一个空格。
3. 不得破坏标题、段落和列表之间的结构关系。
4. 不得擅自删除有意义的标点、数字、单位及技术术语。
5. 清洗操作必须具备可测试性。

如果 PDF 解析结果中已经包含页码信息，清洗后必须保留其来源关系。

建议区分：

- 原始提取文本。
- 清洗后的规范化文本。
- 清洗过程中的来源元数据。

不得因为文本清洗而丢失原始页面定位信息。

### 2. 可配置 Chunk 切分组件

建立独立、可复用的文本切分组件。

要求：

- 支持配置切分策略。
- 支持配置 Chunk Size。
- 支持配置 Chunk Overlap。
- 支持必要的最小 Chunk 长度。
- 支持必要的最大 Chunk 长度。
- 支持按标题或段落组织切分。
- 支持极短段落处理。
- 支持超长段落二次切分。
- 不同切分策略能够独立执行和比较。

配置必须与切分算法分离，避免将参数散落在业务代码中。

优先使用项目现有配置方式。

如果引入新的配置类，明确参数含义、默认值、取值范围和校验规则。

### 3. 固定长度切分

实现固定长度切分策略。

要求：

1. 根据配置的 Chunk Size 切分文本。
2. 根据配置的 Overlap 保留相邻 Chunk 的重叠内容。
3. 避免因为切分位置不合理而破坏明显的语义边界。
4. 对超长文本进行连续切分。
5. 正确处理最后一个不足 Chunk Size 的片段。
6. 不得产生无意义的空 Chunk。
7. 明确长度计算单位。

特别注意：

字符数不等于 Token 数。

本轮必须明确当前采用的长度单位：

- Java String 的 UTF-16 code unit 数量。
- Unicode 码点数量。
- Token 数量。

如果当前没有引入可靠的 Tokenizer，优先实现字符长度策略，并明确其与真实 Token 长度之间的差异。

不得将字符数直接宣称为 Token 数。

### 4. 按标题与段落切分

实现基于文档结构的切分策略。

要求：

- 优先识别已有的标题和段落边界。
- 尽量让一个 Chunk 保持完整的段落语义。
- 多个短段落可以在合理条件下合并。
- 超长段落需要进一步切分。
- 尽可能避免在句子中间截断。
- 对没有明确标题结构的文本提供合理降级方案。

对于 D28 PDF 解析结果：

- 优先利用已有页面边界。
- 尽可能保留段落与页面的对应关系。
- 不得假设所有 PDF 都能够准确提取标题层级。
- 对无法识别的结构明确说明处理策略。

### 5. Chunk 元数据与来源定位

每个 Chunk 必须保留必要的来源元数据。

至少包括：

| 字段           | 说明                          |
| -------------- | ----------------------------- |
| documentId     | 原始知识文档 ID               |
| title          | 原始文档标题                  |
| pageNumber     | 对应 PDF 页面序号，适用时保留 |
| paragraphIndex | 原始段落索引，适用时保留      |
| chunkIndex     | 当前文档内 Chunk 索引         |
| version        | 原始文档版本                  |
| content        | 当前 Chunk 文本               |

要求：

1. Chunk 必须能够关联原始 documentId。
2. 能够定位到原始 PDF 页面。
3. 如果来源具有段落索引，尽可能保留。
4. chunkIndex 必须具有明确的编号规则。
5. chunkIndex 在同一文档版本内必须稳定且有序。
6. 不同文档之间不能因为索引相同而产生身份混淆。
7. 文档版本变化时，必须能够区分不同版本的 Chunk。
8. 清洗、切分不得破坏来源元数据。

特别注意：

- 一个 Chunk 可能跨越多个段落。
- 一个 Chunk 可能跨越多个页面。
- 如果发生跨页或跨段落合并，不能只保留第一个来源而丢弃其他来源。
- 必要时使用来源范围或来源列表记录多个来源。
- 对没有可靠页码或段落信息的文本，允许对应字段为空，但必须明确标注来源定位能力边界。

本轮重点是实现可追溯的 Chunk 元数据，不是建立复杂的知识图谱。

### 6. 切分策略效果对比

必须使用同一份原始文档或相同的清洗后文本，对不同切分策略进行对比。

至少比较：

1. 固定长度切分。
2. 按标题/段落切分。

建议对比以下指标：

| 指标       | 对比内容                         |
| ---------- | -------------------------------- |
| Chunk 数量 | 最终生成多少个 Chunk             |
| 平均长度   | Chunk 平均字符长度               |
| 最大长度   | 最大 Chunk 长度                  |
| 最小长度   | 最小 Chunk 长度                  |
| 长度分布   | 不同长度区间的分布情况           |
| Overlap    | 相邻 Chunk 重叠情况              |
| 语义完整度 | 标题、段落和句子是否被不合理截断 |
| 来源定位   | 能否定位 documentId、页码和段落  |
| 空 Chunk   | 是否产生无效文本片段             |

要求：

- 对比数据必须来自真实运行结果。
- 使用相同输入文档保证对比公平。
- 不得只通过主观描述判断哪种策略更好。
- 选取典型 Chunk 展示切分前后文本。
- 对切分质量进行人工抽查。
- 说明两种策略的适用场景与局限。

语义完整度允许采用人工抽查和明确的检查标准，不要求本轮引入额外大模型进行语义评分。
