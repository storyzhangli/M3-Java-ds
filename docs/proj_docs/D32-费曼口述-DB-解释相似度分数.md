# 费曼口述：解释相似度分数（Similarity Score）

说话人1: 费曼口述，解释相似度分数（Similarity Score）。主题是 RAG 检索中相似度分数的计算原理、数值含义、阈值校准与工程应用。共七十道关键问题，分七个阶段，从相似度分数的基本认知、余弦相似度、内积与欧氏距离、不同距离度量的分数方向与数值含义、分数与 Embedding 模型的关系、RAG 检索中的分数与阈值，到分数的工程应用与评估。技术基线为 JDK 21、Spring Boot 3.5.x、Spring AI 1.1.8、PostgreSQL 18.6、pgvector 0.8.x。训练范围覆盖底层数学原理、pgvector 源码机制、Spring AI API 调用、生产阈值校准和面试综合表达，以制造设备故障知识库 RAG 检索为应用场景。

---

## 一、相似度分数的基本认知

说话人1: 问题一，什么是 Embedding 向量？文本经过 Embedding 模型处理后，为什么会变成一组浮点数？
说话人1: 答，Embedding 向量就是把一段文本编码成一个固定长度的浮点数数组。为什么会变成浮点数？因为 Embedding 模型本质上是一个神经网络。输入文本经过 Tokenizer 切成 Token，每个 Token 转成初始向量，然后经过几十层 Transformer 编码器，最后池化成一个固定长度的输出。这个输出就是一组浮点数，比如 1024 维，每个维度是一个神经元的激活值。
说话人1: 举个例子，"电机无法启动"这句话，经过 BGE-M3 模型，输出 1024 个浮点数，第一个维度可能是 -0.0234，第二个是 0.0567……这 1024 个数合起来，就表达了这句话的语义。
说话人1: 这里要注意，每个维度本身没有人类可解释的含义。你不能说第 100 维代表"电机"。它是模型在训练过程中自己学出来的，整体表达语义。

说话人1: 问题二，什么是相似度分数？它在 RAG 检索流程中承担什么作用？
说话人1: 答，相似度分数就是两个向量之间的接近程度的量化值。在 RAG 里，它的作用是：用户提问的 Query 向量，和知识库里面每一个 Chunk 向量算一个分数，然后按分数排序，取最靠前的 TopK 个 Chunk，交给 LLM 作为上下文。
说话人1: 它是检索排序的唯一依据。没有相似度分数，向量数据库就不知道哪个 Chunk 跟用户问题最相关。
说话人1: 但这里有个关键认知：相似度分数是"粗筛"的结果，不是最终答案正确性的保证。它只是说"这段文本在语义上跟 Query 接近"，不代表"这段文本一定能回答用户的问题"。

说话人1: 问题三，相似度分数是如何产生的？用户 Query 和知识库 Chunk 分别经过哪些处理才能进行比较？
说话人1: 答，两边都要先过 Embedding 模型。
说话人1: 知识库侧：文档解析 → 清洗 → 切分成 Chunk → 每个 Chunk 调 EmbeddingModel.embed() → 得到向量，存到 pgvector 表里。
说话人1: 用户查询侧：用户输入问题 → 可能先做查询改写 → 调同一个 EmbeddingModel.embed() → 得到 Query 向量。
说话人1: 然后用 SQL，比如 SELECT content, embedding <=> query_vector AS distance FROM chunk_table ORDER BY embedding <=> query_vector LIMIT 5; 算出每个 Chunk 和 Query 之间的距离，按距离排序。
说话人1: 这里有个前提：两边必须用同一个 Embedding 模型。如果 Chunk 用 BGE-M3 编码，Query 用 OpenAI text-embedding-3-small 编码，那两个向量不在同一个空间，算出来的相似度毫无意义。

说话人1: 问题四，为什么两个文本的向量距离或相似度可以用于衡量它们的语义接近程度？
说话人1: 答，因为 Embedding 模型是专门训练过的。训练的时候，用对比学习：把语义相近的文本对作为正样本，让它们的向量距离近；把不相关的文本对作为负样本，让它们的向量距离远。
说话人1: 经过海量数据训练之后，模型就学会了把语义相近的文本映射到向量空间中相近的位置。所以你拿两个新文本，算它们的向量距离，就能大致判断语义接近程度。
说话人1: 这不是魔法，是训练出来的。模型见过几百万、几千万对文本对，学会了"意思相近的词在向量空间里应该放一起"。

说话人1: 问题五，相似度分数越高，是否一定代表两个文本在业务含义上越接近？为什么？
说话人1: 答，不一定。相似度高，只代表"语义上接近"，不代表"业务上相关"。
说话人1: 举个设备故障的例子。用户问"E101 故障怎么处理"。知识库里面有一篇讲"E101 报警的含义说明"，另一篇讲"E101 故障的维修步骤"。两篇的向量都跟 Query 很接近，因为都提到了 E101。但用户要的是维修步骤，不是含义说明。相似度分数可能两篇都很高，但只有一篇是真正有用的。
说话人1: 还有更极端的：两篇文档主题完全不同，但用词很像，相似度也会高。比如"电机过热保护触发"和"电机过载保护触发"，向量很接近，但故障原因不一样。
说话人1: 所以相似度高 ≠ 业务相关。这就是为什么后面还要加 Rerank，还要加 Metadata Filter。

说话人1: 问题六，相似度分数与文本匹配程度、语义相关性和答案正确性之间是什么关系？
说话人1: 答，这是三个不同层级的概念，一层比一层要求高。
说话人1: 最底层：文本匹配程度。就是字面用词像不像。关键词检索 BM25 算的是这个。
说话人1: 中间层：语义相关性。就是意思像不像。向量相似度算的是这个。
说话人1: 最顶层：答案正确性。就是这段文本能不能真正回答用户的问题。这个连向量检索都做不到，要靠 Rerank 和 LLM 生成。
说话人1: 向量相似度解决的是"语义相关性"，不是"答案正确性"。从语义相关到答案正确，中间还有很长的路。

说话人1: 问题七，相似度分数是概率吗？为什么不能将 0.9 直接理解为模型有 90% 的把握认为文档正确？
说话人1: 答，不是概率。
说话人1: 余弦相似度的取值范围是 [-1, 1]，但它不是概率分布。它只是衡量两个向量方向的夹角大小。
说话人1: 你看到余弦相似度 0.85，不能理解成"模型有 85% 的把握认为这段文档是正确答案"。它只是说"这段文档的向量方向跟 Query 向量方向夹角的余弦是 0.85"。
说话人1: 不同 Embedding 模型的分数分布完全不一样。BGE-M3 的正常余弦相似度可能在 0.3 到 0.8 之间，OpenAI 的可能在 0.7 到 0.9 之间。你不能跨模型比分数。
说话人1: 这就是为什么不能拿一个固定的 0.7 阈值套所有项目。每个模型、每个业务，分数分布都不一样。

说话人1: 问题八，相似度分数是 Embedding 模型直接输出的吗？还是向量数据库根据两个 Embedding 计算出来的？
说话人1: 答，是向量数据库算出来的，不是 Embedding 模型输出的。
说话人1: Embedding 模型只做一件事：输入文本，输出向量。它不负责比较两个向量的相似度。
说话人1: 相似度计算是在向量数据库里做的。pgvector 用 SQL 运算符 <=>、<#>、<-> 来算。Milvus 在检索的时候内部算。
说话人1: 这个区别很重要。因为换了向量数据库，同样的两个向量，算出来的相似度数值可能不一样。有的返回距离，有的返回相似度，有的方向相反。

说话人1: 问题九，为什么必须区分 Embedding 向量本身的数值与两个 Embedding 之间计算出的相似度分数？
说话人1: 答，因为它们是两个完全不同层面的东西。
说话人1: Embedding 向量本身：是模型输出的原始结果，比如 1024 个浮点数。它是一个点在向量空间里的坐标。
说话人1: 相似度分数：是两个点之间的某种距离或夹角的量化值。它是一个标量，一个数字。
说话人1: 你不能拿着一个向量的第 500 维的值 0.0345 说"相似度是 0.0345"。那是向量的一个维度，不是相似度。
说话人1: 在 Spring AI 里，Document.getEmbedding() 拿到的是向量本身，Document.getScore() 拿到的是相似度分数。两个完全不同的方法，别搞混了。

## 二、余弦相似度（Cosine Similarity）

说话人1: 问题十，什么是余弦相似度？它通过什么方式衡量两个向量的方向接近程度？
说话人1: 答，余弦相似度就是把两个向量当成从原点出发的箭头，算它们之间夹角的余弦值。
说话人1: 想象一下，向量 A 和向量 B 都是从原点伸出去的箭头。两个箭头完全重合，夹角是 0 度，余弦是 1。两个箭头垂直，夹角是 90 度，余弦是 0。两个箭头方向相反，夹角是 180 度，余弦是 -1。
说话人1: 它衡量的是"方向"，不是"长度"。两个箭头方向一样，不管一个长一个短，余弦都是 1。
说话人1: 为什么文本语义检索常用余弦？因为文本的长短不应该影响语义相似度。一篇长文档和一篇短文档，只要讲的是同一个意思，相似度就应该高。余弦只看方向，不看长度，正好符合这个需求。

说话人1: 问题十一，余弦相似度的数学公式是什么？分子和分母分别代表什么？
说话人1: 答，公式是：cos(A, B) = (A · B) / (||A|| × ||B||)
说话人1: 分子 A · B：两个向量的点积。对应位相乘再加起来。它衡量的是两个向量在方向上的乘积。
说话人1: 分母 ||A|| × ||B||：两个向量的模长相乘。就是每个向量先算自己的长度，再乘起来。
说话人1: 为什么要除以模长？因为要把"长度"的影响去掉，只保留"方向"。如果不除以模长，那向量越长，点积就越大，结果就被长度主导了。
说话人1: 代码里怎么算？Java 里用 nd4j 或者直接手写：double dot = 0, normA = 0, normB = 0; for (int i = 0; i < a.length; i++) { dot += a[i] * b[i]; normA += a[i] * a[i]; normB += b[i] * b[i]; } return dot / (Math.sqrt(normA) * Math.sqrt(normB));

说话人1: 问题十二，什么是向量点积？它与余弦相似度有什么关系？
说话人1: 答，点积就是两个向量对应位相乘再求和。公式：A · B = Σ(Ai × Bi)
说话人1: 点积和余弦的关系是：余弦相似度 = 点积 / (||A|| × ||B||)。
说话人1: 也就是说，点积是余弦的分子。余弦是把点积做了归一化之后的结果。
说话人1: 如果两个向量都已经归一化了（模长都是 1），那分母就是 1 × 1 = 1，余弦就等于点积。这就是为什么很多 Embedding 模型建议先归一化向量，这样检索的时候直接算点积就行，不用除以模长，性能更好。

说话人1: 问题十三，为什么余弦相似度主要关注向量方向，而不是单纯比较两个向量的长度？
说话人1: 答，因为长度在文本语义检索里没有意义。
说话人1: 一篇 500 字的 Chunk 和一篇 50 字的 Chunk，只要讲的是同一个故障，语义就应该接近。但如果用欧氏距离算，500 字的向量模长更大，距离就更远，好像不相似似的。这不对。
说话人1: 余弦把模长除掉了，只看方向。所以不管文本长短，只要语义方向一致，相似度就高。这正好符合我们对文本语义的直觉。

说话人1: 问题十四，余弦相似度的理论取值范围是什么？-1、0 和 1 分别代表什么？
说话人1: 答，理论取值范围是 [-1, 1]。
说话人1: 等于 1：两个向量方向完全一致。意思完全相同。
说话人1: 等于 0：两个向量垂直。没有任何语义关联。
说话人1: 等于 -1：两个向量方向完全相反。意思完全对立。
说话人1: 但在实际文本 Embedding 里，你很少看到负的余弦。因为大部分文本之间不会是完全对立的。一般都在 0 到 1 之间。
说话人1: 举个例子，"E101 故障维修"和"E101 报警含义"，余弦可能是 0.7。"E101 故障维修"和"办公室空调保养"，余弦可能是 0.1。

说话人1: 问题十五，当两个向量方向完全一致、正交和完全相反时，余弦相似度分别是多少？
说话人1: 答，方向完全一致：cos(0°) = 1。
说话人1: 正交（垂直）：cos(90°) = 0。
说话人1: 完全相反：cos(180°) = -1。
说话人1: 这个好记，就是三角函数里的余弦值。夹角越小，余弦越大。

说话人1: 问题十六，为什么两个向量的模长不同，但余弦相似度仍然可能等于 1？
说话人1: 答，因为余弦把模长除掉了。
说话人1: 比如向量 A = [2, 4]，向量 B = [1, 2]。B 是 A 的一半，模长不一样。但它们方向完全一样。
说话人1: 算一下：点积 = 2×1 + 4×2 = 2 + 8 = 10。||A|| = √(4+16) = √20 ≈ 4.47。||B|| = √(1+4) = √5 ≈ 2.24。cos = 10 / (4.47 × 2.24) = 10 / 10 = 1。
说话人1: 你看，模长差一倍，余弦还是 1。因为方向一样。
说话人1: 这在文本里是什么意思？就是说一段长文本和一段短文本，只要讲的是同一个意思，余弦相似度就是 1。

说话人1: 问题十七，为什么余弦相似度适合用于很多文本语义检索场景？
说话人1: 答，三个原因。
说话人1: 第一，它只看方向，不看长度。文本长短不影响语义判断。
说话人1: 第二，它的取值范围稳定在 [-1, 1]，好理解。
说话人1: 第三，大部分 Embedding 模型训练的时候，就是用余弦作为训练目标的。模型输出的向量天然适合用余弦来比较。
说话人1: 所以你看，OpenAI、Cohere、BGE、M3E，几乎所有主流 Embedding 模型都默认用余弦相似度。这是行业标准。

说话人1: 问题十八，余弦相似度与余弦距离有什么区别？
说话人1: 答，相似度是越大越相似，距离是越小越相似。方向相反。
说话人1: 余弦相似度：1 最相似，0 最不相关。
说话人1: 余弦距离：0 最相似，1 最不相关。
说话人1: 关系是：余弦距离 = 1 - 余弦相似度。
说话人1: 为什么要有距离这个概念？因为向量数据库做近似最近邻搜索的时候，一般都是按距离从小到大排。距离近的就是相似的。所以数据库返回距离，系统内部排序方便。

说话人1: 问题十九，为什么余弦距离通常通过 1 - Cosine Similarity 计算？
说话人1: 答，因为要把"越大越相似"转成"越小越相似"。
说话人1: 向量数据库做检索，习惯上都是"距离越小越近"。就像地图上两点之间，距离越近越近。
说话人1: 余弦相似度是 1 最像，0 最不像。反过来，余弦距离就是 0 最像，1 最不像。这样就符合"距离越小越近"的直觉了。
说话人1: 所以 pgvector 的 <=> 运算符返回的就是余弦距离，不是余弦相似度。你看到 pgvector 返回 0.15，意思是余弦距离 0.15，对应的余弦相似度是 0.85。别搞反了。

说话人1: 问题二十，如果两个向量的余弦相似度是 0.8，那么余弦距离是多少？这是否代表文本有 80% 的语义重合？
说话人1: 答，余弦距离 = 1 - 0.8 = 0.2。
说话人1: 但这绝不代表"文本有 80% 的语义重合"。
说话人1: 余弦相似度 0.8 只是说两个向量方向夹角的余弦是 0.8，夹角大概是 37 度。它不是百分比，不是重合度。
说话人1: 你不能把 0.8 理解成"80% 内容一样"。两篇文档可能只有一句话相似，其他完全不同，余弦也可能到 0.7。
说话人1: 这是最常见的误解。很多人看到余弦 0.8，就觉得"80% 相关"。不对。它只是个几何度量值，不是百分比。

## 三、内积与欧氏距离

说话人1: 问题二十一，什么是内积相似度？它如何衡量两个向量之间的关系？
说话人1: 答，内积就是点积。A · B = Σ(Ai × Bi)
说话人1: 内积大，说明两个向量在各个维度上的乘积加起来大。它同时受方向和长度影响。
说话人1: 如果两个向量方向相同，长度越大，点积越大。如果方向相反，点积就是负的。
说话人1: 内积在什么场景用？当向量已经归一化的时候，内积等于余弦，而且计算更快。所以很多高性能向量数据库，比如 Milvus，建议向量先归一化，然后用内积做度量，性能比余弦好。

说话人1: 问题二十二，为什么未经归一化的内积既受到向量方向影响，也受到向量模长影响？
说话人1: 答，因为点积公式里没有除以模长。
说话人1: 向量 A = [1, 2]，向量 B = [2, 4]。方向完全一样。点积 = 1×2 + 2×4 = 2 + 8 = 10。
说话人1: 现在把 B 放大一倍，变成 B' = [4, 8]。方向还是一样。点积 = 1×4 + 2×8 = 4 + 16 = 20。
说话人1: 方向没变，但点积翻了一倍。因为 B 变长了。
说话人1: 所以如果你不对向量做归一化，直接用内积检索，那长文本的向量天然点积大，会排在前面。这就不对了，因为长不一定相关。

说话人1: 问题二十三，什么是 L2 归一化？为什么要将向量长度调整为 1？
说话人1: 答，L2 归一化就是把向量的模长缩放到 1。
说话人1: 做法：每个维度的值，除以整个向量的模长。new_vector[i] = vector[i] / ||vector||
说话人1: 归一化之后，向量方向不变，只是长度变成 1。
说话人1: 为什么要归一化？三个好处。第一，消除长度差异的影响，让相似度只看方向。第二，归一化之后，内积等于余弦，计算更快。第三，很多向量索引（比如 HNSW）在归一化向量上性能更好。
说话人1: Embedding 模型返回的向量，有的已经归一化了，有的没有。BGE-M3 默认没归一化，要自己做。OpenAI 的 text-embedding-3 也没自动归一化。

说话人1: 问题二十四，当两个向量都经过 L2 归一化后，为什么内积等于余弦相似度？
说话人1: 答，因为余弦公式是 cos = (A · B) / (||A|| × ||B||)。
说话人1: 两个向量都归一化了，||A|| = 1，||B|| = 1。分母就是 1 × 1 = 1。
说话人1: 所以 cos = A · B。余弦等于点积。
说话人1: 这就是为什么很多系统先归一化向量，然后用内积做检索。因为计算快，效果和余弦一样。

说话人1: 问题二十五，使用内积进行向量检索时，什么情况下必须关注 Embedding 是否已经归一化？
说话人1: 答，只要你用内积作为距离度量，就必须确认向量是不是归一化了。
说话人1: 如果没归一化，内积会被模长影响，结果不准。长文本天然占优势。
说话人1: 在 pgvector 里，用 <#> 运算符就是内积。你要先确认你的 embedding 列是不是已经归一化了。
说话人1: 怎么确认？算一下向量的模长是不是 1。SELECT sqrt(sum(embedding[i] * embedding[i])) FROM ... 查一下。如果不是 1，要么入库前先归一化，要么就用余弦距离 <=>。

说话人1: 问题二十六，什么是欧氏距离？它与余弦距离的计算原理有什么不同？
说话人1: 答，欧氏距离就是两点之间的直线距离。公式：d = √(Σ(Ai - Bi)²)
说话人1: 它衡量的是两个向量在空间中的绝对距离。既看方向，也看长度。
说话人1: 余弦距离只看方向，不看长度。
说话人1: 举个例子。向量 A = [1, 0]，向量 B = [2, 0]。方向完全一样。余弦距离是 0，意思是完全相似。但欧氏距离是 1，意思是差了 1 个单位。
说话人1: 你看，方向一样，但长度不一样，欧氏距离就有值。这就是它们的区别。

说话人1: 问题二十七，为什么欧氏距离越小，两个向量通常越接近，而余弦相似度越大，两个向量通常越接近？
说话人1: 答，因为定义不同。
说话人1: 欧氏距离：两个点之间的直线长度。距离越小，两点越近。就像地图上两个点，距离 1 公里比 100 公里近。
说话人1: 余弦相似度：两个向量方向的夹角。夹角越小，余弦越大。cos(0°) = 1，cos(90°) = 0。
说话人1: 一个是距离，越小越好。一个是相似度，越大越好。方向相反，别搞混了。

说话人1: 问题二十八，两个向量已经归一化时，欧氏距离与余弦相似度之间存在什么数学关系？
说话人1: 答，归一化之后，欧氏距离和余弦相似度有固定关系。
说话人1: 推导一下：||A - B||² = ||A||² + ||B||² - 2A·B。归一化之后 ||A|| = ||B|| = 1。所以 ||A - B||² = 2 - 2A·B = 2(1 - A·B)。
说话人1: 而 A·B 等于余弦相似度（因为归一化了）。所以 ||A - B||² = 2(1 - cos)。欧氏距离的平方 = 2 × 余弦距离。
说话人1: 这意味着，归一化之后，用欧氏距离排序和用余弦距离排序，结果完全一样。只是数值差个常数倍。
说话人1: 所以很多向量数据库，只要向量归一化了，用哪个度量排序，TopK 结果都一样。

说话人1: 问题二十九，为什么同一批归一化向量使用余弦相似度和欧氏距离，可能得到完全一致的排序结果？
说话人1: 答，因为刚才推导了：欧氏距离的平方和余弦距离是线性关系。d² = 2 × (1 - cos)。
说话人1: d 大，就是 d² 大，就是 1 - cos 大，就是 cos 小。排序方向完全一致。
说话人1: 所以你归一化之后，用余弦排序，和用欧氏距离排序，排出来的 TopK 一模一样。只是分数数值不一样。
说话人1: 这就是为什么很多人说"归一化之后，三种度量排序结果一样"。是真的，数学上等价。

说话人1: 问题三十，为什么不同 Embedding 模型产生的向量，不应该直接混合使用同一个相似度比较结果？
说话人1: 答，因为每个模型的向量空间都不一样。
说话人1: BGE-M3 的 1024 维向量空间，和 OpenAI text-embedding-3-small 的 1536 维向量空间，完全是两个不同的坐标系。
说话人1: 就像北京的经纬度和纽约的经纬度，不能直接拿来比两点距离。
说话人1: 所以你不能把 BGE 编码的 Chunk 向量，和 OpenAI 编码的 Query 向量放在一起算相似度。结果完全没意义。
说话人1: 这就是为什么换 Embedding 模型的时候，整个知识库要重新向量化。旧向量和新向量不在一个空间。

## 四、不同距离度量的分数方向与数值含义

说话人1: 问题三十一，Cosine Similarity、Cosine Distance、Inner Product 和 L2 Distance 分别属于相似度还是距离度量？
说话人1: 答，分两类。
说话人1: 相似度（越大越像）：Cosine Similarity、Inner Product。
说话人1: 距离（越小越像）：Cosine Distance、L2 Distance。
说话人1: 这个分类很重要。你看到一个数字，先搞清楚它是相似度还是距离，方向别搞反了。

说话人1: 问题三十二，为什么不同向量数据库可能将相似度和距离以不同字段、不同方向返回？
说话人1: 答，因为各家设计习惯不一样。
说话人1: 有的数据库返回距离，因为检索就是按距离排的。有的返回相似度，因为用户直觉上觉得"分高就是好"。
说话人1: 所以你换一个数据库，第一件事就是搞清楚：它返回的这个 score，是越大越相似，还是越小越相似？取值范围是多少？
说话人1: 别上来就写个 threshold = 0.7。可能方向都搞反了。

说话人1: 问题三十三，为什么余弦相似度和内积通常是数值越大越相似，而欧氏距离和余弦距离通常是数值越小越相似？
说话人1: 答，因为定义不同。
说话人1: 相似度：衡量"有多像"。越像数值越大。1 就是完全像。
说话人1: 距离：衡量"有多远"。越远数值越大。0 就是完全重合。
说话人1: 一个是正向指标，一个是反向指标。方向相反。

说话人1: 问题三十四，为什么不能看到数据库返回一个数值，就直接假定它是 0 到 1 之间的相似度分数？
说话人1: 答，因为不同数据库返回的数值范围不一样。
说话人1: pgvector 的余弦距离 <=>：取值 [0, 2]。0 最相似，1 正交。
说话人1: Milvus 的 COSINE：有的版本返回距离，有的返回相似度。
说话人1: FAISS 的 L2：是平方欧氏距离，没有上限。
说话人1: 你看到一个 0.85，你以为是余弦相似度。结果它是 L2 距离。那方向完全反了。
说话人1: 所以第一步永远是看文档，确认这个 score 是什么意思。

说话人1: 问题三十五，pgvector 的 <=>、<#> 和 <-> 分别代表什么操作？
说话人1: 答，pgvector 三个运算符：
说话人1: <=>：余弦距离（Cosine Distance）。取值 [0, 2]。越小越相似。
说话人1: <#>：负内积（Negative Inner Product）。返回的是 -A·B。越小越相似（因为负的越多，内积越大）。
说话人1: <->：L2 距离（欧氏距离）。越小越相似。
说话人1: 为什么 <#> 返回负内积？因为 pgvector 内部排序是"越小越靠前"。内积越大越相似，所以返回 -内积，这样大的内积就变成小的负数，排在前面。

说话人1: 问题三十六，为什么 pgvector 的 <=> 返回的是余弦距离，而不是余弦相似度？
说话人1: 答，因为 pgvector 是为向量检索设计的。检索的时候，按距离从小到大排。距离近的就是相似的。
说话人1: 如果返回余弦相似度，那就是越大越靠前。数据库内部排序逻辑要反过来。设计上不方便。
说话人1: 所以 pgvector 统一返回距离。用户拿到距离，自己换算成相似度也行。
说话人1: 记住：<=> 返回的是距离。cosine_similarity = 1 - (<=> 的结果)。

说话人1: 问题三十七，为什么 pgvector 的 <#> 返回负内积？如果需要得到正向内积，应该如何转换？
说话人1: 答，因为 pgvector 排序习惯是"越小越靠前"。内积越大越相似，所以返回 -内积，这样大的内积就变成小的负数，排在前面。
说话人1: 比如 A·B = 10，pgvector 返回 -10。A·B = 5，返回 -5。-10 < -5，所以内积 10 的排在前面。
说话人1: 要得到正向内积，就取负号。inner_product = -(embedding <#> query_vector)。

说话人1: 问题三十八，如何使用 SQL 将 pgvector 的余弦距离转换为余弦相似度？
说话人1: 答，直接用 1 减。
说话人1: SELECT content, 1 - (embedding <=> '[0.1, 0.2, ...]') AS cosine_similarity FROM chunk_table ORDER BY embedding <=> '[0.1, 0.2, ...]' LIMIT 5;
说话人1: 这样查出来的 cosine_similarity 就是 0 到 1 之间的数，越大越相似。
说话人1: Spring AI 的 PgVectorStore 内部已经做了这个转换，Document.getScore() 返回的就是余弦相似度。你不用自己算。

说话人1: 问题三十九，Milvus 的 COSINE、IP 和 L2 分别如何解释结果数值的大小方向？
说话人1: 答，Milvus 的度量：
说话人1: COSINE：返回的是距离。0 最相似，1 最不相关。
说话人1: IP（内积）：返回的是相似度。越大越相似。
说话人1: L2：返回的是距离。0 最相似，越大越远。
说话人1: 注意 Milvus 的 COSINE 返回的是距离，不是相似度。这个和 pgvector 一样。但 IP 是相似度，方向不一样。别搞混了。

说话人1: 问题四十，为什么 Milvus 的 L2 度量与部分其他工具返回的欧氏距离数值可能不同？平方欧氏距离有什么含义？
说话人1: 答，因为有的数据库返回的是平方欧氏距离（Squared L2），有的返回的是开根号后的欧氏距离。
说话人1: 平方欧氏距离就是 d² = Σ(Ai - Bi)²。不用开根号。计算更快。
说话人1: 排序结果和欧氏距离一样，因为平方是单调函数。但数值不一样。
说话人1: 所以你看到 Milvus 返回 L2 距离是 4.5，pgvector 返回是 2.1，可能差一倍。因为一个是平方距离，一个是开根号的。别奇怪。

说话人1: 问题四十一，为什么 FAISS、pgvector 和 Milvus 使用不同的度量接口时，必须先确认各自返回的是距离还是相似度？
说话人1: 答，因为各家设计不一样。你以为是相似度，结果是距离。方向搞反了，整个检索就错了。
说话人1: 比如你以为 score 越大越好，设了个阈值 0.7。结果数据库返回的是距离，0.7 已经是很远的了。你过滤完之后，把最相关的都过滤掉了。
说话人1: 这是生产事故级别的坑。换数据库之前，先写个测试，拿两个已知相似的向量，看返回的 score 是多少，方向对不对。

说话人1: 问题四十二，如果三个数据库对同一组向量分别返回 0.85、0.15 和 -0.85，应该如何判断它们是否表达相同的检索结果？
说话人1: 答，先搞清楚每个数据库返回的是什么。
说话人1: 第一个 0.85：如果是余弦相似度，0.85 很高，很相似。
说话人1: 第二个 0.15：如果是余弦距离，1 - 0.15 = 0.85，也是很高的相似度。
说话人1: 第三个 -0.85：如果是负内积，那真实内积是 0.85。也是很高的相似度。
说话人1: 三个数值不一样，但表达的是同一个意思：非常相似。
说话人1: 这就是为什么不能只看数字大小。先搞清楚这个数字是什么度量、什么方向。

## 五、分数与 Embedding 模型的关系

说话人1: 问题四十三，为什么更换 Embedding 模型后，即使使用相同的 Query 和 Chunk，得到的相似度分数也可能发生明显变化？
说话人1: 答，因为每个模型的向量空间都不一样。
说话人1: BGE-M3 和 OpenAI text-embedding-3-small，虽然都能把文本转成向量，但它们训练的时候用的数据不一样，模型结构不一样，向量空间不一样。
说话人1: 同样两段文本，在 BGE 空间里余弦可能是 0.7，在 OpenAI 空间里可能是 0.85。分数分布完全不同。
说话人1: 所以你换了 Embedding 模型，之前校准的阈值就没用了。要重新校准。

说话人1: 问题四十四，为什么相同模型、相同维度和相同距离度量，是比较两组向量结果的重要前提？
说话人1: 答，因为分数只有在同一个空间里才有意义。
说话人1: 同一个模型：向量空间一样。
说话人1: 同一个维度：向量长度一样。
说话人1: 同一个距离度量：算法一样。
说话人1: 满足这三个条件，你才能说"这个 0.85 比那个 0.8 更相似"。不然没法比。

说话人1: 问题四十五，什么是查询向量与文档向量的非对称编码？它会如何影响相似度计算？
说话人1: 答，非对称编码就是：Query 和 Document 用不同的方式编码。
说话人1: 比如 BGE 模型，对 Query 会加一个指令前缀："为这个句子生成表示以用于检索相关文章："。对 Document 就直接编码，不加前缀。
说话人1: 为什么要这样？因为训练的时候就是这么训的。Query 和 Document 的角色不一样。这样做能提高检索准确率。
说话人1: 但如果你 Query 也加了 Document 的前缀，或者 Document 加了 Query 的前缀，相似度就不对了。
说话人1: 所以用 BGE 的时候，Query 和 Document 的编码方式要按模型要求来。别搞反了。

说话人1: 问题四十六，为什么有些 Embedding 模型对 Query 和 Document 使用不同的指令或编码方式？
说话人1: 答，因为检索任务是不对称的。
说话人1: 用户 Query 是短的、问题式的。文档 Chunk 是长的、陈述式的。两者角色不一样。
说话人1: 模型训练的时候，对 Query 和 Document 用不同的处理方式，能让向量更适合检索。比如 M3E、BGE、E5，都是非对称模型。
说话人1: 你要查模型文档，看它是不是非对称的。如果是，Query 和 Document 要分别按要求编码。

说话人1: 问题四十七，为什么向量维度相同，不代表不同 Embedding 模型产生的向量处于同一个语义空间？
说话人1: 答，维度只是向量的长度。空间是模型训练出来的。
说话人1: 两个模型都输出 1024 维向量，不代表第 1 维代表同一个意思。
说话人1: 就像两个城市都有经纬度，都是 3 个数。但北京的经纬度和纽约的经纬度，坐标系不一样。不能直接比两点距离。
说话人1: 所以维度一样，不代表空间一样。

说话人1: 问题四十八，为什么不能把模型 A 的 0.85 分数直接与模型 B 的 0.85 分数进行质量比较？
说话人1: 答，因为分数分布不一样。
说话人1: 模型 A 的 0.85，可能已经是非常高的相似度了。模型 B 的 0.85，可能只是中等水平。
说话人1: 就像考试，60 分及格，有的学校 90 分才算优秀。分数不能跨学校比。
说话人1: 你要比较两个模型的检索质量，不能看绝对分数，要看召回率、精确率这些指标。

说话人1: 问题四十九，Embedding 模型升级后，为什么旧向量和新向量可能不再适合直接混合检索？
说话人1: 答，因为模型版本变了，向量空间就变了。
说话人1: BGE-M3 v1.5 和 v1.6，虽然都是 1024 维，但向量空间有细微差别。
说话人1: 你把旧版本的 Chunk 向量，和新版本的 Query 向量放在一起算相似度，结果不准。
说话人1: 所以模型升级，要么全量重建向量，要么新旧版本分开存，不要混。

说话人1: 问题五十，在设备故障知识库中，"E001 故障代码""电机无法启动"和"电机启动异常"可能得到不同分数，应该如何理解它们之间的语义关系？
说话人1: 答，"电机无法启动"和"电机启动异常"，意思很接近，余弦相似度很高，可能 0.85 以上。因为语义几乎一样。
说话人1: "E001 故障代码"和"电机无法启动"，相似度可能中等，比如 0.6。因为 E001 可能就是电机无法启动的代码，但字面不一样，语义有差距。
说话人1: 这就是向量检索的好处：它能理解"无法启动"和"启动异常"是一个意思。关键词检索就不行，因为字面不一样。
说话人1: 但也要注意，语义接近不代表业务相关。E001 可能是电机故障，也可能是别的。要结合 Metadata 过滤，限定设备型号。

## 六、RAG 检索中的分数与阈值

说话人1: 问题五十一，什么是 TopK 检索？为什么 TopK 只保证返回排序靠前的结果，不保证结果一定相关？
说话人1: 答，TopK 就是按相似度排序，取前 K 个。
说话人1: 它只保证"这 K 个是所有 Chunk 里最相似的"。不保证"这 K 个一定相关"。
说话人1: 因为如果整个知识库都跟用户问题不相关，那 Top5 也都是不相关的。只是相对来说，它们是最不那么不相关的。
说话人1: 这就是为什么光设 TopK 不够，还要加相似度阈值。

说话人1: 问题五十二，当数据库返回 TopK 文档时，为什么即使所有文档相似度都很低，也可能仍然返回结果？
说话人1: 答，因为 TopK 只按排序取前 K 个，不管分数多低。
说话人1: 比如用户问"今天天气怎么样"，知识库是设备手册。所有 Chunk 的余弦可能都在 0.2 以下。但 TopK = 5，还是会返回 5 个最接近的。虽然都不相关。
说话人1: 这就是为什么要加阈值。分数太低的，直接不要，告诉用户"没找到相关信息"。

说话人1: 问题五十三，什么是相似度阈值？它与 TopK 有什么区别？
说话人1: 答，TopK：按数量取，取前 K 个。不管分数多低。
说话人1: 相似度阈值：按分数取，超过阈值的才要。不管数量多少。
说话人1: 两个是互补的。实际用的时候，一般两个一起用：先按阈值过滤，再取 TopK。或者先取 TopK，再按阈值过滤掉低的。
说话人1: Spring AI 的 SearchRequest，既可以设 topK，也可以设 similarityThreshold。两个都配。

说话人1: 问题五十四，为什么设置阈值可以过滤低相关性候选文档，却不能直接保证剩余文档一定包含正确答案？
说话人1: 答，因为阈值只是过滤掉最不相关的。剩下的可能还是不对。
说话人1: 比如阈值设 0.5。剩下的都在 0.5 以上。但 0.6 的文档可能讲的是另一个故障，不是用户要的。
说话人1: 阈值只能保证"这些文档语义上有一定相关度"，不能保证"一定是正确答案"。

说话人1: 问题五十五，阈值设置过高会产生什么问题？为什么可能造成召回率下降和有效知识遗漏？
说话人1: 答，阈值太高，就是很多相关的文档分数没那么高，被过滤掉了。
说话人1: 比如阈值设 0.9。但 Embedding 模型对某些故障的表达能力一般，正确的 Chunk 可能只有 0.7。结果被过滤了。召回率下降。
说话人1: 用户问 E001 怎么处理，正确的维修步骤分数只有 0.65，被阈值 0.7 过滤掉了。系统返回"没找到相关信息"。但其实知识库里有，只是分数没那么高。

说话人1: 问题五十六，阈值设置过低会产生什么问题？为什么可能引入无关 Chunk 和上下文噪声？
说话人1: 答，阈值太低，就是很多不相关的文档也进来了。
说话人1: 比如阈值设 0.3。那所有跟 Query 有点像的 Chunk 都进来了。上下文里混了很多无关内容。
说话人1: LLM 被无关内容干扰，可能答非所问。幻觉增多。Token 消耗也大。
说话人1: 就像你去图书馆找书，门槛设得太低，什么书都让你拿。结果抱了一堆回来，有用的没几本。

说话人1: 问题五十七，为什么不能直接将 0.7、0.8 或 0.9 当成所有 RAG 项目的通用阈值？
说话人1: 答，因为每个模型、每个业务，分数分布都不一样。
说话人1: BGE-M3 的正常余弦相似度，相关的可能在 0.5 到 0.8 之间。OpenAI 的可能在 0.7 到 0.9 之间。
说话人1: 你拿 0.7 当阈值，用 BGE 的话，可能把一半相关的都过滤了。用 OpenAI 的话，又可能放进太多不相关的。
说话人1: 阈值必须针对你的模型、你的业务数据，自己校准。没有通用值。

说话人1: 问题五十八，相似度分数与阈值之间应该如何建立关系？为什么需要结合真实业务数据进行阈值校准？
说话人1: 答，校准方法：
说话人1: 第一步，建一批测试问题，人工标注好正确的 Chunk。
说话人1: 第二步，跑检索，看每个测试问题的 Top1 分数是多少。正确 Chunk 的分数分布是什么样的。
说话人1: 第三步，画个分数分布直方图。正确答案的分数集中在哪个区间，错误答案的集中在哪个区间。
说话人1: 第四步，找一个平衡点。既能把大部分正确答案放进来，又能把大部分错误答案挡在外面。
说话人1: 这就是阈值校准。不是拍脑袋定的，是从真实数据里算出来的。

说话人1: 问题五十九，如果某个 Query 的 Top1 分数是 0.82，Top2 是 0.81，而另一个 Query 的 Top1 是 0.82，Top2 是 0.55，这两组检索结果有什么不同？
说话人1: 答，第一组：Top1 和 Top2 分数很接近，0.82 vs 0.81。说明这两个 Chunk 都跟 Query 很相关，模型分不清哪个更好。可能两个都是对的，或者两个都差不多。
说话人1: 第二组：Top1 是 0.82，Top2 直接掉到 0.55。说明第一个 Chunk 明显比其他的更相关。检索结果很确定。
说话人1: 这就是分数差距的意义。差距大，说明检索结果很明确。差距小，说明有多个候选，可能需要 Rerank 来精排。

说话人1: 问题六十，什么是分数分布？如何通过 Top1 分数、TopK 分数、均值和分数差距分析检索质量？
说话人1: 答，分数分布就是所有检索结果的分数分布情况。
说话人1: 看几个指标：
说话人1: Top1 平均分：平均下来，最相关的 Chunk 分数有多高。越高越好。
说话人1: Top1 和 Top2 的分差：差距大，说明检索结果很明确。差距小，说明有多个候选。
说话人1: TopK 的分数均值：平均相关性。
说话人1: 分数方差：方差大，说明有的高有的低。方差小，说明都差不多。
说话人1: 这些指标可以帮你判断：检索是不是稳定？有没有经常召不回正确答案？

## 七、分数的工程应用与评估

说话人1: 问题六十一，为什么相似度分数高，不代表 Chunk 中的内容一定能回答用户问题？
说话人1: 答，因为相似度是语义接近，不是答案匹配。
说话人1: 用户问"E001 怎么修"。检索到一篇讲"E001 是什么含义"的文档，相似度 0.8。但这篇只讲含义，不讲维修步骤。
说话人1: 语义上很接近（都提到 E001），但业务上不是用户要的。
说话人1: 这就是为什么还要加 Rerank。Rerank 是判断"这段文档能不能回答这个问题"，比向量相似度更准。

说话人1: 问题六十二，为什么设备型号、故障编码、零件编号等精确条件不能只依赖向量相似度？
说话人1: 答，因为向量是语义相似度，不是精确匹配。
说话人1: E101 和 E102，向量可能很像，因为都是故障代码。但它们是完全不同的故障。
说话人1: 你不能靠向量相似度来区分 E101 和 E102。必须用关键词检索，或者 Metadata Filter。
说话人1: 这就是混合检索的意义。向量负责语义，关键词负责精确匹配。

说话人1: 问题六十三，什么是 Metadata Filter？为什么应该先通过设备型号、文档版本和知识状态缩小检索范围？
说话人1: 答，Metadata Filter 就是按元数据过滤。比如只查"设备型号=A001"的 Chunk。
说话人1: 为什么要先过滤？因为如果不过滤，检索范围是整个知识库。里面有很多其他设备的文档，会干扰结果。
说话人1: 先按设备型号、文档版本、审核状态过滤，缩小范围。然后再在这个小范围里做向量相似度检索。这样结果更准。
说话人1: pgvector 里就是 WHERE 条件加在 SQL 里。SELECT ... WHERE device_model = 'A001' AND status = 'approved' ORDER BY embedding <=> query LIMIT 5。

说话人1: 问题六十四，什么是混合检索？BM25 分数与向量相似度为什么不能不加处理地直接比较？
说话人1: 答，混合检索就是关键词检索（BM25）加向量检索，两个一起用。
说话人1: 为什么不能直接比分数？因为 BM25 分数和余弦相似度，完全不是一个尺度。BM25 可能是 12.5，余弦是 0.8。你没法直接加起来比。
说话人1: 怎么融合？用 RRF（Reciprocal Rank Fusion）。不看分数，看排名。两个检索结果按排名融合。
说话人1: 这样就不用管分数尺度了。

说话人1: 问题六十五，什么是 Rerank？为什么重排序模型的相关性分数与 Embedding 相似度分数不是同一种指标？
说话人1: 答，Rerank 就是对召回的候选重新精排。
说话人1: Embedding 相似度：是 Bi-Encoder 算的，两个向量分开编码，粗粒度。
说话人1: Rerank 分数：是 Cross-Encoder 算的，Query 和文档放在一起过模型，细粒度。
说话人1: 两个分数完全不是一回事。Rerank 分数更准，但更慢。
说话人1: 你不能把 Rerank 分数和 Embedding 相似度放在一起比大小。它们是不同模型输出的。

说话人1: 问题六十六，如何通过 Recall@K、Precision@K、MRR 和 NDCG 评估相似度排序是否真正有效？
说话人1: 答，这四个是标准的检索评估指标。
说话人1: Recall@K：前 K 个结果里，召回了多少正确的。召回率。
说话人1: Precision@K：前 K 个结果里，有多少是正确的。精确率。
说话人1: MRR：第一个正确结果排第几。排越靠前越好。
说话人1: NDCG：考虑排序位置的综合分数。越相关的排越前面，分数越高。
说话人1: 这些指标比看绝对分数靠谱多了。因为它们是从结果好不好的角度评的，不是看分数高低。

说话人1: 问题六十七，如何设计真实问题与相关 Chunk 的标注数据集，对不同相似度阈值进行对照实验？
说话人1: 答，步骤：
说话人1: 第一步，收集一批真实用户问题。比如 100 个常见故障问题。
说话人1: 第二步，人工标注每个问题对应的正确 Chunk 是哪个。
说话人1: 第三步，跑检索，用不同的阈值（0.3、0.5、0.7、0.9），看召回率和精确率。
说话人1: 第四步，画曲线。召回率-精确率曲线。找一个平衡点。
说话人1: 这样选出来的阈值，才是适合你这个项目的。

说话人1: 问题六十八，Spring AI 1.1.8 中的 Document.getScore() 和 SearchRequest.similarityThreshold() 分别有什么作用？使用 pgvector 时应该如何结合实际距离类型理解它们？
说话人1: 答，Document.getScore()：检索返回的每个 Chunk 的相似度分数。Spring AI 内部已经做了转换，返回的是 0 到 1 之间的相似度。越大越相似。
说话人1: SearchRequest.similarityThreshold()：设置相似度阈值。低于这个分数的结果会被过滤掉。
说话人1: 用 pgvector 的时候，PgVectorStore 内部会把余弦距离转成相似度。1 - distance = similarity。所以你看到的 score 已经是相似度了，不用自己转。
说话人1: 但如果你直接写 SQL 查 pgvector，那 <=> 返回的是距离，方向相反。别搞混了。

说话人1: 问题六十九，如何在 Java 项目中记录 Query、TopK、相似度分数、距离度量、过滤条件和最终入选 Chunk，方便定位检索错误？
说话人1: 答，每次检索都记日志。
说话人1: 日志字段：query、embedding_model、distance_metric、topK、threshold、filter_conditions、返回的每个 chunk 的 id 和 score。
说话人1: 这样出问题的时候，比如"用户说检索不到 E001 的维修步骤"，你去查日志。看 Query 是什么，Top1 分数是多少，返回了哪些 Chunk。一眼就能定位是阈值太高，还是 Embedding 不准，还是 Chunk 切分有问题。

说话人1: 问题七十，在制造设备故障知识库中，如何建立一套从向量相似度计算、分数解释、阈值校准、混合检索到 RAG 答案评估的完整机制？
说话人1: 答，完整机制分几层。
说话人1: 第一层：向量计算。统一用一个 Embedding 模型，向量归一化。pgvector 用余弦距离。
说话人1: 第二层：分数解释。团队统一认知：分数是相似度，越大越相关。不是百分比。不同模型分数分布不一样。
说话人1: 第三层：阈值校准。建测试集，跑对照实验，找最优阈值。不是拍脑袋定的。
说话人1: 第四层：混合检索。向量 + BM25，RRF 融合。Metadata Filter 先过滤设备型号和版本。
说话人1: 第五层：Rerank。召回 Top20，Rerank 精排，取 Top5。
说话人1: 第六层：答案评估。用 RAGAS 这些工具，定期评估召回率、忠实度、答案准确率。
说话人1: 这样从向量计算到最终答案，全链路都有质量管控。相似度分数只是其中一环。
