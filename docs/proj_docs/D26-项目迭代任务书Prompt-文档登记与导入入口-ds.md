## 三、本次功能需求

### 1. 知识文档登记与导入入口

基于现有 KnowledgeDocument Schema 实现，不另起字段体系，不重复设计已有数据模型。

需要保留以下核心信息：

| 字段       | 说明         |
| ---------- | ------------ |
| documentId | 文档唯一标识 |
| source     | 文档来源     |
| title      | 文档标题     |
| version    | 文档版本     |
| status     | 文档处理状态 |
| updatedAt  | 文档更新时间 |

要求：

- 实现知识文档登记入口。
- 实现文件导入入口。
- 文档登记与文件导入职责分离。
- 复用已有实体、DTO、Repository、Service 和异常处理规范。
- 明确 documentId 的生成与使用规则。
- 明确文档元数据与文件内容的关联关系。
- 更新时间必须在对应业务状态变更时正确维护。
- 避免 Controller 承担业务逻辑。

### 2. 文档状态流转

实现以下基础状态：

`PENDING → PROCESSING → COMPLETED / FAILED`

要求：

- PENDING：文档已登记，等待处理。
- PROCESSING：文档正在执行导入与基础解析。
- COMPLETED：本轮导入与基础解析成功。
- FAILED：导入或解析失败。

明确状态变更的触发时机。

异常发生时正确记录 FAILED 状态及必要的失败信息，避免文档长期停留在 PROCESSING。

状态更新必须考虑异常情况下的数据一致性，不允许通过吞掉异常伪造成功状态。

### 3. 文件上传安全校验

必须在服务端执行文件校验，不能依赖前端限制。

至少覆盖：

- 空文件、零字节文件。
- 超过服务端配置大小限制的文件。
- 不支持的文件类型。
- 非法编码或无法正确解码的文件。
- 文件读取异常。
- 基础解析失败。

要求：

- 文件大小限制采用服务端配置，不在业务代码中随意硬编码。
- 检查 Spring Boot、Multipart 配置及实际业务校验之间的关系。
- 明确校验发生的执行位置。
- 明确异常类型及返回结果。
- 不得仅通过文件扩展名判断文件内容是否合法。
- 不得因为前端已经校验就省略后端校验。

### 4. 重复导入处理

基于文件内容计算 contentHash，识别相同内容的重复导入。

要求：

- 检查现有 Schema 是否已有 contentHash。
- 优先复用已有字段和约束。
- 明确重复导入的业务策略。
- 防止相同内容重复进入处理流程。
- 考虑并发情况下的重复导入问题。
- 必要时使用数据库唯一约束保证数据一致性。
- 明确重复导入时原文档状态、版本及更新时间的处理方式。

不得仅通过文件名判断重复文件。

如果现有数据模型无法支持某项能力，先说明原因和最小必要调整，再实施。
