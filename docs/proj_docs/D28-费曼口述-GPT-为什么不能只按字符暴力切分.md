# 费曼口述：为什么不能只按字符暴力切分

说话人1: 费曼口述，主题，70 道关键问题，由浅入深分为七个阶段。技术基线是 Java 21、Spring Boot 3.5.x、Spring AI 1.1.8，以生产级 RAG 文档处理与知识库构建为背景。核心逻辑是理解文本分块的目的，分析字符暴力切分造成的语义断裂，掌握语义边界、递归切分、Chunk Size、Overlap 和 Token 限制，并结合 Spring AI 1.1.8 的 `TokenTextSplitter` 设计可测试、可评估的 Java 工程方案。最终要能够解释：为什么 Chunk 不能只追求长度合规，还必须保证内容完整、上下文可恢复和检索结果有效。

## 一、文本切分的基本认知

### 1. 什么是文本分块（Chunking）？为什么 RAG 需要将长文档切分成多个 Chunk？

说话人1: 问题一，什么是文本分块？为什么 RAG 需要将长文档切分成多个 Chunk？

说话人1: 答，Chunking 就是把一份较长的文档拆成多个相对独立的小文本片段，每个片段就是一个 Chunk。

RAG 通常不会把整本手册直接交给 Embedding 模型和大语言模型，因为文档可能很长，超过模型输入限制，而且整本书作为一个向量也不利于精准检索。

所以我们先把文档拆成多个 Chunk，分别生成向量并保存。

用户提问时，只检索相关的几个 Chunk，再把它们交给大模型生成答案。

因此，切分的目标不是简单地把文档变短，而是让每个 Chunk 尽可能表达一个完整、可检索的知识单元。

### 2. 什么是固定长度切分？它与按段落、按标题和语义切分有什么区别？

说话人1: 问题二，什么是固定长度切分？它与按段落、按标题和语义切分有什么区别？

说话人1: 答，固定长度切分就是按照预先设定的长度，把文本拆成多个片段。

例如每 500 个字符切一次，不考虑句子是否结束，也不考虑段落是否完整。

按段落切分，是尽量以自然段作为边界。

按标题切分，是根据文档章节结构组织内容。

语义切分，则是根据文本之间的语义关联程度决定是否拆分。

它们的区别在于：固定长度主要关注长度，其他策略更加关注文本本身的结构和含义。

### 3. 为什么字符数量不等于 Token 数量？

说话人1: 问题三，为什么字符数量不等于 Token 数量？

说话人1: 答，因为字符和 Token 是两个不同的计量单位。

字符是文本中可见的文字、数字、符号等内容，而 Token 是模型分词器处理文本后得到的基本单位。

一个字符可能对应一个或多个 Token，多个字符也可能合并成一个 Token。

具体如何切分，取决于模型使用的 Tokenizer。

所以不能简单认为 1000 个字符就等于 1000 个 Token，也不能用一个固定比例准确换算所有文本。

### 4. 中文、英文、数字、代码和表格在 Token 数量上有什么差异？

说话人1: 问题四，中文、英文、数字、代码和表格在 Token 数量上有什么差异？

说话人1: 答，不同类型的文本经过 Tokenizer 处理后，Token 数量可能差异很大。

中文通常会按照模型词表中的字词组合进行切分。

英文常常可以把常见单词切成一个或几个 Token，生僻词可能拆成更多部分。

数字也不一定是一个 Token，例如较长的设备编号可能被拆成多个 Token。

Java 代码包含变量名、关键字、括号、运算符和标点，也可能产生比较多的 Token。

Markdown 表格除了实际内容，还包含竖线、横线和分隔符。

所以 Chunk Size 如果按照字符数计算，不能保证不同类型的文本都符合模型的 Token 限制。

### 5. 为什么相同字符长度的两段文本，实际 Token 数量可能不同？

说话人1: 问题五，为什么相同字符长度的两段文本，实际 Token 数量可能不同？

说话人1: 答，因为 Tokenizer 不会简单地按照字符数量平均切分。

例如，一段文本可能主要由常见英文单词组成，另一段文本可能包含设备型号、数字、特殊符号和 Java 代码。

虽然两段文本字符数量相同，但它们对应的 Token 序列可能完全不同。

所以生产环境应该使用与目标模型兼容的 Tokenizer 或实际 Token 统计方式，而不是仅凭字符数量估算模型输入长度。

### 6. 什么是 Chunk Size？它应该按照字符数、Token 数还是其他指标定义？

说话人1: 问题六，什么是 Chunk Size？它应该按照字符数、Token 数还是其他指标定义？

说话人1: 答，Chunk Size 就是每个 Chunk 的目标长度或者最大长度。

对于 RAG，通常更推荐使用 Token 数作为主要长度指标，因为 Embedding 模型和大语言模型最终受到 Token 输入限制。

但这不意味着只看 Token 数。

还要考虑句子、段落、标题、表格和代码块等结构边界。

所以更合理的设计是：以 Token 数控制长度，以语义和文档结构决定切分位置。

### 7. 什么是 Chunk Overlap？它主要解决什么问题？

说话人1: 问题七，什么是 Chunk Overlap？它主要解决什么问题？

说话人1: 答，Chunk Overlap 就是相邻两个 Chunk 之间保留一部分重复内容。

例如第一个 Chunk 的结尾有一段内容，第二个 Chunk 的开头也保留这段内容。

它主要解决切分边界处的上下文丢失问题。

因为一个完整的知识点可能刚好跨越两个 Chunk，如果完全没有重叠，单独检索其中一个片段时，可能缺少必要的前后文。

但是 Overlap 也不能无限增加，否则会造成大量重复内容。

### 8. 为什么文本切分不仅是长度控制问题，也是语义完整性问题？

说话人1: 问题八，为什么文本切分不仅是长度控制问题，也是语义完整性问题？

说话人1: 答，因为 RAG 最终需要检索的是知识，而不是任意长度的字符串。

假设原文是：设备温度超过 90 摄氏度时，应立即停止运行。

如果切分后一个 Chunk 只有“设备温度超过 90 摄氏度”，另一个 Chunk 只有“应立即停止运行”，两个片段单独检索时都可能缺少完整含义。

所以切分时既要控制长度，也要尽可能保留条件、结论、原因和处理步骤之间的关系。

### 9. 文档解析质量、文本清洗质量与 Chunk 质量之间有什么关系？

说话人1: 问题九，文档解析质量、文本清洗质量与 Chunk 质量之间有什么关系？

说话人1: 答，它们是前后依赖关系。

首先，文档解析负责从 PDF、Word、HTML 等文件中提取文本和结构。

然后，文本清洗负责去除页眉页脚、乱码、重复内容和无意义字符。

最后，Chunking 根据清洗后的内容进行分块。

如果 PDF 解析时已经丢失标题、表格或页码，后面的切分器就很难恢复原始结构。

所以 Chunk 质量不只是切分算法决定的，还受到上游解析和清洗质量的影响。

### 10. 为什么不能认为 Chunk 越小，检索效果就一定越好？

说话人1: 问题十，为什么不能认为 Chunk 越小，检索效果就一定越好？

说话人1: 答，因为 Chunk 太小，虽然每个片段的内容更加集中，但可能丢失必要的上下文。

例如，一个 Chunk 只包含故障代码 E102，却没有设备型号、故障原因和处理步骤。

检索系统可能找到了故障代码，但无法提供完整答案。

而且 Chunk 越小，文档数量和向量数量通常越多，检索和存储成本也会增加。

所以 Chunk 不是越小越好，而是要在语义完整性、检索精度和工程成本之间找到平衡。

## 二、字符暴力切分的主要问题

### 11. 什么是字符暴力切分？它通常采用什么实现方式？

说话人1: 问题十一，什么是字符暴力切分？它通常采用什么实现方式？

说话人1: 答，字符暴力切分就是不考虑文本的句子、段落和章节结构，直接按照固定字符数量切分。

例如 Java 中每 500 个字符截取一次：

```
for (int start = 0; start < text.length(); start += 500) {
    int end = Math.min(start + 500, text.length());
    String chunk = text.substring(start, end);
}
```

这种方式实现简单，执行速度也比较快。

但它只知道字符串的位置，不知道文本表达的含义，所以容易把一个完整知识点拆开。

### 12. 如果直接使用 Java `substring()` 按固定字符数切分，会产生哪些问题？

说话人1: 问题十二，如果直接使用 Java `substring()` 按固定字符数切分，会产生哪些问题？

说话人1: 答，首先，它可能把句子、段落、标题和代码块从中间截断。

其次，它不知道设备型号、故障代码和维修步骤之间的关联，可能把一个业务知识点拆散。

还有一个 Java 层面的细节：`String.length()` 和 `substring()` 使用的是 UTF-16 代码单元索引，不完全等于用户看到的字符数量。如果刚好从代理对中间切开，还可能产生不完整的 Unicode 字符。

所以 `substring()` 本身没有问题，问题在于把它当成完整的 RAG 切分策略。

### 13. 为什么固定字符长度可能把一个完整句子从中间截断？

说话人1: 问题十三，为什么固定字符长度可能把一个完整句子从中间截断？

说话人1: 答，因为固定长度算法只根据索引决定结束位置，不会判断当前位置是不是句号、问号或者其他自然边界。

例如，原文是“当设备温度超过 90 摄氏度时，应立即停止运行并检查冷却系统”。

如果恰好在“应立即停止”中间切开，前后两个 Chunk 都可能无法独立表达完整意思。

所以更合理的做法是先确定目标长度，再尽量向前或向后寻找合适的句子、段落边界。

### 14. 为什么暴力切分可能破坏段落之间的逻辑关系？

说话人1: 问题十四，为什么暴力切分可能破坏段落之间的逻辑关系？

说话人1: 答，因为自然文本通常不是一堆互相独立的句子。

例如第一段介绍故障现象，第二段分析故障原因，第三段给出维修步骤。

如果切分时把这三个段落完全拆散，检索到其中一个 Chunk 时，就可能不知道它对应哪个设备问题。

所以切分时要尽可能保留段落之间的因果关系、条件关系和解释关系。

### 15. 为什么标题、正文和下级标题可能被拆分到不同 Chunk？

说话人1: 问题十五，为什么标题、正文和下级标题可能被拆分到不同 Chunk？

说话人1: 答，因为字符暴力切分不认识文档层级结构。

例如：

```
## E102 故障处理

### 故障原因
冷却系统异常。

### 处理步骤
检查冷却管路。
```

如果切分位置刚好落在标题和正文之间，就可能出现 Chunk 只有“处理步骤”，却没有设备型号和故障名称的情况。

所以处理 Markdown 时，应该先解析标题层级，尽量让标题路径和对应正文一起进入 Chunk。

### 16. 为什么一个完整的技术定义可能被切成两个无法独立理解的片段？

说话人1: 问题十六，为什么一个完整的技术定义可能被切成两个无法独立理解的片段？

说话人1: 答，因为技术定义经常包含概念、条件和结论。

例如，“幂等性是指同一个请求执行一次或多次，产生的业务结果保持一致”。

如果把它切成“幂等性是指同一个请求执行一次或多次”和“产生的业务结果保持一致”，第二个 Chunk 就缺少主语和定义对象。

这种 Chunk 即使被向量检索命中，也可能无法独立提供有用知识。

### 17. 如果切分位置落在 Markdown 表格中间，会对检索产生什么影响？

说话人1: 问题十七，如果切分位置落在 Markdown 表格中间，会对检索产生什么影响？

说话人1: 答，Markdown 表格中的每一行通常依赖表头才能理解。

例如表头是“故障代码、故障现象、处理措施”，后面某一行是“E102、温度过高、检查冷却系统”。

如果表头和数据行被切到不同 Chunk，检索结果就可能只剩下 E102 和一段内容，却不知道各列分别代表什么。

所以处理表格时，应该尽量保留表头和对应数据行的关系，必要时把每一行转换成带字段名称的自然语言文本。

### 18. 如果切分位置落在 Java 代码块中间，会造成哪些问题？

说话人1: 问题十八，如果切分位置落在 Java 代码块中间，会造成哪些问题？

说话人1: 答，可能把方法、类、注释和代码块拆开。

例如，一个 Chunk 只有方法调用，没有方法定义；另一个 Chunk 只有方法定义，却没有调用场景。

这样检索到的代码片段可能缺少依赖和执行上下文。

处理代码文件时，应该优先考虑类、方法、字段和注释等语法结构，尽量按照方法或者逻辑模块切分，而不是直接截断字符。

### 19. 为什么 PDF 解析后的跨页内容尤其容易出现上下文断裂？

说话人1: 问题十九，为什么 PDF 解析后的跨页内容尤其容易出现上下文断裂？

说话人1: 答，因为 PDF 的页面布局不一定等于自然文本的逻辑结构。

一个段落可能在第一页开始，在第二页继续；一个表格也可能跨越多个页面。

如果解析器没有正确处理阅读顺序、页眉页脚和跨页内容，可能把正文拆开，甚至把页码、页眉插入句子中间。

所以 PDF 处理不能只看提取出来的字符串，还要尽可能保留页码、章节、表格和段落等来源信息。

### 20. 如果设备型号、故障代码和故障处理步骤被分到不同 Chunk，会影响什么业务结果？

说话人1: 问题二十，如果设备型号、故障代码和故障处理步骤被分到不同 Chunk，会影响什么业务结果？

说话人1: 答，会影响检索的准确性，也可能影响维修建议的正确性。

例如，E102 在不同设备型号上可能对应不同故障含义。

如果故障代码和设备型号分开，系统可能把其他设备的维修方法检索出来。

如果故障原因和处理步骤分开，模型可能只能回答故障现象，却无法给出完整的维修方案。

所以制造业知识库应该尽量让设备型号、故障代码、故障现象、原因和处理步骤保持关联。

### 21. 为什么字符暴力切分可能导致 Chunk 包含大量无意义的上下文？

说话人1: 问题二十一，为什么字符暴力切分可能导致 Chunk 包含大量无意义的上下文？

说话人1: 答，因为它只按照位置截取文本，不会识别哪些内容对当前知识点有用。

例如，某个 Chunk 可能同时包含上一章节的结尾、当前章节的正文和下一章节的开头。

这些内容虽然在字符位置上连续，但语义上可能没有直接关系。

结果就是一个 Chunk 包含多个主题，Embedding 表示也容易变得不够集中，影响检索区分度。

### 22. 如果 Chunk 切得过大，会对 Embedding、检索和 LLM 上下文产生什么影响？

说话人1: 问题二十二，如果 Chunk 切得过大，会对 Embedding、检索和 LLM 上下文产生什么影响？

说话人1: 答，首先，Chunk 越大，Embedding 输入 Token 越多，可能接近甚至超过模型的最大输入限制。

其次，一个 Chunk 包含多个主题，向量表示可能不够集中，检索时容易出现主题混杂。

最后，检索到一个很大的 Chunk，会占用更多 LLM 上下文窗口，增加输入 Token 成本，也可能挤占其他更相关的知识。

所以 Chunk 应该足够完整，但不能无限变大。

### 23. 如果 Chunk 切得过小，会增加哪些检索和工程成本？

说话人1: 问题二十三，如果 Chunk 切得过小，会增加哪些检索和工程成本？

说话人1: 答，Chunk 过小，首先会增加向量数量和存储成本。

其次，同一个知识点可能被拆成多个片段，检索时需要更多候选才能拼出完整信息。

还可能增加重复 Chunk、上下文重组和 Rerank 的工作量。

因此，Chunk 过小不一定提高精确率，反而可能降低答案完整性。

## 三、语义边界与上下文完整性

### 24. 什么是语义边界？为什么句子、段落和章节通常是重要的切分边界？

说话人1: 问题二十四，什么是语义边界？为什么句子、段落和章节通常是重要的切分边界？

说话人1: 答，语义边界就是文本中一个相对完整的意思结束、另一个意思开始的位置。

句子通常表达一个相对完整的判断，段落通常围绕一个主题展开，章节则代表更高层次的知识组织。

所以这些位置通常比任意字符位置更适合切分。

但也不是所有句号、段落和标题都一定是正确边界，还要结合上下文判断。

### 25. 为什么完整的语义单元比单纯满足字符长度更重要？

说话人1: 问题二十五，为什么完整的语义单元比单纯满足字符长度更重要？

说话人1: 答，因为 RAG 最终是为了检索和使用知识。

一个 Chunk 即使只有 300 个 Token，如果它缺少关键条件，也可能无法正确回答问题。

反过来，一个稍微超过目标长度，但语义完整的段落，可能更适合独立检索。

所以长度是约束条件，语义完整性才是切分质量的重要目标。

### 26. 如何判断一段文本是否适合独立成为一个 Chunk？

说话人1: 问题二十六，如何判断一段文本是否适合独立成为一个 Chunk？

说话人1: 答，我通常会检查几个问题。

第一，它有没有明确的主题？

第二，它的主语、条件和结论是否完整？

第三，离开前后文以后，是否还能理解它表达的意思？

第四，它是否包含必要的设备型号、故障代码、单位和限制条件？

第五，它的 Token 长度是否满足模型要求？

如果这些条件基本满足，就比较适合独立成为一个 Chunk。

### 27. 为什么标题应该尽量与对应正文保持关联？

说话人1: 问题二十七，为什么标题应该尽量与对应正文保持关联？

说话人1: 答，因为标题能够提供正文的主题和上下文。

例如正文只有“检查冷却系统”，单独来看，不知道是在检查什么设备，也不知道对应什么故障。

如果前面带上“XJ-200 设备 / E102 温度过高 / 处理步骤”，含义就清楚得多。

所以可以把文档标题、章节路径作为 Chunk 的上下文信息保存，必要时也可以补充到用于 Embedding 的文本中。

### 28. 如何处理跨段落的因果关系、条件关系和步骤关系？

说话人1: 问题二十八，如何处理跨段落的因果关系、条件关系和步骤关系？

说话人1: 答，首先要识别段落之间的逻辑关系。

例如，“当压力超过 10MPa 时”是条件，“安全阀可能无法正常工作”是风险，“应立即停止设备”是处理动作。

如果这些内容分布在多个段落，就不能简单地独立切开。

可以根据逻辑关系合并成一个完整 Chunk；如果长度超限，则保留必要的前置条件、标题和步骤编号，并通过元数据关联前后片段。

### 29. 为什么需要保留文档标题、章节路径和来源信息？

说话人1: 问题二十九，为什么需要保留文档标题、章节路径和来源信息？

说话人1: 答，因为检索不仅需要知道文本内容，还需要知道文本来自哪里。

文档标题可以说明知识背景，章节路径可以说明具体主题，来源信息可以支持答案引用和原文定位。

例如，检索到“检查冷却管路”，还应该知道它来自哪份设备手册、第几章、第几页。

这样不仅能提高上下文完整性，还能支持用户追溯原文，降低模型编造来源的风险。

### 30. 如何避免 Chunk 只保留结论，却丢失结论成立的条件？

说话人1: 问题三十，如何避免 Chunk 只保留结论，却丢失结论成立的条件？

说话人1: 答，切分时要把条件和结论作为一个逻辑单元处理。

例如，“在设备运行温度超过 90 摄氏度且冷却风扇停止时，应立即停机”。

不能只保留“应立即停机”，也不能只保留“温度超过 90 摄氏度”。

如果原文过长，可以通过标题路径、条件字段或者前置上下文补充来保留必要信息。

### 31. 什么是上下文丢失？它会如何影响 Embedding 表示和向量检索？

说话人1: 问题三十一，什么是上下文丢失？它会如何影响 Embedding 表示和向量检索？

说话人1: 答，上下文丢失就是一个文本片段脱离了理解它所必需的前置或后置信息。

例如，原文是“该型号设备出现 E102 时，应检查冷却系统”，切分后只剩下“应检查冷却系统”。

Embedding 模型只能根据当前输入生成向量，它并不知道已经丢失的设备型号和故障代码。

这样生成的向量可能无法准确表达原始知识，后续检索也可能匹配到其他设备的相似维修内容。

### 32. 为什么在 Chunk 中补充文档标题或章节路径，有助于恢复上下文？

说话人1: 问题三十二，为什么在 Chunk 中补充文档标题或章节路径，有助于恢复上下文？

说话人1: 答，因为标题和章节路径能够提供文档主题信息。

例如，原始 Chunk 只有“检查传感器连接是否松动”。

补充章节路径后，可以变成“XJ-200 设备 / E102 故障处理 / 检查传感器连接是否松动”。

这样 Embedding 模型就能同时看到设备型号、故障主题和具体操作。

不过要注意，标题补充应该基于真实文档结构，不能随意编造上下文。

### 33. 如何处理跨 Chunk 的连续步骤、长列表和多级编号？

说话人1: 问题三十三，如何处理跨 Chunk 的连续步骤、长列表和多级编号？

说话人1: 答，首先要保留步骤编号和父级标题。

例如，一个维修流程有十个步骤，可以按照合理长度拆成多个 Chunk，但每个 Chunk 都应该保留所属流程名称和步骤范围。

对于多级编号，还应该保留父级编号，例如 `2.1.3`，避免只剩下一个孤立的子步骤。

如果业务要求严格按照顺序执行，可以在元数据中保存步骤序号和流程 ID，后续检索时再按顺序组合。

### 34. 如果一个段落本身超过最大 Token 限制，应该如何进一步切分？

说话人1: 问题三十四，如果一个段落本身超过最大 Token 限制，应该如何进一步切分？

说话人1: 答，不能因为它是一个自然段，就无限保留。

我会先尝试按句子边界切分，如果句子仍然过长，再按照分句、标点和语义边界继续拆分。

如果是表格，就按照表头和数据行拆分。

如果是代码，就按照方法和逻辑块拆分。

最终必须保证 Chunk 不超过模型允许的 Token 限制，同时尽量保留必要上下文。

## 四、常见切分策略与适用场景

### 35. 固定长度切分适合什么类型的文档？它的局限性是什么？

说话人1: 问题三十五，固定长度切分适合什么类型的文档？它的局限性是什么？

说话人1: 答，固定长度切分适合结构比较简单、文本连续、没有明显章节和复杂格式的内容。

例如部分日志、长文本记录或者已经预处理成独立文本块的数据。

它的优点是简单、容易控制长度。

缺点是不了解语义边界，可能把句子、标题、表格和代码拆开，所以不适合直接作为所有文档的统一切分方案。

### 36. 按句子切分如何避免破坏句子完整性？

说话人1: 问题三十六，按句子切分如何避免破坏句子完整性？

说话人1: 答，按句子切分需要先识别句子边界，再将完整句子组合成符合目标长度的 Chunk。

例如，先按句号、问号、感叹号等标点识别句子，再不断把相邻句子合并。

如果一个句子本身超过最大 Token 限制，再使用更细的分句策略处理。

另外要注意英文缩写、小数点、版本号等情况，不能简单地把所有句点都当成句子结束符。

### 37. 按段落切分如何保留自然文本的语义结构？

说话人1: 问题三十七，按段落切分如何保留自然文本的语义结构？

说话人1: 答，按段落切分就是尽量把一个自然段作为一个基本语义单元。

当多个相邻段落合并后没有超过最大 Token 限制时，可以将它们放进同一个 Chunk。

如果超过限制，就在段落边界拆分。

如果某个段落本身太长，再进一步按句子切分。

这样可以在长度控制和语义完整性之间取得比较好的平衡。

### 38. 按标题层级切分如何处理 Markdown 文档？

说话人1: 问题三十八，按标题层级切分如何处理 Markdown 文档？

说话人1: 答，首先要识别 Markdown 标题，例如 `#`、`##` 和 `###`。

然后维护当前的标题路径。

例如进入 `## 故障处理`，再进入 `### E102 温度过高`，后面的正文就属于这个章节。

切分时尽量让标题和对应正文保持在同一个 Chunk 中，并把完整标题路径保存为元数据。

如果一个章节内容过长，再按照段落和句子继续切分。

### 39. 递归字符切分（Recursive Character Splitting）与直接字符暴力切分有什么区别？

说话人1: 问题三十九，递归字符切分与直接字符暴力切分有什么区别？

说话人1: 答，直接字符暴力切分是按照固定字符位置直接截断。

递归字符切分则是按照一组分隔符，从更大的结构边界开始尝试切分。

例如，先尝试按段落分隔符切分，如果某个片段仍然太长，再按换行符切分，然后再按句子标点切分。

如果仍然超长，才使用更细的字符边界。

所以递归切分虽然也可能使用字符长度控制，但它优先考虑文本结构，不是简单地从固定索引截断。

### 40. 递归切分为什么通常会优先尝试段落、换行、句子等分隔符？

说话人1: 问题四十，递归切分为什么通常会优先尝试段落、换行、句子等分隔符？

说话人1: 答，因为这些分隔符通常代表不同层次的语义边界。

段落边界通常比句子边界更适合保留完整主题，句子边界又比任意字符位置更自然。

所以递归切分一般按照从大到小的结构顺序尝试。

这样可以尽可能保留文本原有的组织方式，只有在内容确实太长时才继续细分。

### 41. 语义切分（Semantic Chunking）如何判断相邻文本是否属于同一语义单元？

说话人1: 问题四十一，语义切分如何判断相邻文本是否属于同一语义单元？

说话人1: 答，常见做法是先把文本拆成句子或较小的候选片段，再计算相邻片段的语义表示。

例如，使用 Embedding 模型分别生成句子向量，然后计算相邻向量之间的相似度。

如果相似度明显下降，就可能说明主题发生了变化，可以考虑在这里切分。

不过语义相似度只是一个判断信号，不代表一定能够正确识别业务逻辑。

还需要结合标题、段落、长度限制和领域规则。

### 42. 语义切分是否一定比递归切分效果好？它有哪些额外成本？

说话人1: 问题四十二，语义切分是否一定比递归切分效果好？它有哪些额外成本？

说话人1: 答，不一定。

语义切分可以根据内容主题变化选择边界，但它依赖 Embedding 模型和相似度阈值。

如果相邻句子虽然语义相似，但实际上属于不同章节，单纯依赖向量相似度可能切分错误。

而且语义切分通常需要额外计算 Embedding，增加处理时间和模型成本。

对于结构清晰的技术手册，标题加段落的递归切分可能已经足够。

所以应该通过实际检索评估判断哪种策略更适合，而不是认为语义切分一定最好。

### 43. 不同格式的文档为什么需要采用不同的切分策略？

说话人1: 问题四十三，不同格式的文档为什么需要采用不同的切分策略？

说话人1: 答，因为不同文档的结构不同，承载知识的方式也不同。

Markdown 主要依赖标题和列表组织内容。

PDF 可能包含分页、双栏、表格和扫描图片。

Word 可能包含标题样式、表格和图片说明。

代码文件则有类、方法、注释和语法结构。

如果全部使用同一种字符切分算法，就无法充分利用这些结构信息。

所以生产级 RAG 应该先识别文档类型，再选择合适的解析和切分策略。

### 44. PDF、Word、Markdown、HTML 和代码文件分别应该重点考虑哪些结构信息？

说话人1: 问题四十四，PDF、Word、Markdown、HTML 和代码文件分别应该重点考虑哪些结构信息？

说话人1: 答，PDF 重点关注页码、阅读顺序、跨页段落、表格和扫描件。

Word 重点关注标题样式、段落、表格、列表和图片说明。

Markdown 重点关注标题层级、代码块、列表、引用块和表格。

HTML 重点关注 DOM 结构、标题标签、段落标签、列表、表格以及导航和广告等非正文内容。

代码文件重点关注语言语法、类、方法、注释、依赖关系和代码块。

切分策略应该建立在解析出的结构信息上，而不是只拿最终字符串进行统一处理。

## 五、Chunk Size、Overlap 与 Token 限制

### 45. Chunk Size 如何影响 Embedding 模型的输入长度和语义表达？

说话人1: 问题四十五，Chunk Size 如何影响 Embedding 模型的输入长度和语义表达？

说话人1: 答，Chunk Size 越大，Embedding 模型接收到的上下文越多，可能包含更完整的知识关系。

但是如果一个 Chunk 包含多个主题，生成的向量可能混合多种语义，降低检索区分度。

Chunk Size 太小，又可能丢失上下文。

所以需要让每个 Chunk 尽可能围绕一个相对明确的知识主题，同时满足 Embedding 模型的输入限制。

### 46. Chunk Size 如何影响向量检索的召回率与精确率？

说话人1: 问题四十六，Chunk Size 如何影响向量检索的召回率与精确率？

说话人1: 答，Chunk 太大时，一个向量可能包含多个主题，检索时容易召回与问题只有部分相关的内容，降低精确率。

Chunk 太小时，一个完整知识点可能被拆成多个片段，单独检索时缺少上下文，影响有效召回和答案完整性。

因此，Chunk Size 会同时影响召回和精确率，但具体变化并不是简单的单调关系。

必须使用真实问题集进行对比测试。

### 47. Overlap 过小可能导致什么问题？过大又会产生什么副作用？

说话人1: 问题四十七，Overlap 过小可能导致什么问题？过大又会产生什么副作用？

说话人1: 答，Overlap 过小，可能导致切分边界处的条件、解释和连续步骤被分开。

Overlap 过大，则会产生大量重复文本，相邻 Chunk 的内容高度相似。

这会增加 Embedding 计算、向量存储和检索结果重复的成本。

所以 Overlap 应该根据知识单元跨边界的概率和文档结构来设置，不是越大越安全。

### 48. 为什么 Overlap 会增加重复文本、Embedding 费用和向量存储量？

说话人1: 问题四十八，为什么 Overlap 会增加重复文本、Embedding 费用和向量存储量？

说话人1: 答，因为相邻 Chunk 会重复包含一部分内容。

假设 Chunk Size 是 500 个 Token，Overlap 是 100 个 Token，那么每个新 Chunk 理论上只新增大约 400 个 Token 的内容。

为了覆盖同样长度的文档，就会产生更多 Chunk，重复文本也会更多。

如果 Embedding 服务按照输入 Token 计费，重复内容也可能重复产生计算成本。

同时，向量库需要保存更多向量和元数据，检索时也可能返回重复内容。

### 49. 如何根据 Embedding 模型的最大输入 Token 限制确定 Chunk Size？

说话人1: 问题四十九，如何根据 Embedding 模型的最大输入 Token 限制确定 Chunk Size？

说话人1: 答，首先要确认实际使用的 Embedding 模型最大输入 Token 数。

然后不能直接把 Chunk Size 设置成最大值，而要预留安全余量。

例如，模型最大输入是 8192 Token，Chunk Size 可以先从明显低于上限的范围开始测试。

还要考虑标题、章节路径、元数据拼接和特殊格式可能增加的 Token。

最后通过实际 Tokenizer 计算每个 Chunk 的长度，确保不会超过模型限制。

### 50. 为什么必须为模型输入预留 Token 余量，而不能直接使用最大限制？

说话人1: 问题五十，为什么必须为模型输入预留 Token 余量，而不能直接使用最大限制？

说话人1: 答，因为最终提交给模型的文本可能不只是 Chunk 正文。

例如，系统可能在正文前面补充文档标题、章节路径和设备型号。

如果刚好把正文切到模型最大限制，拼接这些上下文后就可能超过限制。

另外，不同模型和供应商对 Token 统计的细节也可能不同。

所以应该预留余量，并在真正调用 Embedding API 前进行长度校验。

### 51. 如何同时考虑 Chunk Size、Overlap、TopK 和最终 LLM 上下文窗口？

说话人1: 问题五十一，如何同时考虑 Chunk Size、Overlap、TopK 和最终 LLM 上下文窗口？

说话人1: 答，这几个参数需要作为一个整体考虑。

Chunk Size 决定单个知识片段的长度，Overlap 决定相邻片段重复多少内容，TopK 决定检索多少个候选片段。

最终送给大模型的上下文，还要受到 System Prompt、用户问题、聊天历史和其他业务信息的影响。

例如，假设每个 Chunk 平均 500 Token，最终选取 5 个 Chunk，那么仅知识上下文就可能达到 2500 Token 左右，还没有计算其他 Prompt 内容。

所以 TopK 不能只看向量检索结果数量，还要设置最终上下文 Token 预算，必要时进行去重、压缩和重排序。

### 52. 如何根据不同文档类型设计不同的 Chunk Size 和 Overlap？

说话人1: 问题五十二，如何根据不同文档类型设计不同的 Chunk Size 和 Overlap？

说话人1: 答，我不会给所有文档设置同一套参数。

普通说明文档可以按段落和标题切分，使用适中的 Chunk Size 和较小 Overlap。

设备维修手册需要保留故障代码、原因和处理步骤之间的关系，必要时增加上下文重叠。

代码文档应该优先按类和方法切分，Overlap 不一定是最合适的解决方式，还可以通过类名、方法名和依赖元数据恢复上下文。

表格则应该优先保留表头和数据行关系。

具体参数需要根据文档结构和检索测试结果确定。

### 53. 为什么 Chunk 参数不能只依赖经验值，而应该通过检索评估进行调整？

说话人1: 问题五十三，为什么 Chunk 参数不能只依赖经验值，而应该通过检索评估进行调整？

说话人1: 答，因为不同知识库的内容和查询方式不同。

技术手册可能包含大量设备型号和故障代码，产品说明书可能以自然语言描述为主，代码知识库又有完全不同的结构。

同一组 Chunk Size 和 Overlap，在不同数据集上的检索效果可能不一样。

所以应该准备一组真实业务问题，比较不同参数下的 Recall\@K、Precision\@K、MRR 和答案质量。

最后选择效果和成本都合理的参数，而不是直接照搬网上的经验值。

## 六、Spring AI 1.1.8 与 Java 工程实现

### 54. Spring AI 1.1.8 中的 `TokenTextSplitter` 解决什么问题？它采用什么切分思路？

说话人1: 问题五十四，Spring AI 1.1.8 中的 `TokenTextSplitter` 解决什么问题？它采用什么切分思路？

说话人1: 答，`TokenTextSplitter` 是 Spring AI 提供的文本切分器，主要解决按照 Token 数量控制 Chunk 长度的问题。

它不是简单地按照字符位置截断，而是先使用 Tokenizer 对文本编码，再按照目标 Token 数量切分。

然后，它会尝试寻找合适的标点或换行位置，让切分结果尽量靠近自然语言边界。

Spring AI 1.1.x 的实现使用 `CL100K_BASE` 编码思路，依赖 JTokkit。

但要注意，它主要解决 Token 长度控制和基础标点边界问题，不等于完整的 Markdown 结构切分器，也不等于语义切分器。

### 55. `TokenTextSplitter` 的 `chunkSize`、`minChunkSizeChars`、`minChunkLengthToEmbed` 和 `maxNumChunks` 分别控制什么？

说话人1: 问题五十五，`TokenTextSplitter` 的 `chunkSize`、`minChunkSizeChars`、`minChunkLengthToEmbed` 和 `maxNumChunks` 分别控制什么？

说话人1: 答，`chunkSize` 控制目标 Chunk Token 数量，也就是每个 Chunk 希望控制在多大。

`minChunkSizeChars` 控制寻找标点切分位置时的最小字符长度门槛，避免切分结果过短。

`minChunkLengthToEmbed` 控制一个 Chunk 至少达到多长，才会被保留用于后续处理。

`maxNumChunks` 控制一次切分最多生成多少个 Chunk，避免极端输入产生过多分块。

这里最容易混淆的是，`minChunkSizeChars` 是字符相关的边界控制参数，不是相邻 Chunk 之间的重叠长度。

### 56. 为什么 `minChunkSizeChars` 不能简单理解为 Chunk Overlap？

说话人1: 问题五十六，为什么 `minChunkSizeChars` 不能简单理解为 Chunk Overlap？

说话人1: 答，因为它们解决的是两个不同的问题。

`minChunkSizeChars` 是 TokenTextSplitter 寻找合适切分位置时使用的字符长度参数。

Chunk Overlap 则是相邻两个 Chunk 之间有意保留的重复内容长度。

例如，Overlap 设置为 100 个 Token，意味着后一个 Chunk 会重复包含前一个 Chunk 的部分内容。

而 `minChunkSizeChars=350` 并不代表前后 Chunk 重复 350 个字符。

这两个参数不能混为一谈。

### 57. Spring AI 1.1.x 的 `TokenTextSplitter` 是否原生提供独立的 Overlap 参数？如果没有，如何实现？

说话人1: 问题五十七，Spring AI 1.1.x 的 `TokenTextSplitter` 是否原生提供独立的 Overlap 参数？如果没有，如何实现？

说话人1: 答，Spring AI 1.1.8 的 `TokenTextSplitter` 没有提供独立的 Chunk Overlap 配置参数。

它主要根据 Token 数量切分，并尝试在标点和换行位置调整边界。

如果业务需要 Overlap，可以自己实现切分器，或者在切分结果上进行有边界的重叠处理。

例如，先按段落和句子生成基础 Chunk，再让后一个 Chunk 保留前一个 Chunk 末尾的一部分完整句子。

我更倾向于按照语义单元实现 Overlap，而不是简单地重复固定数量的字符，因为固定字符重叠同样可能截断句子。

### 58. 如何使用 Java 实现一个保留段落边界的递归切分器？

说话人1: 问题五十八，如何使用 Java 实现一个保留段落边界的递归切分器？

说话人1: 答，核心思路是先按段落切分，再把相邻段落组合起来，直到接近目标 Token 长度。

如果某个段落本身就超过限制，再继续按句子切分。

下面是一个简化实现，重点展示切分思路。生产代码还需要接入实际 Tokenizer、超长句处理、Overlap 和元数据管理。

```
public class ParagraphChunker {

    private final int maxChars;

    public ParagraphChunker(int maxChars) {
        if (maxChars <= 0) {
            throw new IllegalArgumentException("maxChars must be positive");
        }
        this.maxChars = maxChars;
    }

    public List<String> split(String text) {
        List<String> chunks = new ArrayList<>();
        StringBuilder current = new StringBuilder();

        String[] paragraphs = text.split("\\R\\s*\\R");

        for (String paragraph : paragraphs) {
            String part = paragraph.trim();

            if (part.isEmpty()) {
                continue;
            }

            if (part.length() > maxChars) {
                flush(current, chunks);
                splitLongParagraph(part, chunks);
                continue;
            }

            int nextLength = current.length()
                    + (current.isEmpty() ? 0 : 2)
                    + part.length();

            if (nextLength > maxChars) {
                flush(current, chunks);
            }

            if (!current.isEmpty()) {
                current.append("\n\n");
            }

            current.append(part);
        }

        flush(current, chunks);
        return chunks;
    }

    private void splitLongParagraph(
            String paragraph,
            List<String> chunks) {

        String[] sentences = paragraph.split("(?<=[。！？.!?])");

        StringBuilder current = new StringBuilder();

        for (String sentence : sentences) {
            if (sentence.length() > maxChars) {
                flush(current, chunks);

                // 极端超长句的兜底处理。
                for (int i = 0; i < sentence.length(); i += maxChars) {
                    chunks.add(sentence.substring(
                            i,
                            Math.min(i + maxChars, sentence.length())
                    ));
                }
                continue;
            }

            if (current.length() + sentence.length() > maxChars) {
                flush(current, chunks);
            }

            current.append(sentence);
        }

        flush(current, chunks);
    }

    private void flush(
            StringBuilder current,
            List<String> chunks) {

        if (!current.isEmpty()) {
            chunks.add(current.toString().trim());
            current.setLength(0);
        }
    }
}
```

说话人1: 答，这个示例有一个重要限制：它用字符数控制长度，只适合解释递归切分的结构思路。

真正的 RAG 工程应该把 `maxChars` 替换成 Token 长度判断，并且对超长句、Markdown 表格、代码块和标题路径做专门处理。

### 59. 如何设计统一的 Chunk 元数据，包括文档 ID、章节路径、页码、Chunk 序号和来源？

说话人1: 问题五十九，如何设计统一的 Chunk 元数据，包括文档 ID、章节路径、页码、Chunk 序号和来源？

说话人1: 答，Chunk 不应该只保存正文，还应该保存能够定位原文的信息。

例如：

```
Map<String, Object> metadata = new HashMap<>();

metadata.put("document_id", "manual-001");
metadata.put("document_name", "XJ-200设备使用手册");

metadata.put("parser_version", "1.0");

```

这样检索到 Chunk 后，就可以知道它来自哪份文档、哪个章节和哪几页。

生产环境还可以增加文档版本、内容哈希、设备型号、故障代码和解析任务 ID。

注意，页码应该来自真实解析结果，不能因为 Chunk 序号就推测原文页码。

### 60. 如何为不同文档类型配置不同的 TextSplitter？

说话人1: 问题六十，如何为不同文档类型配置不同的 TextSplitter？

说话人1: 答，我会先定义统一的切分接口，再针对不同文档类型提供不同实现。

例如：

```
public interface DocumentChunker {

    boolean supports(DocumentType type);

    List<Document> split(Document document);

```

然后分别实现 MarkdownChunker、PdfChunker、WordChunker 和 CodeChunker。

Markdown 主要按照标题和段落切分，PDF 需要考虑页码和跨页结构，Word 需要考虑标题样式和表格，代码则需要考虑类和方法边界。

业务层只依赖统一接口，通过文档类型选择对应策略。

这样以后增加新的文档类型，不需要把所有切分逻辑写进一个巨大的 if-else。

### 61. 如何编写单元测试，验证 Chunk 长度、边界完整性、Overlap 和元数据保留？

说话人1: 问题六十一，如何编写单元测试，验证 Chunk 长度、边界完整性、Overlap 和元数据保留？

说话人1: 答，首先要针对不同维度设计测试。

Chunk 长度测试，验证每个 Chunk 的 Token 数量没有超过配置上限。

边界完整性测试，验证标题、句子、段落和代码块没有被意外截断。

Overlap 测试，验证相邻 Chunk 是否保留了预期的上下文内容。

元数据测试，验证文档 ID、章节路径、页码和 Chunk 序号都正确保留。

还应该增加边界测试，例如空文档、只有一个段落、超长句子、中文和英文混合、表格、代码块以及特殊 Unicode 字符。

不能只测试最终生成了多少个 Chunk，还要检查内容是否正确。

### 62. 如何抽查原文与 Chunk 内容，发现解析异常、内容丢失和上下文断裂？

说话人1: 问题六十二，如何抽查原文与 Chunk 内容，发现解析异常、内容丢失和上下文断裂？

说话人1: 答，我会建立原文和 Chunk 的对应关系。

每个 Chunk 保存原始文档 ID、页码、章节路径和原文位置等信息。

抽查时从 Chunk 反向定位原文，比较正文是否完整，标题、表格、代码和关键字段有没有丢失。

还可以随机抽取文档，对比原始 PDF 页面和解析文本，重点检查设备型号、故障代码、数值、单位和维修步骤。

如果发现解析文本本身就有问题，就先修复解析器；如果原文正确但 Chunk 不完整，再检查切分策略。

## 七、生产级 RAG 质量评估

### 63. 为什么 Chunk 切分质量会直接影响 Embedding 表示和向量检索效果？

说话人1: 问题六十三，为什么 Chunk 切分质量会直接影响 Embedding 表示和向量检索效果？

说话人1: 答，因为 Embedding 模型是根据输入文本生成向量的。

如果输入文本缺少关键上下文，模型就无法从当前文本中获取已经丢失的信息。

如果一个 Chunk 同时包含多个不相关主题，向量表示也可能混合多种语义。

所以 Embedding 不是独立于 Chunking 的，输入文本质量直接影响向量表达和后续检索。

### 64. 如何通过 Recall\@K、Precision\@K 和 MRR 评估不同切分策略？

说话人1: 问题六十四，如何通过 Recall\@K、Precision\@K 和 MRR 评估不同切分策略？

说话人1: 答，首先要准备一组有标准答案和相关文档标注的测试问题。

Recall\@K 关注前 K 个检索结果中，找回了多少相关内容。

Precision\@K 关注前 K 个结果中，有多少是真正相关的内容。

MRR 关注第一个相关结果出现的位置，越靠前通常越好。

例如，我们分别使用固定长度切分、递归切分和语义切分建立三套索引，然后使用同一组问题进行检索。

最后比较指标，判断哪种策略更适合当前知识库。

需要注意，评估时要统一 Embedding 模型、检索算法和 TopK，否则无法确定指标变化到底来自切分策略还是其他因素。

### 65. 如何设计一组测试问题，对比固定长度切分、递归切分和语义切分？

说话人1: 问题六十五，如何设计一组测试问题，对比固定长度切分、递归切分和语义切分？

说话人1: 答，测试问题应该覆盖不同的知识类型。

例如，第一类是设备型号和故障代码的精确查询。

第二类是故障现象和原因分析。

第三类是连续维修步骤。

第四类是跨段落的条件和结论。

第五类是表格中的参数查询。

第六类是跨页内容和长章节查询。

然后给每个问题标注应该召回的原文片段或相关 Chunk。

使用相同的检索配置测试三种切分方案，比较 Recall\@K、Precision\@K、MRR，同时人工检查召回内容是否完整。

这样才能判断哪种切分策略真正适合业务，而不是只看 Chunk 数量或者单次检索结果。

### 66. 如果检索结果经常缺少故障原因或处理步骤，如何判断是否由 Chunk 边界不合理造成？

说话人1: 问题六十六，如果检索结果经常缺少故障原因或处理步骤，如何判断是否由 Chunk 边界不合理造成？

说话人1: 答，首先要回到原始文档，确认故障原因和处理步骤是否被正确解析出来。

如果原文解析正常，再检查它们是否被拆分到不同 Chunk。

然后查看检索日志，确认系统是否只召回了故障现象所在的 Chunk，而没有召回原因和处理步骤。

如果确实是边界问题，可以调整 Chunk Size、Overlap，或者将故障现象、原因和处理步骤组织成一个更完整的知识单元。

如果相关 Chunk 已经被正确召回，但大模型没有使用它们，就要继续检查上下文构建和 Prompt，而不能把所有问题都归咎于切分。

### 67. 如果 TopK 返回多个高度重复的 Chunk，应该从哪些切分和检索参数排查？

说话人1: 问题六十七，如果 TopK 返回多个高度重复的 Chunk，应该从哪些切分和检索参数排查？

说话人1: 答，首先检查 Overlap 是否设置过大，导致相邻 Chunk 内容高度重复。

其次检查 Chunk Size 是否过小，导致同一段知识被拆成很多相似片段。

然后检查文档是否重复入库，或者不同版本文档是否同时存在。

检索层面还要检查 TopK、去重规则和候选合并逻辑。

可以通过 Document ID、Chunk ID、内容哈希和来源版本进行去重，必要时按照文档和章节限制重复候选数量。

### 68. 如何评估 Chunk 数量、向量存储成本、检索质量和模型上下文成本之间的平衡？

说话人1: 问题六十八，如何评估 Chunk 数量、向量存储成本、检索质量和模型上下文成本之间的平衡？

说话人1: 答，我会同时看四个方面。

第一，Chunk 数量，数量越多，通常意味着需要生成和维护更多向量。

第二，向量存储成本，包括向量维度、索引结构和元数据占用。

第三，检索质量，重点关注 Recall\@K、Precision\@K、MRR 和最终答案质量。

第四，模型上下文成本，关注最终送给大模型的 Token 数量，以及相应的模型调用费用。

例如，Chunk 太小可能导致向量数量增加，TopK 需要提高才能拼出完整知识；Chunk 太大则可能增加单个检索结果的上下文占用。

最终应该通过离线评测和线上成本指标，找到一个质量与成本都能接受的参数组合。

### 69. 如果要为制造设备故障知识库设计切分方案，你会如何处理设备型号、故障代码、故障现象、原因分析和维修步骤之间的关联？

说话人1: 问题六十九，如果要为制造设备故障知识库设计切分方案，你会如何处理设备型号、故障代码、故障现象、原因分析和维修步骤之间的关联？

说话人1: 答，我会优先按照设备故障知识单元组织内容，而不是直接按照字符长度切分。

例如，一个故障知识单元可以包含：

```
设备型号：XJ-200
故障代码：E102
故障现象：运行过程中温度异常升高
可能原因：冷却管路堵塞、风扇异常
处理步骤：
1. 停止设备运行
2. 检查冷却管路
3. 检查风扇运行状态
4. 排除故障后进行试运行
```

如果这个知识单元没有超过 Token 限制，就尽量保留在同一个 Chunk 中。

如果内容太长，就按照原因分析和维修步骤等逻辑边界拆分，但每个 Chunk 都要保留设备型号、故障代码和必要的章节上下文。

另外，我会把设备型号、故障代码、文档版本、页码和章节路径保存为 Metadata。

这样检索时既可以使用向量相似度，也可以使用设备型号和故障代码进行精确过滤。

对于连续维修步骤，还要保留步骤编号和顺序，避免模型把维修流程拼接错误。

### 70. 面试官问：为什么不能只按字符暴力切分？你会如何从语义完整性、Token 限制、检索质量和生产成本四个层面回答？

说话人1: 问题七十，面试官问：为什么不能只按字符暴力切分？你会如何从语义完整性、Token 限制、检索质量和生产成本四个层面回答？

说话人1: 答，我认为字符暴力切分最大的问题，就是它只关注字符串长度，不关注知识本身的结构。

我从四个角度回答。

第一，语义完整性。字符暴力切分可能把标题、句子、表格、代码和故障处理步骤从中间截断，导致 Chunk 缺少必要的上下文。应该优先按照标题、段落和句子等语义边界切分。

第二，Token 限制。字符数不等于 Token 数量，不同语言、数字和代码的 Token 密度不同。应该使用与 Embedding 模型兼容的 Tokenizer 控制 Chunk 长度，并预留输入余量。

第三，检索质量。Chunk 太大容易混合多个主题，Chunk 太小又容易丢失上下文，都会影响向量表示和检索效果。应该通过 Recall\@K、Precision\@K 和 MRR 等指标评估不同切分策略。

第四，生产成本。Chunk Size 和 Overlap 会影响向量数量、Embedding 费用、存储成本、检索候选数量以及最终 LLM 上下文 Token 成本。不能只追求检索效果，还要考虑整体成本。

在实际项目中，我会先解析并保留文档结构，再根据 PDF、Word、Markdown 和代码等不同类型选择切分策略。普通文本优先使用标题、段落和句子边界，超长内容再递归切分，同时通过 Token 数量控制长度。

最后使用真实业务问题建立评测集，对比不同 Chunk Size、Overlap 和 TopK 的效果。

所以我的结论是：Chunking 不是简单地把长字符串切短，而是把原始文档转换成语义完整、长度可控、来源可追溯、适合检索的知识单元。
