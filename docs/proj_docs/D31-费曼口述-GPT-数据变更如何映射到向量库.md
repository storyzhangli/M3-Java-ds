# **费曼口述：数据变更如何映射到向量库**

**技术基线：** JDK 21、Spring Boot 3.5.x、Spring AI 1.1.8、PostgreSQL 18.6、pgvector。

**应用场景：** 制造设备故障知识库。假设知识库中保存设备维修手册、故障案例、维修记录和技术说明书。我们要解决的问题是：原始知识发生新增、修改、删除时，如何让 PostgreSQL + pgvector 中的 Chunk 和 Embedding 正确同步。

## **一、数据变更与向量库的基本关系**

**说话人1：问题1，为什么 RAG 知识库中的向量数据不是一次性写入后就永远不变？**

**说话人1：答：** 因为知识本身会变化。比如设备厂商发布了新版维修手册，原来的维修参数可能已经失效；维修人员发现了新的故障原因，也需要补充知识库。

RAG 中的向量是从原始文档经过切块和 Embedding 计算得到的派生数据。只要原文发生变化，对应的 Chunk 和向量就可能需要更新。

如果只更新原文、不更新向量库，检索出来的仍然是旧知识，模型就可能根据过期信息回答。

所以向量库不是一次性导入就结束，而是需要持续维护的数据系统。

**说话人1：问题2，什么是数据源（Source）、文档（Document）、Chunk 和 Embedding？它们之间是什么关系？**

**说话人1：答：** 这四个概念可以理解为一条数据加工链路。

- Source：原始数据来源，比如 PDF 维修手册、Word 技术文档、数据库中的维修记录。
- Document：经过解析后形成的文档对象，包含正文和相关 Metadata。
- Chunk：将 Document 按照一定策略切分得到的文本片段。
- Embedding：通过 Embedding 模型将 Chunk 文本转换得到的向量。

例如，一份设备维修手册经过解析得到一个 Document，再切分成 100 个 Chunk，每个 Chunk 分别生成一个向量。

它们之间的关系是：

`Source → Document → Chunk → Embedding`

注意，一个 Source 不一定只对应一个 Document，一个 Document 也不一定只对应一个 Chunk。

**说话人1：问题3，原始文档发生新增、修改、删除时，为什么必须考虑向量库中的数据同步？**

**说话人1：答：** 因为 RAG 检索通常不是直接查询原始 PDF，而是查询向量库中的 Chunk。

新增文档但没有向量化，模型就检索不到新知识。

修改文档但保留旧向量，模型可能检索到过期内容。

删除文档但保留旧向量，已经失效的知识仍然可能被召回。

因此，原始数据的新增、修改和删除，都必须映射成对应的向量数据变更操作。

**说话人1：问题4，为什么向量库中的数据应该被视为原始知识数据的派生数据，而不是唯一事实来源？**

**说话人1：答：** 因为向量是计算结果，不是原始事实。

比如维修手册中的原文写着：某型号设备的额定压力为 10 MPa。系统将这段内容切块并生成向量，向量本身并不能完整表达原文，也不能代替原始文档作为审计依据。

如果向量库损坏，我们应该能够根据原始文档重新解析、切块和向量化。

所以原始文档或权威业务记录才是事实来源，向量库是为语义检索服务的派生索引。

**说话人1：问题5，什么是数据变更映射（Change Mapping）？它要解决什么问题？**

**说话人1：答：** 数据变更映射，就是把原始数据发生的业务变化，转换成向量库需要执行的操作。

例如：

- 新增维修手册：解析、切块、生成 Embedding、写入向量库。
- 修改维修手册：重新处理受影响的 Chunk，替换旧版本。
- 删除维修手册：删除或停用对应文档的全部 Chunk。
- 更换 Embedding 模型：重新计算向量。

它要解决的是业务数据和向量数据之间的对应关系，以及变更如何可靠地传递和执行。

**说话人1：问题6，为什么业务数据变更不能简单地等同于向量库新增一条记录？**

**说话人1：答：** 因为业务变更可能对应新增、更新、删除，也可能不需要重新生成向量。

例如，只修改维修手册的来源 URL，正文没有变化，那么可能只需要更新 Metadata。

如果修改了维修步骤，就需要重新生成受影响内容的 Embedding。

如果删除了整份手册，就需要清理它对应的全部 Chunk。

所以不能把所有业务变化都当成 Insert，否则会产生重复数据和过期数据。

**说话人1：问题7，数据库中的一条业务记录，经过文档转换和切块后，为什么可能对应多个向量记录？**

**说话人1：答：** 因为一条业务记录可能包含大量文本，而一个 Chunk 通常只承载有限长度的内容。

例如，一条设备维修记录包含故障现象、原因分析、维修步骤、检测结果和注意事项，经过切块可能形成 5 个 Chunk。

每个 Chunk 都需要单独生成 Embedding，才能进行向量检索。

因此，业务记录与向量记录通常不是一对一，而是一对多关系。

**说话人1：问题8，如何建立业务主键、文档 ID、Chunk ID 和向量记录 ID 之间的映射关系？**

**说话人1：答：** 首先要区分它们各自的职责。

- `business_id`：原始业务记录的主键。
- `document_id`：知识库中的文档标识。
- `chunk_id`：文档内部某个 Chunk 的标识。
- `vector_id`：向量存储记录的主键。

例如，设备维修记录 `business_id=1001` 转换成 `document_id=DOC-1001`，再切分成多个 Chunk，每个 Chunk 有自己的 `chunk_id` 和 `vector_id`。

可以设计如下关系：

`business_id → document_id → chunk_id → vector_id`

如果采用 PostgreSQL + pgvector，也可以让 Chunk 记录和向量记录共用同一张表，以 `chunk_id` 作为主键，避免不必要的 ID 映射层。

**说话人1：问题9，为什么每个 Chunk 都应该保留稳定的来源标识和必要的业务元数据？**

**说话人1：答：** 因为 Chunk 不能成为没有来源的孤立文本。

检索到一个维修步骤时，我们需要知道它来自哪份手册、哪个设备型号、哪个文档版本，以及原文中的哪个章节。

这些信息可以用于：

1. 过滤特定设备型号的知识。
2. 追溯原始文档。
3. 更新或删除某份文档的全部 Chunk。
4. 判断检索结果是否属于当前有效版本。
5. 展示来源和引用依据。

所以每个 Chunk 至少应该保留 `document_id`、`document_version`、`chunk_id`、`device_model` 等必要信息。

**说话人1：问题10，什么是知识库数据的生命周期？新增、更新、删除和重建分别处于什么阶段？**

**说话人1：答：** 知识库生命周期，就是从原始知识进入系统，到最终被更新或清理的完整过程。

可以分成四类操作：

- 新增：原始文档首次进入知识库，完成解析、切块和向量化。
- 更新：原始内容发生变化，重新处理并发布新版本。
- 删除：文档失效或被移除，停止检索并清理对应数据。
- 重建：根据原始文档重新生成 Chunk 和 Embedding，恢复或迁移向量索引。

新增、更新和删除属于日常数据维护；重建通常用于数据修复、模型升级或索引迁移。

## **二、新增数据如何映射到向量库**

**说话人1：问题11，当一份新的设备维修手册进入知识库时，应该经过哪些处理步骤才能写入向量库？**

**说话人1：答：** 我会把它设计成一条完整的数据处理流水线：

1. 接收原始文件，记录文件来源和业务标识。
2. 生成或确定 `document_id`。
3. 解析 PDF、Word 等文件格式。
4. 清洗无效文本，检查文档质量。
5. 根据文档结构进行 Chunk 切分。
6. 为每个 Chunk 生成稳定标识。
7. 调用 EmbeddingModel 生成向量。
8. 将文本、向量和 Metadata 写入 pgvector。
9. 校验写入结果和 Chunk 数量。
10. 全部通过后，将文档标记为已发布。

关键是不能只关注向量是否写入，还要关注文档版本、处理状态和数据完整性。

**说话人1：问题12，为什么新增文档需要先进行格式解析、内容清洗和质量检测？**

**说话人1：答：** 因为原始文件不一定适合直接用于 RAG。

PDF 可能存在乱码、页眉页脚重复、跨页表格、文本顺序错乱等问题。

如果不做解析和清洗，这些噪声也会进入 Chunk，最终生成质量较差的 Embedding。

质量检测还需要发现空文档、重复文档、错误设备型号、无效维修记录等问题。

所以应该先保证输入知识的质量，再进行切块和向量化，不能把垃圾数据直接写入向量库。

**说话人1：问题13，为什么必须先确定文档 ID，再执行 Chunk 切分和向量化？**

**说话人1：答：** 因为后续所有 Chunk 都需要归属于某个明确的文档。

如果先切块再确定文档 ID，就会出现 Chunk 无法稳定关联原始文档的问题。

提前确定 `document_id`，可以让每个 Chunk 在生成时就携带文档标识，后续方便执行更新、删除、版本管理和一致性对账。

文档 ID 应该在文档首次登记时生成，并在同一逻辑文档的生命周期内保持稳定。

**说话人1：问题14，如何为同一份文档生成稳定且可追溯的 Chunk ID？**

**说话人1：答：** 一种简单方案是使用文档 ID、文档版本和 Chunk 序号组合生成。

例如：

`DOC-1001-V3-CHUNK-0001`

这种方式可追溯，也容易定位具体版本。

如果希望使用确定性 ID，也可以对 `document_id + document_version + chunk_index` 进行 SHA-256 哈希，再取合适长度作为标识。

不过要注意，Chunk 序号稳定不代表语义内容稳定。文档重新切分后，Chunk 的位置和内容可能改变，因此版本号也应该参与 ID 生成。

**说话人1：问题15，文档切分后，为什么每个 Chunk 都需要保存所属文档 ID？**

**说话人1：答：** 因为文档 ID 是批量管理 Chunk 的关键。

当某份维修手册更新或删除时，系统可以通过 `document_id` 找到它对应的全部 Chunk。

如果没有这个字段，就很难准确判断某条向量属于哪份文档，也无法可靠地执行批量更新、删除和数据对账。

所以 `document_id` 是文档和 Chunk 之间的重要关联键。

**说话人1：问题16，EmbeddingModel 如何将 Chunk 文本转换为向量？**

**说话人1：答：** EmbeddingModel 本质上是一个文本向量化模型。

系统将 Chunk 文本输入模型，模型经过分词、编码和神经网络计算，输出一个固定维度的浮点数数组。

例如：

`"设备运行过程中出现异常振动"`

经过模型处理后，可能得到一个 1024 维向量。

这个向量表达的是文本在模型语义空间中的特征，后续可以通过余弦相似度、内积或欧氏距离等方式进行相似度检索。

需要注意，向量不是原文的压缩副本，也不能直接还原成原始文本。

**说话人1：问题17，为什么向量维度必须与向量库中的字段定义保持一致？**

**说话人1：答：** 因为向量数据库需要按照固定维度存储和计算向量。

假设 pgvector 中定义的是 `vector(1024)`，但 Embedding 模型输出 768 维，就无法正常写入这个字段。

即使维度相同，如果使用了不同模型，向量空间也可能完全不同，不能简单地混合检索。

所以系统必须明确 Embedding 模型、向量维度和距离计算方式，并在写入时进行校验。

**说话人1：问题18，如何将 Chunk 文本、Embedding 向量和 Metadata 一起写入 pgvector？**

**说话人1：答：** 可以使用 PostgreSQL 表保存三类核心数据。

例如：

```
CREATE TABLE knowledge_chunk (
    chunk_id          VARCHAR(128) PRIMARY KEY,
    document_id       VARCHAR(128) NOT NULL,
    document_version  BIGINT NOT NULL,
    chunk_index       INTEGER NOT NULL,
    content           TEXT NOT NULL,
    metadata          JSONB,
    embedding         VECTOR(1024),
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    UNIQUE (document_id, document_version, chunk_index)
);
```

写入时，将 Chunk 文本保存到 `content`，Embedding 保存到 `embedding`，来源、设备型号、章节等信息保存到 `metadata` 或独立字段。

在 Spring AI 1.1.8 中，可以通过 `VectorStore` 的 `add` 操作写入 Document，由具体的 PgVectorStore 实现完成向量存储。

不过生产系统还需要结合文档版本、发布状态和事务策略，不能只依赖简单的 `add`。

**说话人1：问题19，如果一份文档包含多个 Chunk，如何保证这些 Chunk 全部成功入库？**

**说话人1：答：** 首先要明确文档级别的发布原则：不能只写入一部分 Chunk，就把整份文档标记为已发布。

如果所有 Chunk 已经完成向量化，并且写入操作都在同一个 PostgreSQL 事务中，可以利用事务保证整批写入要么全部提交，要么全部回滚。

如果向量化和写入被拆成多个批次，就需要增加处理状态、批次记录和校验机制。

例如，预期有 100 个 Chunk，最终只成功写入 98 个，那么这份文档就不能进入已发布状态，应该重试失败部分，或者清理未完成版本后重新处理。

**说话人1：问题20，如果文档向量化过程中部分 Chunk 写入失败，应该如何处理？**

**说话人1：答：** 要根据失败发生的位置分别处理。

如果 Embedding 调用失败，应该保留失败任务和错误信息，重试失败的 Chunk。

如果向量写入失败，应该通过幂等键重新执行写入，避免重复生成记录。

如果采用文档版本发布机制，那么失败版本不能覆盖当前已发布版本。

例如，旧版本 V1 正常提供检索，新版本 V2 处理到一半失败，那么继续让 V1 可检索，等 V2 完整成功后再切换。

**说话人1：问题21，如何避免同一份文档重复导入，产生重复 Chunk 和重复向量？**

**说话人1：答：** 可以从三个层面处理。

第一，使用稳定的 `document_id` 识别同一份逻辑文档。

第二，计算原始内容的 SHA-256 哈希，判断内容是否已经处理过。

第三，为 Chunk 设置业务唯一约束，例如：

`UNIQUE(document_id, document_version, chunk_index)`

如果相同文档、相同版本重复提交，就可以识别为重复任务，而不是再次创建一批向量。

需要注意，文件名相同不代表内容相同，文件名不能作为可靠的内容去重依据。

**说话人1：问题22，什么是 Upsert？它与普通 Insert 有什么区别？**

**说话人1：答：** Insert 是插入一条新记录。如果主键或唯一键已经存在，通常会发生唯一约束冲突。

Upsert 是 Insert 或 Update 的组合：如果记录不存在就插入，存在就按照指定规则更新。

在 PostgreSQL 中，可以使用：

```
INSERT INTO knowledge_chunk (
    chunk_id, document_id, document_version,
    chunk_index, content, embedding
)
VALUES (
    'DOC-1001-V1-CHUNK-0001',
    'DOC-1001',
    1,
    1,
    '设备异常振动的维修说明',
    '[...]'
)
ON CONFLICT (chunk_id)
DO UPDATE SET
    content = EXCLUDED.content,
    embedding = EXCLUDED.embedding;
```

这里的 `ON CONFLICT` 就是 PostgreSQL 实现 Upsert 的常见方式。

但 Upsert 不等于自动实现完整的数据同步，它只解决单条记录冲突时的写入行为。

**说话人1：问题23，使用 Upsert 实现新增数据写入时，应该选择什么业务唯一键？**

**说话人1：答：** 应该选择能够唯一标识某个版本中某个 Chunk 的键。

例如：

`document_id + document_version + chunk_index`

也可以将这几个字段组合后生成确定性 `chunk_id`，并设置唯一约束。

这样同一文档版本中的同一个 Chunk 重复处理时，就不会重复插入。

如果只使用 `document_id`，一份文档的所有 Chunk 就会发生冲突；如果只使用 `chunk_index`，不同文档之间又会产生冲突。

**说话人1：问题24，为什么不能直接使用随机生成的向量记录 ID 作为重复入库判断依据？**

**说话人1：答：** 因为随机 ID 每次生成都可能不同。

同一个 Chunk 第一次导入生成 `UUID-A`，第二次导入又生成 `UUID-B`。数据库只会认为这是两条不同记录，无法识别它们其实来自同一份文档的同一段内容。

所以随机 ID 可以作为数据库主键，但不能单独承担业务幂等判断。

更合理的做法是使用稳定的业务唯一键，或者通过文档 ID、版本号和 Chunk 标识生成确定性 ID。

## **三、更新数据如何映射到向量库**

**说话人1：问题25，当设备维修手册内容发生修改时，为什么不能只更新原始文档而不处理旧向量？**

**说话人1：答：** 因为旧向量仍然对应修改之前的文本。

例如，维修手册原来要求将设备压力调整到 8 MPa，更新后要求调整到 9 MPa。如果只更新原始文件，而没有更新向量库，检索仍然可能返回 8 MPa 的旧知识。

这就造成原始数据和检索数据不一致。

因此，更新原文时，必须同步处理旧 Chunk 和旧 Embedding，确保检索结果对应当前有效的知识版本。

**说话人1：问题26，为什么原文修改后，原有 Chunk 的文本内容和 Embedding 可能已经失效？**

**说话人1：答：** 因为 Embedding 是根据特定文本计算出来的。

原文发生修改后，Chunk 的语义可能发生变化，原来的向量就不能准确表示新内容。

例如，原来写的是“检查冷却系统”，修改后变成“检查冷却系统，并确认冷却液流量不低于规定值”。

修改后的内容增加了重要条件，原来的 Embedding 没有包含这部分语义。

因此，只要 Chunk 的有效文本发生变化，通常就应该重新生成 Embedding。

**说话人1：问题27，什么是增量更新？它与全量重建有什么区别？**

**说话人1：答：** 增量更新是只处理发生变化的数据，而不是重新处理整个知识库。

例如，知识库有 10 万个 Chunk，只有一份维修手册中的 3 个 Chunk 发生变化，那么增量更新只需要处理受影响的 Chunk。

全量重建则是重新读取全部有效文档，重新解析、切块和生成 Embedding，再建立新的向量数据集。

增量更新成本较低，适合日常维护；全量重建成本较高，通常用于 Embedding 模型迁移、切块策略调整、数据损坏修复等场景。

**说话人1：问题28，如何判断一份文档是否真正发生了内容变更？**

**说话人1：答：** 可以对规范化后的文档内容计算哈希值，再和上一次处理成功的哈希值比较。

如果哈希相同，说明参与计算的内容没有变化，可以跳过重复处理。

如果哈希不同，就说明内容发生了变化，需要进一步判断哪些 Chunk 受到了影响。

不过，哈希比较之前要先确定规范化规则。例如，是否忽略空白字符、页眉页脚、文件元数据等。否则，仅仅修改 PDF 的创建时间，也可能导致文件二进制哈希变化。

**说话人1：问题29，什么是内容哈希（Content Hash）？如何利用 SHA-256 判断文档内容是否变化？**

**说话人1：答：** 内容哈希就是将一段内容通过哈希算法转换成固定长度的摘要。

SHA-256 会生成 256 位摘要，通常表示为 64 个十六进制字符。

Java 21 可以使用 JDK 自带的 `MessageDigest`：

```
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.HexFormat;

public class ContentHash {

    public static String sha256(String content) throws Exception {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");

        byte[] hash = digest.digest(
                content.getBytes(StandardCharsets.UTF_8)
        );

        return HexFormat.of().formatHex(hash);
    }
}
```

将新文档的规范化文本计算出 SHA-256，再与数据库中保存的旧哈希比较。

相同则认为内容未发生变化；不同则触发后续更新流程。

需要注意，哈希只能判断内容是否不同，不能告诉我们具体修改了哪个段落。

**说话人1：问题30，为什么应该区分文件元数据变化、文档内容变化和 Embedding 模型变化？**

**说话人1：答：** 因为这三种变化影响的范围不同。

第一，文件元数据变化，例如文件名、来源 URL 或上传人变化，通常只需要更新 Metadata。

第二，文档内容变化，例如维修步骤或设备参数变化，需要重新解析受影响的内容、切块并生成 Embedding。

第三，Embedding 模型变化，即使原文完全没有变化，也可能需要重新生成全部向量，因为新旧模型的向量空间可能不同。

如果不区分这三种变化，就容易出现不必要的重复向量化，或者漏掉必须执行的向量更新。

**说话人1：问题31，如果只修改文档标题、来源地址或业务标签，是否一定需要重新生成 Embedding？**

**说话人1：答：** 不一定。

如果只修改来源地址、上传人、业务标签等 Metadata，而 Chunk 正文没有变化，通常只需要更新对应的 Metadata。

如果修改的是标题，就要看标题是否参与 Chunk 正文和 Embedding 计算。

例如，标题原来是“设备 A 冷却系统维修”，修改为“设备 B 冷却系统维修”，如果标题已经拼接进 Chunk 文本，那么语义发生变化，就应该重新生成 Embedding。

所以关键不是字段名称，而是判断这个字段是否参与了向量化文本的构造。

**说话人1：问题32，如果只修改文档中的一个段落，应该重新处理整份文档还是只处理受影响的 Chunk？**

**说话人1：答：** 理想情况下可以增量处理受影响的 Chunk，但不能简单地认为只修改一个段落就只重新生成一个 Chunk。

因为切块是有边界的。修改一个段落后，可能影响前后 Chunk 的内容、重叠区域、序号和语义关系。

如果使用固定长度切块，修改位置附近的多个 Chunk 都可能需要重新计算。

如果使用按章节和段落切块，且结构边界稳定，那么更容易只重新处理受影响的章节。

因此，是否增量处理取决于切块策略是否能可靠地定位和识别受影响范围。

**说话人1：问题33，如何判断修改后的 Chunk 与旧 Chunk 是否属于同一份知识内容？**

**说话人1：答：** 需要区分业务身份和内容身份。

业务身份可以通过 `document_id`、章节 ID、段落 ID 等确定。

内容身份可以通过规范化文本的 SHA-256 判断。

例如，同一份维修手册的第三章发生修改，章节 ID 仍然是 `CHAPTER-03`，说明它们属于同一个业务位置；但新旧内容的哈希不同，说明内容已经发生变化。

工程上可以将 `document_id + section_id + content_hash` 作为辅助识别依据。

不过，文档结构变化后，章节 ID 也可能改变，因此不能只依赖单一字段判断。

**说话人1：问题34，当新版本文档重新切块后，旧 Chunk 的 ID 是否应该继续沿用？为什么？**

**说话人1：答：** 通常不应该直接沿用旧版本 Chunk ID。

因为新版本可能改变了文本内容、切块边界和 Chunk 数量。如果继续沿用旧 ID，可能导致新旧内容覆盖关系不清楚，也不利于版本追踪。

更合理的方式是将文档版本纳入 Chunk ID，例如：

- `DOC-1001-V1-CHUNK-0001`
- `DOC-1001-V2-CHUNK-0001`

这样可以明确区分不同版本的 Chunk。

对于确实没有变化的内容，可以通过内容哈希识别并复用已有 Embedding 计算结果，但仍然需要保证新版本的数据归属和发布关系正确。

**说话人1：问题35，为什么更新文档时需要先生成新版本 Chunk，再处理旧版本 Chunk？**

**说话人1：答：** 这是为了避免更新过程中出现知识不可用。

假设当前 V1 正在为线上 RAG 提供检索，如果先删除 V1，再生成 V2，那么在 V2 处理完成之前，用户就可能检索不到这份文档。

更可靠的流程是：

1. 保留 V1 的检索能力。
2. 生成 V2 的 Chunk 和 Embedding。
3. 校验 V2 的数据完整性。
4. 将 V2 标记为已发布。
5. 切换当前有效版本。
6. 最后清理 V1。

这样即使 V2 生成失败，V1 仍然可以继续提供服务。

**说话人1：问题36，如何避免更新过程中出现新旧 Chunk 同时可检索或全部不可检索的状态？**

**说话人1：答：** 可以使用文档版本和发布状态控制检索范围。

例如，文档表中保存 `active_version=1`，V1 是当前有效版本。V2 生成完成后，先确保所有 Chunk 已经写入，再通过数据库事务将 `active_version` 更新为 2。

检索时只允许查询当前有效版本。

如果文档主表和 Chunk 表在同一个 PostgreSQL 实例中，可以在一个事务中完成版本切换，避免其他事务看到不完整的切换结果。

需要注意，所有检索 SQL 都必须遵循有效版本过滤规则。如果有缓存、异步副本或独立向量数据库，还要考虑它们各自的同步延迟。

**说话人1：问题37，什么是版本化更新？如何通过&#x20;**`document_version`**&#x20;管理文档的多个版本？**

**说话人1：答：** 版本化更新就是不直接覆盖旧数据，而是为每次有效变更创建新的文档版本。

例如：

| document_id | document_version | 状态   |
| ----------- | ---------------- | ------ |
| DOC-1001    | 1                | 已归档 |
| DOC-1001    | 2                | 已发布 |
| DOC-1001    | 3                | 处理中 |

每个 Chunk 都保存所属的 `document_id` 和 `document_version`。

这样可以追踪每次修改的内容，也可以在新版本失败时回退到旧版本。

在实际检索时，应通过文档主表的当前有效版本，或可靠维护的发布状态，筛选出可以参与检索的 Chunk。

**说话人1：问题38，当文档更新失败时，如何保证旧版本知识仍然可用？**

**说话人1：答：** 核心原则是先构建新版本，再发布新版本，不要提前破坏旧版本。

例如，V1 已经发布，V2 在调用 Embedding API 时发生超时。

系统应该把 V2 标记为失败，记录失败原因，并根据策略重试；同时保持 V1 的发布状态不变。

只有 V2 的 Chunk 全部写入并通过校验后，才允许切换当前有效版本。

这样就实现了更新失败时的服务可用性保障。

**说话人1：问题39，如何设计文档更新的状态机，例如待处理、处理中、已发布和失败？**

**说话人1：答：** 可以设计四个基本状态：

- `PENDING`：变更任务已经创建，等待处理。
- `PROCESSING`：正在解析、切块、向量化或写入。
- `PUBLISHED`：新版本已经完成校验，并且正式参与检索。
- `FAILED`：处理失败，需要记录原因并等待重试或人工处理。

状态转换可以设计为：

```
PENDING → PROCESSING → PUBLISHED
                 ↓
               FAILED
                 ↓
             PROCESSING
```

这里还要区分文档版本状态和处理任务状态。一个文档可以有 V1 已发布，同时 V2 处于处理中。

不能因为 V2 处理失败，就把整个文档标记为不可用。

**说话人1：问题40，为什么文档更新应该具备幂等性？如何保证同一个变更事件重复执行不会产生错误？**

**说话人1：答：** 因为分布式系统中，消息重复投递和任务重试是很常见的。

例如，同一个维修手册更新事件因为消费者超时，被消息队列投递了两次。如果每次都生成一批新的 Chunk，就会造成重复向量。

可以通过以下方式实现幂等：

1. 每个变更事件有唯一 `event_id`。
2. 每个文档版本有唯一版本号。
3. Chunk 使用确定性业务唯一键。
4. 数据库设置唯一约束。
5. 消费者记录已经成功处理的事件。
6. 对重复事件直接返回已处理结果，或安全地重新执行 Upsert。

幂等的目标是：同一个事件执行一次或多次，最终数据状态都应该一致。

## **四、删除数据如何映射到向量库**

**说话人1：问题41，当原始文档被删除时，为什么必须同时考虑其全部 Chunk 和向量记录？**

**说话人1：答：** 因为一份原始文档可能对应多个 Chunk，每个 Chunk 又对应一条向量记录。

如果只删除原始文档，而不删除或停用 Chunk，向量检索仍然可能返回这份文档的旧知识。

例如，一份已经废弃的设备维修手册仍然保留在向量库中，模型就可能根据它给出已经不适用的维修建议。

所以删除文档时，必须根据 `document_id` 找到对应的全部版本和 Chunk，执行逻辑删除或物理清理。

**说话人1：问题42，如何通过&#x20;**`document_id`**&#x20;找到一份文档对应的全部向量记录？**

**说话人1：答：** 最简单的方法就是在 Chunk 表中保存 `document_id`，并建立索引。

例如：

```
CREATE INDEX idx_chunk_document_id
ON knowledge_chunk (document_id);
```

查询时：

```
SELECT chunk_id, document_version, content
FROM knowledge_chunk
WHERE document_id = 'DOC-1001';
```

如果只想查询当前有效版本，还需要结合文档主表中的当前版本或发布状态进行过滤。

这样就可以定位某份文档对应的全部 Chunk 和向量记录。

**说话人1：问题43，什么是级联删除？为什么不应该默认认为删除 PostgreSQL 业务记录就会自动删除 pgvector 中的向量？**

**说话人1：答：** 级联删除是指删除父记录时，数据库根据外键约束自动删除关联的子记录。

例如，文档主表是父表，Chunk 表是子表，可以通过外键设置 `ON DELETE CASCADE`。

但是，级联删除必须建立在真实的数据库外键关系上。

如果业务表和向量表没有外键约束，或者向量数据存放在独立数据库中，删除业务记录不会自动删除向量。

即使使用同一个 PostgreSQL 实例，也不能因为它们都在 PostgreSQL 中，就认为它们天然存在级联关系。

另外，生产环境是否使用物理级联删除，还要考虑版本留存、审计和误删恢复需求。

**说话人1：问题44，如何区分逻辑删除和物理删除？**

**说话人1：答：** 逻辑删除是改变数据状态，让系统认为这条数据已经失效，但数据库中仍然保留记录。

物理删除则是真正执行 `DELETE`，将记录从表中删除。

例如，维修手册被废弃时，可以先设置 `deleted_at`，停止它参与检索；经过保留期限和审计确认后，再执行物理清理。

逻辑删除有利于恢复和审计，物理删除可以释放存储空间，但恢复成本更高。

**说话人1：问题45，什么是软删除？如何通过&#x20;**`deleted_at`**&#x20;或状态字段控制知识是否参与检索？**

**说话人1：答：** 软删除就是不直接删除数据库记录，而是设置一个删除标记。

例如：

```
ALTER TABLE knowledge_chunk
ADD COLUMN deleted_at TIMESTAMPTZ;
```

正常记录的 `deleted_at` 为 NULL；被删除的记录则设置为删除时间。

检索时：

```
SELECT chunk_id, content
FROM knowledge_chunk
WHERE deleted_at IS NULL;
```

也可以使用 `status` 字段，例如 `ACTIVE`、`DELETED`。

这样可以保留原始记录，同时让检索只访问有效知识。

**说话人1：问题46，为什么软删除的向量必须在检索阶段被过滤？**

**说话人1：答：** 因为软删除只是改变了数据状态，并没有真正删除向量。

如果向量检索没有过滤 `deleted_at` 或状态字段，已经失效的知识仍然可能进入 TopK。

例如，一份维修手册已经被标记为废弃，但它的 Chunk 仍然具有很高的向量相似度。如果不做过滤，系统仍然可能优先召回它。

因此，软删除必须与检索过滤配套实施。

在 Spring AI 1.1.8 中，可以结合 VectorStore 的 Metadata 过滤能力实现相应约束；如果需要强制过滤、复杂版本条件或数据库级别的数据隔离，也可以使用自定义检索 SQL。

需要强调：不能只在 Prompt 中告诉模型忽略旧数据，应该在检索数据层面就排除失效记录。

**说话人1：问题47，如果文档删除成功，但向量删除失败，会造成什么数据一致性问题？**

**说话人1：答：** 这会形成孤儿向量，也就是原始文档已经不存在或已经失效，但对应的向量仍然留在向量库中。

它可能造成三个问题：

1. 过期知识仍然被召回。
2. 向量存储中积累无效数据。
3. 后续无法准确追溯和维护这些记录。

因此，删除不能只依赖一次数据库操作，还需要删除任务状态、失败重试和定期对账机制。

**说话人1：问题48，如何通过删除事件和重试机制，最终清理已经失效的向量记录？**

**说话人1：答：** 可以将删除操作设计为一个可靠的异步任务。

首先，业务系统将文档标记为已删除，并记录删除事件。

消费者收到事件后，根据 `document_id` 查询全部相关 Chunk，执行软删除或物理删除。

如果删除失败，就记录错误原因、失败次数和下次重试时间。

对于持续失败的任务，可以进入死信队列或人工处理队列。

同时，定期对账检查已删除文档是否仍然存在有效 Chunk。

这样即使第一次删除失败，也能够通过重试和对账最终清理。

**说话人1：问题49，当文档被误删除时，如何利用原始文件、版本记录和备份恢复知识？**

**说话人1：答：** 如果采用软删除，恢复通常比较简单，只需要将文档和对应 Chunk 的状态恢复为有效，并确认当前版本关系正确。

如果已经物理删除，就需要依赖原始文件、版本记录或数据库备份重新恢复。

例如，从对象存储中取回原始维修手册，重新解析、切块和向量化，写入新的有效版本。

如果使用 PostgreSQL，还可以结合数据库备份和 WAL 归档实现时间点恢复。

所以重要知识不能只保留一份向量副本，原始文档、版本记录和备份都应该有明确的保留策略。

**说话人1：问题50，如果一份文档被多个知识库或业务场景引用，删除时应该如何处理引用关系？**

**说话人1：答：** 不能简单地因为一个知识库取消引用，就直接删除底层文档和全部向量。

例如，一份设备安全操作手册同时被设备维修知识库、客户服务知识库和培训知识库引用。

如果维修知识库不再使用这份手册，但培训知识库仍然需要它，那么就不能直接删除原始文档。

可以设计文档与知识库之间的多对多关系，例如：

- `document`：保存文档本身。
- `knowledge_base`：保存知识库。
- `document_knowledge_base`：保存文档引用关系。

删除某个知识库中的引用时，只删除对应关联关系。

只有当文档已经没有任何有效引用，并且满足保留策略时，才考虑删除底层文档和向量数据。

## **五、数据一致性、事务与可靠性**

**说话人1：问题51，为什么 PostgreSQL 业务表与向量表之间的更新可能出现部分成功？**

**说话人1：答：** 因为业务更新和向量更新可能是两个独立操作。

例如，系统先更新维修手册业务表，更新成功；随后调用 Embedding API 失败，向量表没有更新。

最终就会出现原始文档已经是新版本，但向量库仍然保存旧版本的情况。

如果两个操作没有统一的事务或可靠的异步处理机制，就可能出现部分成功。

所以生产系统必须考虑事务边界、失败补偿、重试和数据对账。

**说话人1：问题52，如果业务数据和向量数据存储在同一个 PostgreSQL 实例中，能否利用数据库事务保证两者一致？**

**说话人1：答：** 可以，但要区分哪些操作能够放进同一个事务。

例如，业务表更新和已经生成好的 Chunk、Embedding 写入同一个 PostgreSQL 实例，可以使用 Spring 事务管理器，在同一个数据库事务中提交。

如果其中一个操作失败，整个事务就可以回滚。

但是，Embedding API 调用不是 PostgreSQL 事务的一部分，数据库无法自动回滚外部模型服务已经完成的计算。

因此，比较合理的方式是：

1. 在事务外完成文档解析和 Embedding 计算。
2. 在事务内写入新版本 Chunk 和向量。
3. 校验数据并切换发布版本。
4. 事务提交后，再执行旧版本清理。

这样既缩短了数据库事务时间，也避免了部分数据提前发布。

**说话人1：问题53，当向量化调用外部 Embedding API 时，为什么不应该长时间占用数据库事务？**

**说话人1：答：** 因为外部 API 的响应时间不可控。

例如，Embedding 服务可能发生网络延迟、限流或超时。如果在数据库事务中调用外部 API，事务就会长时间占用连接和数据库资源。

可能造成：

- 数据库连接池被占满。
- 行锁或表锁持有时间增加。
- 其他事务等待时间变长。
- 数据库吞吐量下降。
- 事务超时和死锁风险增加。

因此，应该尽量将外部调用放在事务之外，完成计算后再使用较短的事务写入数据库。

**说话人1：问题54，什么是双写问题？为什么同时写业务数据库和独立向量数据库容易出现数据不一致？**

**说话人1：答：** 双写问题就是一个业务操作需要同时写入两个独立的数据系统。

例如，设备维修手册更新后，系统既要更新 MySQL 业务库，又要更新 Milvus 向量库。

如果业务库写入成功，但 Milvus 写入失败，就会出现两边数据不一致。

反过来，如果向量库成功、业务库失败，也可能出现没有业务依据的向量数据。

两个数据库通常没有共享的本地事务，简单地先写一个、再写另一个，无法保证原子性。

所以需要使用 Outbox、消息队列、幂等消费、重试和对账等机制实现最终一致性。

**说话人1：问题55，什么是 Transactional Outbox Pattern？它如何保证业务数据变更事件不会轻易丢失？**

**说话人1：答：** Transactional Outbox，也叫事务发件箱模式。

它的核心思想是：业务数据变更和变更事件记录，写入同一个数据库事务。

例如，用户更新了一份维修手册，系统在同一个 PostgreSQL 事务中：

1. 更新文档业务表。
2. 插入一条 Outbox 事件。
3. 提交事务。

如果事务失败，两者一起回滚；如果事务成功，Outbox 事件就已经可靠地保存在数据库中。

然后由后台任务或 CDC 工具读取 Outbox，将事件发送到消息队列。

这样就避免了业务更新成功、但事件还没发送出去时服务突然宕机，导致变更事件丢失的问题。

注意，Outbox 解决的是业务事务与事件记录之间的原子性问题，不意味着消息只会投递一次。消费者仍然必须具备幂等能力。

**说话人1：问题56，什么是最终一致性？为什么 RAG 知识库可以采用最终一致性，但必须定义可接受的同步延迟？**

**说话人1：答：** 最终一致性是指多个数据系统在某个时刻可能存在短暂差异，但经过异步同步、重试和修复后，最终能够达到一致状态。

例如，一份新维修手册在 10:00 上传，业务数据库已经保存成功，但向量化任务到 10:02 才完成。

这两分钟内，用户可能还检索不到这份新知识。

对于普通知识库，这种短暂延迟通常可以接受，但必须明确同步 SLA。

例如，可以规定正常情况下 99% 的文档在 2 分钟内完成发布。

不过，对于涉及设备安全、紧急故障处理和高风险维修参数的知识，不能简单地认为最终一致性就足够。应该结合业务风险设计发布控制、人工审核和旧版本失效策略。

**说话人1：问题57，如何使用消息队列实现文档变更事件的异步处理？**

**说话人1：答：** 可以将文档变更设计为事件，再交给消费者异步处理。

例如，文档更新后产生：

```
{
  "eventId": "EVT-10001",
  "eventType": "DOCUMENT_UPDATED",
  "documentId": "DOC-1001",
  "documentVersion": 2,
  "contentHash": "sha256-value",
  "occurredAt": "2026-11-14T10:00:00+08:00"
}
```

消费者收到事件后，根据 `documentId` 查询原始文档，执行解析、清洗、切块、Embedding 和向量入库。

处理成功后更新任务状态；处理失败则根据策略重试。

这样业务请求不需要等待所有 Chunk 完成向量化，提高了系统响应能力，也便于横向扩展消费者。

**说话人1：问题58，如何设计事件 ID、幂等键、重试次数和死信队列，避免重复消费与永久丢失？**

**说话人1：答：** 需要从消息生产端和消费端分别保证可靠性。

生产端：

- 每个事件生成唯一 `event_id`。
- Outbox 记录事件内容和发送状态。
- 发送失败后可以重新投递。

消费端：

- 使用 `event_id` 作为消费幂等键。
- 保存已处理事件记录。
- 使用数据库唯一约束防止重复处理。
- 记录失败次数和错误原因。
- 超过最大重试次数后进入死信队列。

例如，同一个事件最多自动重试 5 次，仍然失败就转入死信队列，由人工排查或通过专门的修复任务处理。

这里要注意，消息确认时机也很重要：只有在消费者完成可靠处理后，才应该确认消息，不能消息刚收到就直接 ACK。

**说话人1：问题59，如何处理乱序事件？例如旧版本更新事件晚于新版本更新事件到达？**

**说话人1：答：** 不能简单地按照消息到达顺序覆盖数据，因为消息队列中的事件可能重复或乱序。

例如：

- V2 更新事件先到达。
- V3 更新事件后到达。
- 由于网络延迟，V2 的另一次重试又晚于 V3 到达。

如果消费者无条件执行 Upsert，旧版本就可能覆盖新版本。

正确做法是使用文档版本号进行比较，只允许符合当前处理规则的版本进入发布流程。

如果收到的事件版本低于当前有效版本，就应该拒绝它直接发布，并记录为过期事件。

对于并行处理，还需要控制同一文档的版本发布顺序，不能仅靠消息队列的全局消费顺序保证一致性。

**说话人1：问题60，如何通过版本号或更新时间戳阻止旧事件覆盖新版本向量？**

**说话人1：答：** 最好优先使用单调递增的业务版本号，而不是只依赖更新时间戳。

例如，当前有效版本是 V3，收到 V2 事件时，就不允许它覆盖 V3。

数据库更新可以加入版本条件：

```
UPDATE knowledge_document
SET active_version = :new_version
WHERE document_id = :document_id
  AND active_version < :new_version;
```

实际使用时还应该校验新版本已经完成向量写入，并且处理状态满足发布条件。

更新时间戳可以辅助判断事件新旧，但可能受到时钟偏差、时间精度和相同时间戳等问题影响。

因此，业务版本号通常比单纯时间戳更适合控制文档更新顺序。

## **六、生产级数据同步与工程实践**

**说话人1：问题61，如何设计一张文档主表，记录文档 ID、版本号、内容哈希、处理状态和更新时间？**

**说话人1：答：** 文档主表负责管理文档的身份、版本和生命周期。

可以设计：

```
CREATE TABLE knowledge_document (
    document_id       VARCHAR(128) PRIMARY KEY,
    business_id       VARCHAR(128),
    document_name     VARCHAR(512) NOT NULL,
    document_version  BIGINT NOT NULL DEFAULT 1,
    content_hash      VARCHAR(64),
    embedding_model   VARCHAR(128),
    status            VARCHAR(32) NOT NULL,
    deleted_at        TIMESTAMPTZ,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    UNIQUE (business_id, document_id)
);
```

这里需要注意，实际生产系统通常还会将文档主表和文档版本表拆开。

主表负责记录文档当前状态和当前有效版本；版本表负责保存每次变更的哈希、处理状态、模型版本和发布时间。

这样更方便回溯历史，也能支持新版本失败时继续使用旧版本。

**说话人1：问题62，如何设计 Chunk 元数据，使其能够追溯到原始文档、文档版本和具体位置？**

**说话人1：答：** Chunk Metadata 应该至少包含以下信息：

| 字段               | 含义           |
| ------------------ | -------------- |
| `chunk_id`         | Chunk 唯一标识 |
| `document_id`      | 所属文档       |
| `document_version` | 文档版本       |
| `chunk_index`      | Chunk 顺序     |
| `section_id`       | 所属章节       |
| `page_number`      | 原始页码       |
| `device_model`     | 设备型号       |
| `fault_code`       | 故障代码       |
| `content_hash`     | Chunk 内容哈希 |
| `embedding_model`  | 使用的向量模型 |

在制造设备知识库中，还可以记录知识类型，例如维修手册、故障案例、技术参数和安全规范。

这些 Metadata 不仅用于展示来源，还可以用于过滤、更新、删除、版本管理和审计。

**说话人1：问题63，如何设计文档变更事件，使新增、更新和删除都能够被统一处理？**

**说话人1：答：** 可以设计统一的文档变更事件结构，通过 `eventType` 区分不同操作。

例如：

```
{
  "eventId": "EVT-10001",
  "eventType": "DOCUMENT_UPDATED",
  "documentId": "DOC-1001",
  "documentVersion": 3,
  "contentHash": "sha256-value",
  "occurredAt": "2026-11-14T10:00:00+08:00",
  "source": "MANUAL_IMPORT"
}
```

事件类型可以包括：

- `DOCUMENT_CREATED`
- `DOCUMENT_UPDATED`
- `DOCUMENT_DELETED`
- `DOCUMENT_REBUILD_REQUESTED`

消费者统一接收事件，再根据类型执行对应的处理流程。

这样可以避免新增、更新和删除各自实现一套完全独立的消息处理机制。

另外，事件应该携带足够的业务标识和版本信息，但不一定需要直接携带完整文档内容。对于大型文档，可以让消费者根据 `documentId` 和版本号读取对应的原始数据。

**说话人1：问题64，为什么需要定期执行原始数据与向量库之间的一致性对账？**

**说话人1：答：** 因为即使有事务、消息队列和重试机制，生产环境仍然可能出现异常。

例如，消费者长期停机、消息进入死信队列、人工误删数据，或者历史版本清理任务执行失败。

这些情况可能导致业务数据和向量数据不一致。

定期对账就是通过比较原始文档、版本记录和向量数据，发现遗漏或异常。

它相当于系统的最后一道数据质量保障机制，不能完全依赖消息队列保证一致性。

**说话人1：问题65，如何发现原文存在但向量缺失、原文已删除但向量残留、Chunk 数量不一致等问题？**

**说话人1：答：** 可以建立定期对账任务，根据文档 ID 和版本号进行比较。

主要检查：

1. 原始文档已发布，但没有对应的 Chunk。
2. 文档预期有 100 个 Chunk，实际只写入 98 个。
3. 文档已经删除，但仍然存在有效向量。
4. 文档当前有效版本是 V3，但检索数据仍然指向 V2。
5. Chunk 有记录，但 Embedding 为空或维度不符合预期。
6. 向量记录找不到对应的文档版本。

例如，可以先检查已发布文档是否存在 Chunk：

```
SELECT d.document_id, d.document_version
FROM knowledge_document d
WHERE d.status = 'PUBLISHED'
  AND NOT EXISTS (
      SELECT 1
      FROM knowledge_chunk c
      WHERE c.document_id = d.document_id
        AND c.document_version = d.document_version
  );
```

对于 Chunk 数量一致性，应该比较预期数量和实际数量。

需要注意，对账任务要根据数据发布状态判断，不能把正在处理的新版本误判成数据缺失。

**说话人1：问题66，当 Embedding 模型或向量维度发生变化时，为什么需要考虑全量重新向量化？**

**说话人1：答：** 因为不同 Embedding 模型生成的向量，可能处于完全不同的语义空间。

例如，原来使用模型 A，生成 1024 维向量；后来切换模型 B，生成 768 维向量。

首先，两个向量的维度不同，无法直接存入同一个固定维度的向量列。

即使两个模型的维度相同，它们的训练方式、向量分布和语义表达也可能不同。

因此，不能将旧模型和新模型的向量混合后直接进行相似度检索。

通常需要对所有有效 Chunk 使用新模型重新生成 Embedding，并建立新的索引。

**说话人1：问题67，如何通过双版本向量库或新旧索引并行方案完成 Embedding 模型迁移？**

**说话人1：答：** 可以采用新旧版本并行的方式进行迁移。

例如，当前线上使用 Embedding A，向量维度为 1024。

现在准备迁移到 Embedding B，维度为 768。

可以按照以下步骤执行：

1. 保留 A 的向量表和线上检索能力。
2. 新建 B 对应的向量表或向量列。
3. 使用原始文档重新切块或复用符合条件的 Chunk。
4. 使用模型 B 重新生成全部向量。
5. 建立 B 对应的向量索引。
6. 使用固定测试集验证召回率和回答质量。
7. 将线上检索切换到 B。
8. 观察运行情况，确认稳定后再下线 A。

如果使用 PostgreSQL + pgvector，可以建立两张不同维度的向量表，例如：

- `knowledge_chunk_v1`：保存模型 A 的向量。
- `knowledge_chunk_v2`：保存模型 B 的向量。

也可以使用独立的 Schema 或表版本管理。

关键是新旧模型的向量空间必须隔离，不能仅因为向量维度相同就认为可以混合使用。

**说话人1：问题68，如何设计向量数据重建任务，保证重建过程中线上 RAG 检索仍然可用？**

**说话人1：答：** 核心思想是新建数据集，不要直接破坏线上正在使用的数据。

例如，当前线上使用索引 A，准备重建索引 B。

可以这样做：

1. 记录当前有效文档和版本快照。
2. 创建新的向量表或索引。
3. 批量读取原始文档。
4. 执行解析、清洗、切块和 Embedding。
5. 写入新的向量数据集。
6. 校验文档数量、Chunk 数量和向量维度。
7. 使用评估集测试检索质量和响应延迟。
8. 将线上检索切换到新索引。
9. 对重建期间发生的文档变更进行补偿同步。
10. 确认新索引稳定后，再清理旧索引。

其中最容易忽略的是第 9 步。

因为重建需要时间，如果重建过程中原始文档又发生变化，新的索引可能遗漏这些变更。

因此，需要通过 Outbox、CDC 或变更日志记录重建期间的增量事件，在切换之前追平增量数据。

**说话人1：问题69，如何监控文档变更处理成功率、同步延迟、失败重试次数和孤儿向量数量？**

**说话人1：答：** 应该建立从文档接收到向量发布的完整可观测性。

主要监控以下指标：

| 指标               | 说明                               |
| ------------------ | ---------------------------------- |
| 文档处理成功率     | 成功发布文档数 / 总处理文档数      |
| 同步延迟           | 业务变更时间到向量发布完成时间     |
| Embedding 失败次数 | 模型调用失败的次数                 |
| 写入失败次数       | pgvector 写入失败的次数            |
| 重试次数           | 每个事件或任务的重试情况           |
| 死信事件数量       | 超过重试上限的事件数               |
| 孤儿向量数量       | 找不到有效文档或版本的向量记录     |
| Chunk 数量差异     | 预期 Chunk 数与实际 Chunk 数的差异 |
| 重建完成率         | 计划重建数据与实际完成数据的比例   |

在 Java 工程中，可以结合 Spring Boot Actuator 和 Micrometer 暴露指标，再通过 Prometheus 和 Grafana 进行监控。

日志中应包含 `traceId`、`eventId`、`documentId` 和 `documentVersion`，这样可以从一次业务变更追踪到具体的 Embedding 调用和数据库写入。

还需要避免将文档正文、API Key 等敏感内容直接写入日志。

**说话人1：问题70，在制造设备故障知识库中，如何设计一套从原始文档变更到 pgvector 更新、删除、重试和一致性对账的完整数据同步机制？**

**说话人1：答：** 我会设计成以 PostgreSQL 为事实数据源，以 pgvector 为检索派生数据，以 Outbox 和异步消费者实现最终一致性的架构。

整个过程分成六个部分。

**第一，原始文档管理。**

使用文档主表和版本表保存原始知识。

文档主表记录：

- `document_id`
- `business_id`
- `document_name`
- `active_version`
- `status`
- `deleted_at`

版本表记录：

- `document_version`
- `content_hash`
- `source_uri`
- `embedding_model`
- `processing_status`
- `created_at`

原始 PDF、Word 等文件可以存放在文件系统或对象存储中，数据库保存来源和版本信息。

**第二，变更事件管理。**

文档新增、更新和删除时，在同一个 PostgreSQL 事务中修改业务数据，并写入 Outbox 事件。

事件包含：

- `event_id`
- `event_type`
- `document_id`
- `document_version`
- `content_hash`
- `occurred_at`

通过后台任务或 CDC 将 Outbox 事件发送给消息队列。

**第三，文档处理流水线。**

消费者收到事件后，根据文档 ID 和版本号执行：

`解析 → 清洗 → 质量检测 → Chunk 切分 → Embedding → 向量入库`

每个 Chunk 保存文档 ID、版本号、Chunk ID、设备型号、故障代码和原文位置。

如果是新增，创建第一版 Chunk。

如果是更新，生成新版本 Chunk。

如果是删除，则进入删除处理流程。

**第四，向量写入与版本发布。**

所有新版本 Chunk 写入 pgvector 后，执行完整性校验。

例如，预期有 100 个 Chunk，就必须确认 100 个 Chunk 都已经成功写入，向量维度也必须符合表结构要求。

校验成功后，通过数据库事务切换文档的当前有效版本。

检索时只允许读取当前有效版本，并过滤已经删除的文档。

这样可以避免更新过程中出现新旧知识混合。

**第五，失败重试和删除清理。**

处理失败时记录：

- 失败事件 ID。
- 文档 ID 和版本号。
- 失败阶段。
- 错误原因。
- 重试次数。
- 下次重试时间。

短暂网络故障可以自动重试；超过重试上限后进入死信队列。

对于删除事件，先保证文档不再参与检索，再异步清理对应的 Chunk 和向量记录。

**第六，定期一致性对账。**

定期比较原始文档、版本表和 Chunk 表：

- 是否存在已发布但没有向量的文档。
- 是否存在 Chunk 数量不一致。
- 是否存在已删除但仍然可检索的向量。
- 是否存在旧版本覆盖新版本。
- 是否存在向量维度或模型版本错误。

发现问题后，根据原始文档和版本记录执行补偿、重试或重建。

这套设计的核心不是追求每一次操作都瞬间同步，而是保证：

1. 原始知识始终有权威来源。

3. 重复事件不会产生重复数据。
4. 旧版本不会覆盖新版本。
5. 更新失败不会轻易破坏线上检索。
6. 删除后失效知识不会继续参与检索。
7. 即使发生异常，也能通过重试和对账最终恢复一致。

## **四、核心知识总结**

| 核心问题         | 关键技术方案                             |
| ---------------- | ---------------------------------------- |
| 新增如何同步     | 解析、清洗、切块、Embedding、Upsert      |
| 如何避免重复     | SHA-256、确定性 Chunk ID、唯一约束、幂等 |
| 更新如何同步     | 文档版本化、新版本构建、校验后发布       |
| 删除如何同步     | 软删除、检索过滤、异步清理               |
| 如何保证可靠性   | PostgreSQL 事务、Outbox、消息队列、重试  |
| 如何处理乱序     | 单调递增版本号、条件更新                 |
| 如何防止数据丢失 | 原始文档留存、备份、WAL、PITR            |
| 如何发现异常     | 定期一致性对账、孤儿向量检查             |
| 模型如何迁移     | 新旧向量表并行、全量重建、切换           |
| 如何保证线上可用 | 新版本构建完成后再发布                   |

**最重要的三个工程原则：**

1. **原始数据是事实来源，向量数据是派生索引。** 向量库必须可以从原始知识重新构建。
2. **先构建新版本，再切换发布，最后清理旧版本。** 不要在新版本尚未准备好时提前删除线上有效知识。
3. **事务保证局部原子性，Outbox 保证变更事件可靠记录，幂等和对账保证最终一致性。** 这三者解决的是不同层次的问题，不能相互替代。
