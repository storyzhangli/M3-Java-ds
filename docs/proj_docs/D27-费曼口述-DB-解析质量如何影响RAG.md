# 费曼口述：解析质量如何影响 RAG

说话人1: 费曼口述，解析质量如何影响 RAG 全链路，共八十道关键问题，由浅入深分八个阶段，从文档解析质量基础、不同格式的解析问题、解析错误对全链路的影响、解析结果与切分、解析结果与 Embedding 检索、解析质量评估与定位、Spring AI 工程实践，到企业级 RAG 综合设计，技术基线为 JDK 21、Spring Boot 3.5.x、Spring AI 1.1.8。核心主线：原始文档 → 文档解析 → 结构保留 → 文本清洗 → Chunk 切分 → Embedding → 向量检索 → 上下文构建 → 大模型生成。

## 第一阶段：文档解析质量基础

说话人1: 问题一，什么是文档解析质量？为什么它是 RAG 的基础？
说话人1: 答，文档解析质量就是从原始文件里提取出来的文本，是不是完整、准确、结构清晰。它是 RAG 的基础，因为后面所有步骤——切分、向量化、检索、生成——都是基于解析出来的文本做的。解析错了，后面再好的模型也救不回来。

说话人1: 问题二，文档解析、文档清洗、文本切分分别解决什么问题？
说话人1: 答，文档解析：把原始文件（PDF、Word、Excel）转成纯文本；文档清洗：把解析出来的脏文本清理干净，去掉页眉页脚、多余空白；文本切分：把长文本切成适合 Embedding 的小块。三步是顺序关系，解析是第一步。

说话人1: 问题三，为什么 RAG 的最终答案质量不仅取决于大模型和 Embedding 模型？
说话人1: 答，因为垃圾进垃圾出。你给大模型的上下文里如果缺了关键信息、顺序错乱、混了无关内容，大模型再强也只能基于错误的输入生成答案。输入质量决定输出上限。

说话人1: 问题四，文档解析质量通常包含哪些评价维度？
说话人1: 答，四个维度：文本完整性——该提取的有没有漏；文本准确性——识别得对不对；结构保留——标题、表格、列表的结构有没有保留；来源可追溯——能不能对应回原始文档的位置。

说话人1: 问题五，什么是文本完整性？文本丢失会造成什么后果？
说话人1: 答，文本完整性就是原始文档里的文字，解析出来有没有全部提取到。如果丢了关键段落、表格里的几行数据，那 RAG 检索的时候就找不到这些信息，用户问相关问题就答不出来。

说话人1: 问题六，什么是文本准确性？OCR 识别错误如何影响知识内容？
说话人1: 答，文本准确性就是提取出来的文字和原文是不是一致。OCR 识别错了，比如把"故障代码 E102"识别成"故障代码 E1O2"，那用户搜 E102 就搜不到，模型也会基于错误的内容回答。

说话人1: 问题七，什么是结构保留？为什么不能只关注提取出的纯文本？
说话人1: 答，结构保留就是标题层级、段落、表格、列表这些结构有没有保留下来。只提取纯文本，丢掉了结构，切分的时候就不知道哪里是标题、哪里是正文，Chunk 的语义就不完整。

说话人1: 问题八，文档标题、章节层级、段落和列表结构对 RAG 有什么价值？
说话人1: 答，标题和章节层级是切分的边界依据，按章节切出来的 Chunk 语义更完整；列表结构保留下来，信息才不会乱；段落结构让 Chunk 不会把两段不相关的内容拼在一起。

说话人1: 问题九，页码、表格、图片和脚注等元素为什么需要保留来源信息？
说话人1: 答，保留来源信息，是为了用户看到答案之后，能回过去查原文。比如答案引用了第 3 页的表格，用户可以翻到第 3 页核对。这也是 RAG 可信度的基础。

说话人1: 问题十，为什么解析结果需要能够追溯到原始文档？
说话人1: 答，因为出了问题你要能定位：是解析错了，还是切分错了，还是检索错了，还是模型生成错了。如果不能追溯，你根本不知道问题出在哪一环。

## 第二阶段：不同文档格式的解析质量问题

说话人1: 问题十一，TXT 文档解析可能出现哪些质量问题？
说话人1: 答，TXT 本身就是纯文本，解析简单。问题主要在编码——如果是 GBK 编码，用 UTF-8 读就乱码；还有换行和段落不规范，切分的时候容易出问题。

说话人1: 问题十二，Markdown 文档解析时为什么需要保留标题层级和代码块？
说话人1: 答，Markdown 的标题层级就是天然的切分边界，按标题切分，Chunk 语义完整。代码块如果拆开，就破坏了代码的完整性，检索到了也没法用。

说话人1: 问题十三，PDF 的文本提取为什么可能出现阅读顺序错乱？
说话人1: 答，因为 PDF 里的文本是按视觉位置摆放的，不是按阅读顺序存的。提取的时候，如果只按坐标从上到下扫，双栏、多列的文档就会左右栏混在一起，顺序就乱了。

说话人1: 问题十四，PDF 双栏排版会给文本解析带来什么问题？
说话人1: 答，双栏排版，简单的按从上到下提取，会把左栏第一行和右栏第一行拼在一起，读起来完全不通。必须先识别分栏，再按栏提取，顺序才对。

说话人1: 问题十五，PDF 中的页眉、页脚和页码如何影响解析结果？
说话人1: 答，每页都有页眉页脚，如果不处理，切分之后每个 Chunk 里都混着重复的页眉页脚。这些无关内容会稀释文本的语义，影响 Embedding 和检索。

说话人1: 问题十六，为什么扫描版 PDF 不能简单依靠普通文本提取？
说话人1: 答，扫描版 PDF 本质是图片，里面没有文本层，普通的文本提取工具读不出来。必须走 OCR，把图片里的文字识别出来，才有文本可用。

说话人1: 问题十七，OCR 的准确率如何影响 RAG 的检索和生成？
说话人1: 答，OCR 准确率低，识别出来的错字、乱码就多。关键词搜不到，向量相似度也低，检索质量差；模型基于错误文本生成，答案自然也错。

说话人1: 问题十八，Word 文档中的标题、表格、图片和文本框为什么需要区别处理？
说话人1: 答，标题是结构信息，要保留层级；表格要按行列提取成结构化数据；图片要 OCR 或者跳过；文本框里的文字经常容易被漏掉。每种元素处理方式不一样，不能一刀切。

说话人1: 问题十九，Excel 文档为什么不能简单地按普通段落进行文本提取？
说话人1: 答，Excel 是表格结构，一行就是一条记录，一列就是一个字段。如果你按普通文本提取，行列关系就乱了，参数和数值对不上，检索出来也用不了。

说话人1: 问题二十，PowerPoint 文档中的页面标题、文本框和图表如何影响知识组织？
说话人1: 答，PPT 的每一页是一个独立主题，标题就是主题。按页切分，每页的标题加内容就是一个 Chunk。如果把多页的文本混在一起，主题就乱了。

说话人1: 问题二十一，HTML 页面中的导航栏、广告和正文混杂会造成什么问题？
说话人1: 答，网页里大量导航、广告、侧边栏，如果不清洗，这些无关内容会混进 Chunk，稀释正文语义，Embedding 和检索都会受影响。

说话人1: 问题二十二，不同文件格式是否应该采用完全相同的解析策略？
说话人1: 答，不应该。每种格式有自己的特点和坑，PDF 要处理分栏和 OCR，Word 要处理样式和表格，Excel 要处理行列结构。用同一套策略，肯定有一类格式解析不好。

## 第三阶段：解析错误对 RAG 全链路的影响

说话人1: 问题二十三，文档解析遗漏关键信息后，后续切分阶段能否自动恢复？
说话人1: 答，不能。解析阶段丢了的信息，就是没了，切分阶段只能处理已经存在的文本，变不出来丢失的内容。错误从源头就产生了。

说话人1: 问题二十四，文本顺序错误为什么可能破坏原本的业务语义？
说话人1: 答，语言的语义是有顺序的。一句话前后颠倒，意思可能完全反过来。顺序错了，Embedding 出来的向量语义就错了，检索和生成都跟着错。

说话人1: 问题二十五，表格解析错误如何影响设备参数、故障代码和技术指标的检索？
说话人1: 答，设备参数、故障代码这些，都是表格里的结构化数据。表格解析错了，字段名和数值对不上，用户搜"E102 故障"就找不到对应的处理方法，因为字段和数值已经错位了。

说话人1: 问题二十六，如果表格中的字段名与数值被拆开，Embedding 会受到什么影响？
说话人1: 答，字段名和数值本来是一体的，拆开之后，各自的语义都不完整。Embedding 出来的向量，表达的不是一个完整的参数信息，相似度计算就不准。

说话人1: 问题二十七，如果 PDF 中的标题和正文顺序错乱，会怎样影响 Chunk 的语义完整性？
说话人1: 答，标题是正文的概括，正文是标题的展开。顺序错乱了，切分的时候标题和对应的正文可能分到不同 Chunk 里。Chunk 里只有正文没有标题，语义就不完整。

说话人1: 问题二十八，如果解析结果混入大量页眉、页脚和无关文本，会产生什么后果？
说话人1: 答，这些无关内容会稀释正文的语义。Embedding 的时候，向量里混了大量重复的页眉页脚信息，真正的正文特征被冲淡了。检索的时候，相似度就不准。

说话人1: 问题二十九，如果 OCR 将数字 0 识别为字母 O，可能造成什么业务风险？
说话人1: 答，比如故障代码 E102 识别成 E1O2，用户搜 E102 就搜不到。设备型号、参数值这些关键信息错一个字符，就可能导致错误的维修方案，有实际业务风险。

说话人1: 问题三十，为什么解析阶段产生的错误可能一直传递到最终答案？
说话人1: 答，因为 RAG 是流水线，前面一步的输出就是后面一步的输入。解析错了 → 切分基于错误文本 → Embedding 基于错误 Chunk → 检索召回错误内容 → 模型基于错误上下文生成答案。一路传下去。

说话人1: 问题三十一，为什么高质量 Embedding 模型无法弥补严重的原始文本缺失？
说话人1: 答，Embedding 模型只能把已有文本转成向量，它变不出不存在的内容。原文丢了一大段，Embedding 再好，那一段的信息还是没有。输入缺了，输出补不上。

说话人1: 问题三十二，为什么检索结果相关性高，也不代表原始文档解析质量高？
说话人1: 答，相关性高可能是因为你搜的关键词刚好在里面。但不代表整个文档解析得完整准确。可能大部分内容都丢了，就这一段碰巧对了。

说话人1: 问题三十三，解析错误如何导致 RAG 产生错误引用或错误答案？
说话人1: 答，解析错了 → 切出来的 Chunk 内容不对 → 检索召回了错误或者不完整的 Chunk → 模型基于错误的 Chunk 生成答案 → 答案就是错的，引用的来源也是错的。

说话人1: 问题三十四，如何区分解析错误、切分错误、检索错误和模型生成错误？
说话人1: 答，逐层排查。先看原始文档和解析结果对不对，不对就是解析错；解析对了，看切分出来的 Chunk 对不对，不对就是切分错；Chunk 对了，看检索召回的 Chunk 是不是相关的，不对就是检索错；召回对了但答案错，就是模型生成的问题。

## 第四阶段：解析结果与文本切分

说话人1: 问题三十五，为什么解析完成后不能直接认为文档已经可以进入向量数据库？
说话人1: 答，因为解析完的文本还是脏的，有页眉页脚、多余空白、顺序错乱。必须先清洗，再切分，才能进向量库。直接扔进去，后面全是问题。

说话人1: 问题三十六，文档结构如何影响 Chunk 的边界设计？
说话人1: 答，文档结构就是天然的切分边界。按标题、章节、段落切，切出来的 Chunk 语义完整。如果没有结构信息，硬按固定字数切，很容易把一个完整的意思切成两半。

说话人1: 问题三十七，为什么应该优先按照标题、章节和段落进行结构化切分？
说话人1: 答，因为结构化切分，每一块都是一个完整的主题，语义不会被破坏。按字数硬切，切出来的 Chunk 可能前半句讲 A，后半句讲 B，语义混乱。

说话人1: 问题三十八，如果一个完整表格被切分成多个 Chunk，可能造成什么问题？
说话人1: 答，表格是一个整体，行和列是关联的。切成多个 Chunk，就拆开了。检索的时候可能只召回其中几行，用户看到的参数不完整，答案自然也不完整。

说话人1: 问题三十九，为什么切分时需要避免标题与对应正文分离？
说话人1: 答，标题是正文的概括。Chunk 里只有正文没有标题，你不知道这段内容讲的是什么主题。语义就不完整，Embedding 和检索都受影响。

说话人1: 问题四十，解析结果中的空行、换行符和特殊字符如何影响文本切分？
说话人1: 答，乱的空行和换行，会让切分工具误判段落边界。该切的地方没切，不该切的地方切了。特殊字符也会干扰 Embedding。

说话人1: 问题四十一，为什么需要在切分前处理重复页眉、页脚和无意义空白？
说话人1: 答，这些是噪声，混在文本里会污染 Chunk。切分前清掉，Chunk 才干净，语义才纯粹。

说话人1: 问题四十二，如何处理跨页表格，避免表头与数据行分离？
说话人1: 答，识别跨页的表格，把它合并成一个完整表格再切分。表头只保留一次，数据行接在后面。这样切出来的表格是完整的。

说话人1: 问题四十三，如何处理代码块、公式和列表，避免破坏其内部结构？
说话人1: 答，这些有内部结构的内容，要整块保留，不要从中间切开。切分的时候，识别到代码块、列表，就把它们作为一个整体处理。

说话人1: 问题四十四，文档解析质量与 Chunk Size、Overlap 之间有什么关系？
说话人1: 答，解析质量高，结构清晰，Chunk Size 可以设小一点，因为切分边界准确。解析质量差，结构乱，你就得把 Chunk Size 设大一点，多留点冗余，保证语义不丢。

## 第五阶段：解析结果与 Embedding、向量检索

说话人1: 问题四十五，为什么解析质量会影响 Embedding 向量的语义表达？
说话人1: 答，Embedding 是基于输入文本生成的。文本质量差，有错字、顺序乱、混了无关内容，生成的向量表达的语义就不准。向量不准，检索就不准。

说话人1: 问题四十六，文本中混入无关内容，为什么可能降低向量检索质量？
说话人1: 答，无关内容会冲淡真正正文的语义特征。向量里混了大量噪声，和查询向量算相似度的时候，真正相关的特征被冲淡了，排序就不准。

说话人1: 问题四十七，关键业务术语丢失后，可能如何影响向量相似度检索？
说话人1: 答，业务术语是用户查询和文档之间的桥梁。术语丢了，用户搜这个术语，对应的 Chunk 里没有，就召回不到。向量相似度再高，也没用。

说话人1: 问题四十八，设备型号、故障代码和专业缩写解析错误，会造成什么检索问题？
说话人1: 答，这些是精确匹配的关键词。错一个字符，精确检索就搜不到，向量相似度也会下降。用户搜正确的型号，召回的都是错的型号的内容。

说话人1: 问题四十九，为什么相同的 Embedding 模型可能因为输入文本质量不同而产生不同检索效果？
说话人1: 答，Embedding 模型只是一个转换工具，输入决定输出。同样的模型，输入干净准确的文本，向量质量就高；输入脏的、错的文本，向量质量就差。

说话人1: 问题五十，解析错误如何影响 Hybrid Search 中的关键词检索？
说话人1: 答，Hybrid Search 有关键词检索部分。解析错了，关键词本身就错了，BM25 这些关键词检索自然就搜不到。向量部分也受影响。两边都不准。

说话人1: 问题五十一，Metadata 中的页码、章节、文档版本和来源信息为什么重要？
说话人1: 答，这些是溯源和过滤的依据。你可以按文档版本过滤，只检索最新版的文档；可以按章节缩小检索范围；答案出来了，能告诉用户出自哪一页哪一份文档。

说话人1: 问题五十二，如何通过检索结果反向判断文档解析质量？
说话人1: 答，看检索回来的 Chunk 内容是不是完整、是不是和查询相关。如果经常召回不完整的、混杂的、顺序错乱的 Chunk，那大概率是解析阶段就有问题。

## 第六阶段：解析质量评估与问题定位

说话人1: 问题五十三，如何建立文档解析质量评估指标？
说话人1: 答，几个核心指标：文本提取完整率——该提的提了多少；文本准确率——提对的占多少；结构保留率——标题、表格的结构保留了多少；来源可追溯率——能不能对应回原文。

说话人1: 问题五十四，如何衡量文本提取完整率？
说话人1: 答，人工标注一份标准文档，有多少文字。然后看解析结果里有多少文字，比值就是完整率。也可以用字符数、段落数粗算。

说话人1: 问题五十五，如何发现解析结果中的乱码、重复内容和异常字符？
说话人1: 答，自动检查：找乱码字符、找重复段落、找异常符号。再人工抽样看几页，确认有没有明显问题。

说话人1: 问题五十六，如何验证 PDF 解析后的阅读顺序是否正确？
说话人1: 答，把解析出来的文本从头到尾读一遍，看逻辑通不通。双栏的地方，看是不是先左栏后右栏。也可以人工对比原文，逐段核对。

说话人1: 问题五十七，如何检查表格解析后的字段、行列和数值是否完整？
说话人1: 答，解析出来的表格，和原表格对比：行列数对不对，字段名对不对，数值对不对。重点看跨页表格、合并单元格这些容易出错的地方。

说话人1: 问题五十八，如何通过人工抽样对比原始文档和解析结果？
说话人1: 答，随机抽几份文档，每份抽几页，人工对照原文，看提取的文本、顺序、结构对不对。抽样不用全做，但要有代表性。

说话人1: 问题五十九，什么是解析质量测试集？应该如何构建？
说话人1: 答，测试集就是一批已知标准答案的文档，用来测解析器的效果。构建的时候，选各种典型文档：正常的、扫描的、复杂表格的、双栏的，每份都人工标注好正确结果。

说话人1: 问题六十，如何设计包含正常文档、扫描件、复杂表格和异常文件的测试样本？
说话人1: 答，分类收集样本。正常文档：普通 PDF、Word；扫描件：图片版 PDF；复杂表格：多列、跨页、合并单元格；异常文件：损坏的、加密的、格式奇怪的。各种类型都要有。

说话人1: 问题六十一，如何对比不同解析器的效果？
说话人1: 答，用同一套测试集，跑不同的解析器，对比完整率、准确率、结构保留率。哪个综合效果好，就用哪个。

说话人1: 问题六十二，如何区分解析失败、部分解析成功和解析成功但质量不合格？
说话人1: 答，解析失败：完全没提取出来内容；部分解析成功：提取了一部分，但漏了很多；解析成功但质量不合格：文本出来了，但错字多、顺序乱、结构丢了。三档。

说话人1: 问题六十三，为什么文档导入成功不代表文档解析质量合格？
说话人1: 答，导入成功只是说文件传到系统里了，流程跑通了。但跑出来的结果质量好不好，是另一回事。很多系统只判断有没有报错，不判断结果质量。

说话人1: 问题六十四，如何建立解析质量门禁，阻止低质量文档进入知识库？
说话人1: 答，文档解析完之后，自动跑质量检查：完整率够不够，准确率够不够，结构有没有大问题。不合格的，打回去，不进向量库。

## 第七阶段：Spring AI 工程实践

说话人1: 问题六十五，Spring AI 中 Document、DocumentReader 分别承担什么职责？
说话人1: 答，Document 是统一的文档数据结构，包含文本内容和 Metadata；DocumentReader 是读取器接口，负责把各种格式的文件读成 Document。

说话人1: 问题六十六，Spring AI 的文档读取组件如何与 PDF、Word 等外部解析工具配合？
说话人1: 答，Spring AI 本身的 DocumentReader 是抽象接口，具体的解析实现，可以集成 Apache Tika、PDFBox、POI 这些外部解析库。Spring AI 定义标准，外部工具做具体解析。

说话人1: 问题六十七，如何在 Spring AI 文档导入流程中保留来源、标题、页码和版本等 Metadata？
说话人1: 答，Document 对象里有一个 Map<String, Object> metadata，把来源文件名、当前页码、章节标题、文档版本这些信息都放进去。后面切分的时候，Metadata 会跟着 Chunk 走。

说话人1: 问题六十八，如何设计解析器接口，使不同文件格式能够采用不同解析策略？
说话人1: 答，定义一个统一的 DocumentReader 接口，然后 PDF 一个实现，Word 一个实现，Excel 一个实现。根据文件后缀，选对应的解析器实现。策略模式。

说话人1: 问题六十九，如何为 PDF、Word、Excel 和 Markdown 分别设计解析质量验证？
说话人1: 答，PDF：验证阅读顺序、页眉页脚过滤、表格完整性；Word：验证标题层级、表格、文本框；Excel：验证行列结构、字段对应；Markdown：验证标题层级、代码块保留。每类格式重点不一样。

说话人1: 问题七十，如何设计文档解析失败后的重试、隔离和错误记录机制？
说话人1: 答，解析失败的，自动重试几次；还是失败的，隔离到失败队列，不阻塞整个导入流程；记录错误日志，包括文件名、失败原因、时间，后面人工处理。

说话人1: 问题七十一，如果文档解析成功但质量检测不合格，应该如何处理？
说话人1: 答，不进入向量库，标记为质量不合格，记录问题原因。通知人工检查，或者换一个解析器重试。不要让低质量文档污染知识库。

说话人1: 问题七十二，如何记录解析器版本和解析配置，保证问题可追溯？
说话人1: 答，Metadata 里加上解析器版本号、解析配置参数。后面出问题了，你能知道这份文档是用哪个版本的解析器、什么配置解析出来的，方便复现和排查。

说话人1: 问题七十三，如果文档更新后解析结果发生变化，如何识别并重新构建对应的向量数据？
说话人1: 答，文档更新的时候，记录文档版本号。版本变了，就把旧的 Chunk 和向量删掉，重新解析、切分、向量化。

说话人1: 问题七十四，如何避免解析质量问题污染已经发布的生产知识库？
说话人1: 答，解析质量门禁，不合格的不进生产库。先在测试环境验证，没问题了再同步到生产。新解析器上线，先灰度，不要全量切。

## 第八阶段：企业级 RAG 综合设计

说话人1: 问题七十五，如果一份设备维修手册包含扫描页、复杂表格和图片，你会如何设计完整解析方案？
说话人1: 答，分步骤：先识别哪些页是扫描页，扫描页走 OCR；表格页专门做表格解析，保留行列结构；图片里的文字也走 OCR。解析完之后，做清洗，去页眉页脚。然后按章节结构化切分，表格整块保留。Metadata 记上页码、章节、表格类型。最后做质量检查，合格了再入库。

说话人1: 问题七十六，如果用户询问某设备故障代码的处理步骤，但解析时遗漏了表格中的关键参数，你会如何定位问题？
说话人1: 答，先看检索回来的 Chunk 是不是相关的。如果召回的文档是对的，但内容不完整，就回到解析结果里找。看那个故障代码对应的表格，是不是解析的时候漏了行。确认是解析阶段丢了信息，重新解析那一页。

说话人1: 问题七十七，如果 RAG 能检索到正确文档，却始终生成错误答案，你会如何沿数据链路排查？
说话人1: 答，从后往前查。先看模型生成的输入——也就是检索回来的 Chunk 内容对不对。Chunk 对的话，就是模型 Prompt 的问题；Chunk 不对的话，看切分是不是把关键信息切丢了；切分没问题的话，看解析是不是错了。一层一层往前找。

说话人1: 问题七十八，如果不同解析器对同一 PDF 产生不同结果，你会如何选择和验证？
说话人1: 答，拿一批典型测试文档，分别用两个解析器跑，对比完整率、准确率、结构保留率。选综合效果好的那个。再拿实际业务文档做小流量验证，效果稳定了再全量切。

说话人1: 问题七十九，如何建立从原始文档、解析结果、Chunk、Embedding 到最终答案的全链路质量追踪？
说话人1: 答，每一层都加 TraceId 和版本信息。原始文档有文档 ID，解析结果有解析批次 ID，每个 Chunk 有 Chunk ID 和对应的文档位置，Embedding 记录模型版本。用户问问题的时候，能回溯到召回了哪些 Chunk，这些 Chunk 来自哪份文档哪一页，是哪次解析生成的。全链路可追溯。

说话人1: 问题八十，如果让你负责企业知识库的文档解析质量治理，你会如何设计评估体系、质量门禁和持续改进机制？
说话人1: 答，三个方面。
说话人1: 第一，评估体系：建测试集，定指标，定期跑评测，看解析质量怎么样。
说话人1: 第二，质量门禁：解析完自动检查，不合格的不入库，把好入口关。
说话人1: 第三，持续改进：收集线上 bad case，就是那些答得不好的问题，反推回去看是解析、切分、检索还是生成的问题。解析有问题的，改解析器，补测试用例。循环迭代，质量一步步提升。
说话人1: 核心思路就是：入口有门禁，过程可追溯，问题有反馈，持续有改进。
