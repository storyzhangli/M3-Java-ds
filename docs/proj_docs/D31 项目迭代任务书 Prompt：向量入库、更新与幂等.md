## 4. 核心实施需求

### 4.1 文档与 Chunk 关联及稳定 ID

建立清晰、可追溯的数据关系：

- 一个文档对应多个 Chunks。
- 每个 Chunk 能追溯所属文档及文档版本。
- 向量记录能够关联原始 Chunk。
- 删除或更新文档时能够准确定位相关向量。

设计并说明：

1. 稳定的 documentId。
2. 稳定的 chunkId。
3. documentVersion 或内容版本标识。
4. 幂等操作标识。
5. Embedding 模型及维度等必要版本信息。

ID 设计应基于稳定业务标识和可确定的内容或版本信息，不得依赖每次导入随机生成 ID。

同一文档、同一版本、相同切分结果重复处理时，应得到一致的 Chunk 标识和幂等操作标识。

如果文档内容、切分规则或 Embedding 版本发生变化，应能正确识别为需要更新的版本。

### 4.2 向量入库与幂等

实现：

1. 读取已切分的 Chunks。
2. 调用现有 EmbeddingModel 生成向量。
3. 检查向量非空、384 维及数值合法性。
4. 写入 PostgreSQL + pgvector。
5. 保存文档、版本、Chunk 与向量的关联信息。

幂等要求：

- 同一文档重复导入不产生重复 Chunk 或向量。
- 重复执行同一任务不会重复创建业务数据。
- 写入失败后重新执行，不产生重复记录。
- 并发导入同一文档时，不产生重复或相互覆盖的数据。
- 通过数据库唯一约束、幂等键、事务或适当的并发控制保证正确性，不能只依赖 Java 内存判断。

优先沿用 Spring AI 1.1.8 的 PgVectorStore；必须核实其实际 ID、更新和删除语义。如果现有接口不足以满足业务幂等要求，可设计必要的 Repository/JDBC 操作补充，不得假设框架自动提供完整业务一致性。

### 4.3 文档更新与旧版本处理

文档内容更新后，必须正确处理旧版本 Chunks 和向量。

设计并验证：

- 如何识别新旧文档版本。
- 如何确定需要重新向量化的 Chunks。
- 新版本写入过程中如何避免部分数据被检索。
- 新版本成功后如何切换有效版本。
- 旧版本如何清理。
- 更新失败时如何保留可恢复状态。
- 旧任务或迟到任务如何避免覆盖更新版本。

重点防止新旧版本同时被当成有效数据，以及更新中断后产生不可追溯的数据。

不得简单采用先删除全部旧数据、再无保护写入新数据的方案。

### 4.4 删除与关联数据清理

实现按 documentId 或 documentVersion 定位相关数据的删除流程。

要求：

- 删除目标准确。
- 相关 Chunk 与向量能够正确清理。
- 不误删其他文档数据。
- 删除任务重复执行仍然安全。
- 删除中途失败可以继续恢复。
- 删除状态与实际向量数据保持可核对。

如采用软删除、标记删除或延迟清理，必须说明状态流转和最终清理机制。

### 4.5 失败重试与部分失败恢复

设计必要的处理状态，例如：

`PENDING → PROCESSING → SUCCEEDED / FAILED`

可根据现有架构扩展为删除、恢复等状态，但避免无必要的复杂状态机。

必须支持：

- 任务失败后识别失败位置。
- 重试时跳过已经正确完成的部分。
- 已写入的 Chunk 不重复创建。
- 未完成的 Chunk 可以继续处理。
- 重试次数、最后错误和处理结果可追踪。
- 任务重复触发或并发执行时结果一致。

对 Embedding 生成、向量写入、状态更新等关键步骤设置必要的失败处理和可恢复边界。

不能仅通过捕获异常后重新执行整个流程来声称具备恢复能力。

## 5. 六种场景验收

必须设计可重复执行的测试，至少覆盖以下六种场景：

| 场景         | 验收重点                                        |
| ------------ | ----------------------------------------------- |
| 新增         | Chunks 正常向量化入库，文档关联正确             |
| 重复导入     | 同一文档重复执行，不产生重复数据                |
| 更新         | 新版本正确生效，旧版本按策略处理                |
| 删除         | 对应 Chunk 和向量正确清理，不误删其他文档       |
| 失败重试     | 模拟写入失败后重试，不产生重复写入              |
| 部分失败恢复 | 部分 Chunk 已完成时发生异常，能够识别状态并恢复 |

额外检查：

- 并发重复导入。
- 旧版本任务迟到。
- 删除任务重复执行。
- 向量写入成功但状态更新失败。
- 数据库连接中断后恢复。

测试必须使用实际 PostgreSQL/pgvector 集成环境验证关键数据一致性。单元测试和 Mock 只能辅助，不能代替真实数据库验收。

每个场景都应检查数据库记录数量、文档关联、版本状态和孤儿数据情况，不能只检查接口返回成功。

## 6. 原文库与向量库一致性

必须分析原文数据和向量数据的实际存储边界。

**禁止将数据库事务误认为能够自动保证不同数据库之间的跨系统一致性。**

如原文库和向量库属于不同数据库或独立事务边界，必须明确说明：

- 原文写入成功、向量写入失败的风险。
- 向量写入成功、原文状态更新失败的风险。
- 删除原文成功、向量残留的风险。
- 更新任务重复执行或执行顺序错乱的风险。
- 应用宕机、网络中断和消息丢失带来的风险。

根据现有架构选择合适的最终一致性方案，优先评估：

1. 原文库事务内记录 Outbox 事件。
2. 异步任务或可靠任务记录驱动向量处理。
3. 消费端基于幂等键执行。
4. 失败重试及失败任务记录。
5. 定期对账，识别缺失向量、孤儿向量和版本不一致。
6. 补偿任务支持重新入库、清理或恢复。

如果现有架构不适合引入完整消息中间件，不要为了设计而额外引入复杂基础设施；优先实现可落地的最小可靠方案。

最终必须形成一份一致性风险与补偿策略说明，明确哪些保证是强一致的，哪些属于最终一致，以及异常后如何恢复。
