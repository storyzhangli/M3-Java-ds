# D26 文档导入与基础解析技术原理及操作实践指南

## 1. 文档生命周期

```text
PENDING -> PROCESSING -> COMPLETED
                     \-> FAILED
FAILED -> PROCESSING -> COMPLETED/FAILED
```

| 状态 | 语义 |
|---|---|
| PENDING | 元数据已登记，无成功文件内容 |
| PROCESSING | 文件字节已关联，正在识别/解析 |
| COMPLETED | 文件校验和基础解析成功 |
| FAILED | 当前导入失败，可重试 |

状态不是 D25 的发布生命周期，而是 D26 导入状态。

## 2. 元数据与文件内容的区别

元数据：

- 文档是什么。
- 来源、标题、版本。
- 状态、更新时间。
- 文件描述和 contentHash。

文件内容：

- 原始字节。
- 基础解析文本。

D26 分表：

```text
knowledge_document
knowledge_document_content
```

documentId 是关联键。

## 3. 为什么登记与导入分离

登记和导入发生时间不同：

- 文档可以先建档，文件稍后上传。
- 文件替换/重试不应创建新的元数据身份。
- 文件校验属于导入职责。
- 登记接口更易做业务元数据校验。
- Controller 不会因文件与元数据两类职责混合而膨胀。

## 4. Multipart 机制

客户端：

```text
Content-Type: multipart/form-data
file=<binary>
```

Spring MVC：

1. Servlet multipart resolver 解析请求。
2. 文件写入临时存储或内存阈值。
3. `MultipartFile` 进入 Controller。
4. Service 读取字节并执行业务校验。

容器限制在 Controller 前执行；业务限制在 Service/Parser 中再次执行。

## 5. 文件大小限制

### Servlet

```yaml
spring.servlet.multipart.max-file-size: 5MB
spring.servlet.multipart.max-request-size: 6MB
```

过大会抛 `MaxUploadSizeExceededException`，由全局异常处理转换为 4101。

### 业务

```yaml
app.knowledge.import.max-file-size: 5MB
```

即使有人直接调用 Service，也无法绕过。

### 测试教训

MockMvc 的 `MockMultipartFile` 不会经过 Servlet multipart 上限。因此容器限制使用随机端口真实 HTTP 测试；业务限制单独测试。

## 6. 文件内容类型

不能信任：

- 扩展名。
- 前端声明的 Content-Type。

D26：

1. 扩展名白名单先过滤明显不支持类型。
2. Tika 根据字节检测实际 MIME。
3. 实际 MIME 必须匹配扩展名类别。

示例：

- PNG 字节命名为 `.txt` -> 拒绝。
- HTML 声称 text/plain -> 实际检测 text/html，可正确解析。
- PDF 必须是 application/pdf。

D26 支持 txt/md/markdown/html/htm/pdf。

## 7. UTF-8 解码

文本使用严格解码：

```java
StandardCharsets.UTF_8.newDecoder()
    .onMalformedInput(CodingErrorAction.REPORT)
    .onUnmappableCharacter(CodingErrorAction.REPORT)
```

默认替换符 `�` 会把坏数据伪装成可解析文本，因此必须 REPORT。

同时拒绝 NUL，避免二进制内容伪装成文本。

## 8. Tika/PDFBox 基础解析

- HTML/PDF 使用 `TikaDocumentReader`。
- PDF 底层使用 PDFBox。
- 输出文本为空 -> 4221。
- 输出超过 `maxParsedChars` -> 421/解析失败。

本轮只生成解析文本，不切 Chunk。

## 9. SHA-256 与重复识别

```text
contentHash = SHA-256(original bytes)
```

不是：

- 文件名 hash。
- 解析文本 hash。
- 时间/UUID随机值。

文件改名但内容相同，仍识别为重复。

## 10. 数据库唯一约束

```sql
UNIQUE KEY uk_knowledge_content_hash (content_hash)
```

`NULL` 允许多个未导入文档；一旦导入写入非空 hash，相同 hash 只能存在一行。

业务还做导入前查询，避免明显重复进入处理。

## 11. 并发重复

竞态：

```text
线程A查询无重复
线程B查询无重复
A/B同时尝试 PROCESSING
```

最终保护：

- 唯一索引只允许一个成功。
- 另一个事务回滚。
- 另一个文档保持 PENDING。
- 已有文档的 version/status/updatedAt 不变。

测试实际用两个线程同时导入相同内容，DB 只有一个非空 content_hash。

## 12. 事务边界

不要把整个文件解析放在一个大事务中：

- 大文件解析可能耗时。
- 长时间占用连接。
- 解析异常会回滚 PROCESSING，状态可能回到 PENDING。

D26 使用：

1. 短事务 claim PROCESSING + 写原始字节。
2. 事务外解析。
3. 短事务 complete 或 fail。

如果解析异常，fail 独立事务把 PROCESSING 改为 FAILED。

## 13. MIME 与状态失败

失败不是只返回异常：

- 文件存在时，记录 FAILED。
- errorCode 稳定。
- errorMessage 安全。
- updatedAt 更新。

容器 multipart 超限无法可靠进入业务状态更新，因此文档保持 PENDING。

## 14. 代码实践

### 登记

```java
KnowledgeDocument document = new KnowledgeDocument();
document.setDocumentId(UUID.randomUUID().toString().replace("-", ""));
document.setStatus(KnowledgeDocumentStatus.PENDING);
repository.register(document);
```

### 导入抢占

```java
UPDATE knowledge_document
SET status='PROCESSING', content_hash=?, ...
WHERE document_id=? AND status IN ('PENDING','FAILED')
```

条件更新避免两个并发请求都成功。

### 完成

```java
repository.complete(documentId, parsed.contentType(), parsed.text(), now);
```

只允许 PROCESSING -> COMPLETED。

### 失败

```java
repository.fail(documentId, errorCode(ex), safeFailureMessage(ex), now);
```

### 幂等

- COMPLETED + 相同 hash：返回当前文档，duplicate=true，不更新 updatedAt。
- COMPLETED + 不同 hash：4091。

## 15. 错误码

| Code | 含义 |
|---:|---|
| 4041 | 文档不存在 |
| 4091 | 状态冲突 |
| 4092 | 内容重复 |
| 4101 | 文件不合法 |
| 4221 | 解析失败 |

HTTP 层仍返回 200，`Result.code` 区分。

## 18. 常见问题

### 登记成功但导入说文档不存在

检查 documentId 和数据库是否已应用 DDL。

### 一直 PENDING

- 尚未调用导入接口。
- 容器 multipart 超限，请求未进入 Service。
- 可修正文件后重试。

### 一直 PROCESSING

异常路径会写 FAILED；若进程在解析中被强制终止，当前没有自动恢复扫描，需要后续任务处理 stale PROCESSING。

### 文件类型正确却失败

检查实际 MIME 和 UTF-8；扩展名不能保证内容类型。

### 重复上传为什么返回 4092

contentHash 已属于其他文档。原文档不会被覆盖，当前文档也未被处理。

### 同文档重复上传是否报错

COMPLETED + 相同 hash 幂等返回 duplicate=true；不同 hash 为 4091。

## 19. 面试与工程应用总结

这个功能的关键不是“保存一个文件”，而是：

- 元数据身份和文件载荷分离。
- 上传内容校验不能信任客户端。
- 状态机需要并发 CAS。
- 文件解析不能放在长数据库事务中。
- 内容去重应以原始字节 hash 为业务键。
- 数据库唯一约束是并发场景的最终一致性保障。
- 失败路径和成功路径都必须有明确终态。
